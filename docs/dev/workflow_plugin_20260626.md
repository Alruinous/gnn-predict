# Workflow 的 idea 构思和实现设计文档

## 背景

LangGraph 主要用于描述和执行 Agent Workflow。当前典型执行方式以节点依赖和状态更新为核心：上游节点完成一次执行并提交结果后，下游节点才会被调度。

这种模式适合决策流程、状态机和步骤较少的 Agent 工作流，但在以下场景中存在限制：

- 上游节点可以持续产生多个数据项
- 下游节点单次处理较慢
- 上下游节点处理速度差异较大
- 希望多个节点同时处理不同数据
- 不希望上游节点等待下游完成后才能继续工作
- 希望提高 Agent Workflow 的资源利用率和整体吞吐量

同时一个本地部署了模型的 AgentNode 中，缺少模型输入输出总 token 上限的预测能力，导致在处理长文本时会因为参数设置不当而出现 OOM 或 提示词截断的问题。

其次在资源有限场景各种，缺少模型驱除和调度的能力，如上游 agent 在完成任务后，可以驱逐模型，将加速卡资源释放给下游 agent 使用，也可以根据资源预测器的预测结果，动态释放资源和启动下游 agent 的模型。

## 创新点

本项目的核心创新方向是把 Agent Workflow 从粗粒度的步骤执行，推进到预测驱动的数据流执行。传统 workflow 运行时通常只在节点完成后调度下游节点，因此调度器看到的是节点级依赖，而不是数据项、session、队列积压和模型资源状态。BufferNode 的价值不只是增加一个缓冲区，而是让系统能够在 workflow 运行过程中观察和控制数据流、资源流和模型生命周期。

第一个创新点是面向 Agent Workflow 的细粒度流水线执行。对于文档分块、批量工具调用和动态任务生成等场景，上游节点可能持续产生多个数据项，下游节点的处理速度也可能显著不同。BufferNode 通过 session 聚合、有界缓冲和背压机制，把原本受 fan-in barrier 限制的执行过程转化为可流水线推进的数据流过程。后续实现应重点验证这种机制能否降低节点空闲时间、提高吞吐，并保持 workflow 语义依赖不被破坏。

第二个创新点是将已有 GNN 预测器从离线资源估计扩展为在线调度信号。预测器不只用于判断某个模型能否运行在某张加速卡上，还应服务于 workflow 运行时的资源决策，包括显存风险、部署成本、推理耗时、功耗和 token 上限。这样系统可以在执行前识别 OOM 或截断风险，在执行中根据预测结果调整处理顺序、资源申请和模型释放策略。

第三个创新点是 workflow-aware 的模型生命周期管理。Agent Workflow 中的模型加载、复用、驱逐和预取不应只由最近访问时间或静态显存大小决定，而应结合 workflow 依赖、上游 ETA、下游队列状态和模型重部署成本。这个方向的目标是在有限加速卡资源下减少冷启动、避免无效换入，并让模型预取发生在真正可能缩短端到端等待的时间窗口内。

第四个创新点是把 token budget 纳入资源控制闭环。对于本地部署的生成式 AgentNode，输入长度和输出上限会直接影响显存峰值、耗时和截断风险。后续实现应探索用预测器为节点规划更合理的输入输出 token 上限，使系统不是在 OOM 或硬截断后被动失败，而是在执行前主动约束生成成本，并尽量保持任务质量。

这些创新点共同指向一个研究目标：让 workflow 结构、节点资源预测和运行时缓冲机制形成闭环。后续 agent 在实现功能时，应优先保留这一主线，避免把系统退化为单纯的队列封装、静态选卡器或普通模型缓存策略。

## 目标

### BufferNode

为 LangGraph 提供 BufferNode 能力。

BufferNode 是一种带有数据缓冲区和内部调度能力的复合节点。上游节点产生的数据先进入 BufferNode，BufferNode 按 session 聚合数据，在数据聚合完成后才触发内部处理逻辑。这样上游节点不需要等待下游节点完成，可以继续处理新的输入或产生新的输出。

#### 核心能力

- BufferNode 内部能够缓冲多个待处理数据
- 上游和下游能够独立并发执行
- 缓冲区容量可以限制
- 如果上游也使用 BufferNode ，下游缓冲区满时能够限制上游的数据处理
- 工作流可以等待缓冲数据全部处理完成后结束

#### 不解决以下问题

- 分布式消息队列
- 跨机器执行
- Exactly-once 语义
- 大规模数据持久化
- 无限数据流
- 自动扩缩容
- 复杂窗口计算
- 复杂多流 Join
- 任意循环数据流
- 对 LangGraph 内部调度器进行深度修改

#### Session 聚合与触发

一个下游节点可能同时依赖多个上游节点的数据。

系统需要用 session 标识把相关数据归为同一组。每个缓冲数据项至少应包含：

- session id
- source node
- payload
- item id

下游节点只有在某个 session 的必需输入齐全后才可以开始执行。

例如下游节点依赖 `chunk_a` 和 `chunk_b` 两个上游结果时，系统应分别缓存同一 session 下来自两个上游的数据。当 `chunk_a` 和 `chunk_b` 都到达后，系统构建该 session 的 prompt，并开始处理。

不同 session 之间可以并发推进。一个 session 等待缺失上游数据时，不应阻塞其他已经就绪的 session。

#### 失败与重试

Consumer 处理失败时，系统应支持重试。

用户至少可以配置：

- 最大重试次数
- 重试等待时间
- 重试失败后是否终止整个工作流
- 重试失败后是否跳过当前数据

失败的数据不能在没有记录的情况下静默丢失。

#### BufferNode 核心目标

目标主要验证 BufferNode 是否能够改善 Agent Workflow 中的细粒度并发和节点吞吐。

### Adaptive Resource Management

实现一个控制器，控制器中提供一个资源预测器，预测器暂时只使用项目中现有的 GNN 预测器。

控制器负责维护全局 workflow 的调度，维护一个全局的加速卡资源池。

#### 资源预测

控制器内维护一个常驻的 GNN 预测器，提供资源预测服务。

#### 加速卡资源管理

BufferNode 向控制器申请加速卡资源，控制器维护一个全局的加速卡资源池，负责分配和回收加速卡资源。

## 典型使用场景

### 文档分块处理

一个文档读取节点持续产生多个文本块。

后续摘要节点处理每个文本块需要较长时间。

使用 Buffered Node 后，文档读取节点可以继续产生文本块，不需要等待每个摘要任务完成。

### 批量工具调用

规划节点产生多个工具调用任务。

工具执行节点通过多个并发实例处理这些任务。

规划节点和工具执行节点之间通过缓冲区解耦。

### 动态任务生成

一个 Agent 节点在执行过程中持续发现新的子任务。

新任务进入缓冲区，由后续 Worker 节点逐个或并发处理。
