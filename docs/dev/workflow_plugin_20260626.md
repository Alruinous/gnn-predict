# LangGraph Buffered Node 需求文档

## 背景

LangGraph 主要用于描述和执行 Agent Workflow。当前典型执行方式以节点依赖和状态更新为核心：上游节点完成一次执行并提交结果后，下游节点才会被调度。

这种模式适合决策流程、状态机和步骤较少的 Agent 工作流，但在以下场景中存在限制：

- 上游节点可以持续产生多个数据项
- 下游节点单次处理较慢
- 上下游节点处理速度差异较大
- 希望多个节点同时处理不同数据
- 不希望上游节点等待下游完成后才能继续工作
- 希望提高 Agent Workflow 的资源利用率和整体吞吐量

本产品希望为 LangGraph 增加一种带缓冲能力的节点类型，使部分工作流可以从“步骤驱动”扩展为“数据驱动”。

## 目标

为 LangGraph 提供 Buffered Node 能力。

Buffered Node 是一种带有数据缓冲区和内部调度能力的复合节点。上游节点产生的数据先进入 Buffered Node，Buffered Node 按 session 聚合数据，并在下游输入就绪后调度内部 Consumer 处理。

在缓冲区未满时，上游节点不需要等待下游节点完成，可以继续处理新的输入或产生新的输出。

对于原始 `A/B -> C` 的工作流，可以通过插入 Buffered Node `D` 改写为 `A/B -> D -> C`。`D` 负责缓存来自 `A` 和 `B` 的数据、判断 session 是否就绪、并将处理结果传递给 `C`。

产品需要实现以下核心能力：

- Buffered Node 内部能够缓冲多个待处理数据
- 上游和下游能够独立并发执行
- Buffered Node 内部 Consumer 能够配置多个并发执行实例
- 缓冲区容量可以限制
- 缓冲区满时能够限制上游继续生产
- 工作流可以等待缓冲数据全部处理完成后结束

不解决以下问题：

- 分布式消息队列
- 跨机器执行
- Exactly-once 语义
- 大规模数据持久化
- 无限数据流
- 自动扩缩容
- 复杂窗口计算
- 复杂多流 Join
- 任意循环数据流
- 对 LangGraph 内部调度器进行深度修改

目标主要验证 Buffered Node 是否能够改善 Agent Workflow 中的细粒度并发和节点吞吐。

## 典型使用场景

### 文档分块处理

一个文档读取节点持续产生多个文本块。

后续摘要节点处理每个文本块需要较长时间。

使用 Buffered Node 后，文档读取节点可以继续产生文本块，不需要等待每个摘要任务完成。

### 批量工具调用

规划节点产生多个工具调用任务。

工具执行节点通过多个并发实例处理这些任务。

规划节点和工具执行节点之间通过缓冲区解耦。

### 动态任务生成

一个 Agent 节点在执行过程中持续发现新的子任务。

新任务进入缓冲区，由后续 Worker 节点逐个或并发处理。

## Methodology

### Buffered Node

普通 Edge 依然保留 LangGraph 原有语义。新增 Buffered Node 类型，用一个节点承载异步缓冲、session 聚合和 Consumer 调度。

上游每产生一个数据项，都可以将数据写入 Buffered Node 的缓冲区。缓冲区按 session 归集来自一个或多个上游节点的数据；当某个 session 满足下游节点声明的输入依赖后，该 session 才进入下游待处理队列。上游和下游不需要保持相同的处理速度，也不需要逐次同步执行。

Buffered Node 不要求等待所有 Producer 完整结束。等待范围仅限于同一个 session 内下游节点构建 prompt 所需的上游数据。

### 图改写方式

Buffered Node 通过插入节点实现缓冲语义，不修改 LangGraph 原生 Edge 调度。

例如原始工作流：

```text
A
 \
  -> C
 /
B
```

可以改写为：

```text
A
 \
  -> D -> C
 /
B
```

其中 `D` 是 Buffered Node。`D` 接收来自 `A` 和 `B` 的数据，按 session 聚合输入，并在 session 就绪后执行内部 Consumer。`C` 只接收 `D` 输出的处理结果。

### Buffer

Buffer 用于保存已经由上游产生、但尚未被下游处理的数据。

Buffer 应当具备以下属性：

- 有限容量
- 默认先进先出
- 可以观察当前积压量
- 可以判断是否为空或已满
- 支持关闭
- 支持等待全部数据处理完成

### Session 聚合与触发

一个下游节点可能同时依赖多个上游节点的数据。

系统需要用 session 标识把相关数据归为同一组。每个缓冲数据项至少应包含：

- session id
- source node
- payload
- item index 或顺序标识

下游节点只有在某个 session 的必需输入齐全后才可以开始执行。

例如下游节点依赖 `chunk_a` 和 `chunk_b` 两个上游结果时，系统应分别缓存同一 session 下来自两个上游的数据。当 `chunk_a` 和 `chunk_b` 都到达后，系统构建该 session 的 prompt，并将它提交给 Consumer 处理。

不同 session 之间可以并发推进。一个 session 等待缺失上游数据时，不应阻塞其他已经就绪的 session。

## 功能需求

### 创建 Buffered Node

用户可以在任意符合要求的上游和下游之间插入 Buffered Node。

Buffered Node 至少允许配置：

- Buffer 容量
- 下游并发度
- 数据顺序要求
- 缓冲区满时的行为
- 节点失败后的处理方式

Buffered Node 必须在工作流定义中明确声明。普通 Edge 仍使用 LangGraph 原有语义。

### 有界缓冲

Buffer 必须支持容量限制。

默认情况下不允许无限积压数据。

容量表示尚未完成处理的数据项数量上限。

当 Buffer 达到容量上限时，默认行为是阻塞上游，而不是丢弃数据。

### 背压

当下游长期慢于上游时，Buffer 最终会被填满。

此时系统必须向上游施加背压。

背压发生后：

- 上游不能继续向该 Buffer 写入数据
- 上游节点可以暂停等待
- 下游消费数据后，上游恢复运行
- 系统应记录 Buffer 满事件

第一版本以阻塞上游作为默认且主要的背压策略。

### 细粒度并发

Buffered Node 内部 Consumer 可以设置并发度。

例如下游并发度为 4 时，最多可以同时处理 4 个不同数据项。

并发度仅影响 Buffered Node 内部同时处理的数据数量，不改变 DAG 的逻辑关系。

### 持续输出

Producer 节点可以在单次运行中产生多个输出。

系统不需要等待 Producer 完整结束后才将所有结果交给下游。

每个输出产生后，应尽快进入 Buffer，并允许内部 Consumer 处理已经就绪的 session。

这是产品区别于普通 LangGraph 节点执行方式的核心能力。

如果目标处理逻辑依赖多个上游输入，单个输出进入 Buffer 后不一定立即触发处理。系统应先检查对应 session 的输入依赖是否齐全；只有就绪 session 才会被内部 Consumer 获取。

### 顺序保证

第一版本默认保证单个 Buffered Node 内同一输入流的数据按照写入顺序进入消费流程。

当 Consumer 并发度大于 1 时：

- 数据开始处理的顺序应尽量保持
- 数据完成处理的顺序不保证一致

### 失败与重试

Consumer 处理失败时，系统应支持重试。

用户至少可以配置：

- 最大重试次数
- 重试等待时间
- 重试失败后是否终止整个工作流
- 重试失败后是否跳过当前数据

失败的数据不能在没有记录的情况下静默丢失。

第一版本不承诺进程崩溃后的数据恢复。

### 工作流结束

Buffered Workflow 不能在 Producer 结束时立即结束。

只有满足以下条件，工作流才算完成：

- 所有 Producer 已停止产生新数据
- 所有 Buffer 不再接收新数据
- 所有 Buffer 已清空
- 所有 Consumer 当前任务已完成
- 没有等待重试的数据

系统需要支持优雅结束，即等待已产生的数据全部处理完成。

### 主动停止

用户可以主动停止工作流。

支持两种停止模式：

立即停止：

- 停止所有节点
- 不保证 Buffer 中数据被处理
- 尽快结束工作流

排空后停止：

- 停止 Producer 产生新数据
- 继续处理 Buffer 中已有数据
- 所有数据处理完成后结束
