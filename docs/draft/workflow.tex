\section{Scope and Candidate Claims}

This fragment focuses on lifecycle management for agentic workflows running on
a fixed, user-controlled accelerator pool. The runtime exposes workflow and
session state, while a resource predictor estimates execution time and peak
memory for each local LLM activation. The lifecycle layer uses those forecasts
to compare reuse, load, prefetch, reclaim, and defer actions without violating
workflow dependencies or memory admission.

The candidate claims are deliberately narrower than an end-to-end workflow
scheduler:

\begin{itemize}
    \item A shared lifecycle layer coordinates model state, accelerator capacity,
    and workflow readiness.
    \item Resource forecasts become plan-level admission constraints rather than
    direct placement decisions.
    \item Cross-session DAG lookahead enables safe preparation before an
    activation becomes ready.
\end{itemize}

\section{Motivation}

\subsection{Chain Workflow}

A chain workflow with $n$ sequential LLM nodes and $m$ independent sessions
exposes a structural resource-waste problem. Let $t_{i,j}$ be the active LLM
execution time of node $i$ on session $j$, and let
$A=\sum_i\sum_j t_{i,j}$ be the active GPU-seconds. Let $G\ge 0$ denote the
remaining execution span in which none of the chain models is active, including
arrival gaps and intervening non-LLM work. The makespan is $T=A+G$. If all $n$
model instances remain resident throughout this span, their resident GPU-seconds
are $R_{\mathrm{static}}=nT$, yielding
\[
    \rho_{\mathrm{static}}
    = \frac{R_{\mathrm{static}}}{A}
    = n\left(1+\frac{G}{A}\right)
    \ge n.
\]

We validate this bound on MBPP~\cite{austin2021program} with a
\texttt{coder $\rightarrow$ reviewer $\rightarrow$ repair} chain. The three
stages use Qwen3-14B, Qwen3-8B, and Qwen3-14B on separate GPUs. Across 60
sessions, active and resident GPU-seconds are 5,656 and 17,017, respectively,
giving a measured gap of 3.009 (Table~\ref{tab:mbpp_empirical}).

\begin{table}[htbp]
    \centering
    \caption{MBPP chain resource gap ($n=3$, $m=60$).}
    \label{tab:mbpp_empirical}
    \begin{tabular}{lr}
        \toprule
        Metric & Value \\
        \midrule
        Active GPU-seconds & 5,656 \\
        Resident GPU-seconds & 17,017 \\
        Resource gap $\rho$ & 3.009 \\
        \bottomrule
    \end{tabular}
\end{table}

This bound is specific to a chain whose distinct stage models are resident
concurrently. It should not be generalized to workflows backed by one shared
model or to runtimes that already load models on demand.

\section{Prediction-Aware Lifecycle Scheduling}
\label{sec:lifecycle-scheduling-draft}

\subsection{Scope and Abstraction}

The runtime serves multiple workflow instances from a shared accelerator and
model pool. An activation $x=(w,s,v)$ identifies workflow $w$, session $s$, and
node $v$. Workflow-local state remains isolated, while compatible physical model
instances may be reused across activations. The scheduler operates on two
frontiers: ready activations $\mathcal{R}_t$, whose dependencies are satisfied,
and near-ready activations $\mathcal{N}_t$, whose release times can be estimated
from running predecessors.

The scheduling interface contains only the required model, candidate device,
predicted resource envelope, and legal lifecycle actions. Backend bookkeeping
that does not change the decision or a stated invariant remains outside this
abstraction.

\subsection{Forecasts and Candidate Plans}

For activation $x$ on device $g$, the forecaster exposes
\begin{equation}
    \widehat{K}(x,g)=\left\langle
        \hat{t}_{\mathrm{ready}},
        \hat{t}_{\mathrm{load}},
        \hat{t}_{\mathrm{run}},
        U_{\mathrm{mem}}
    \right\rangle,
    \label{eq:lifecycle-contract}
\end{equation}
where the time estimates guide ordering and prefetch, while
$U_{\mathrm{mem}}$ is a calibrated upper bound used for admission. The GNN may
provide execution time and peak-memory estimates from the model graph and token
regime; online measurements provide model-load costs and current residency.
The predictor is therefore an input to scheduling, not the scheduling policy
itself.

For each activation-device pair, the planner constructs a small set
$\Pi(x,\mathcal{S}_t)$ of executable lifecycle plans: reuse a compatible
resident instance, load the model on free capacity, or reclaim idle state before
loading. If none is safe, the activation is deferred. A load is a prefetch when
it starts before the activation becomes ready. Near-ready activation $x$ becomes
eligible when
\begin{equation}
    \hat{t}_{\mathrm{ready}}(x)-t
    \le \hat{t}_{\mathrm{load}}(x)+\delta,
    \label{eq:prefetch-window}
\end{equation}
where $\delta$ absorbs forecast uncertainty and $\hat{t}_{\mathrm{load}}(x)$ is
the shortest predicted load time among candidate-device plans. Ready work always
precedes speculative prefetch. We write
$\Pi_{\mathrm{pfx}}(x,\mathcal{S}_t)\subseteq\Pi(x,\mathcal{S}_t)$ for plans
that prepare state without dispatching the activation.

A plan is feasible only if its dependencies and model compatibility hold and its
predicted peak, including transient overlap during reclamation and loading, fits
the target device. Selecting a plan reserves the state and capacity on which the
decision depends; otherwise a concurrent lifecycle action could invalidate the
admission check before dispatch.

\subsection{One Scheduling Event}

The runtime invokes Algorithm~\ref{alg:lifecycle-scheduling-event} on arrivals,
completions, and material state changes. Each invocation admits ready work first,
considers prefetch only when ready work cannot progress, and defers when no safe
plan exists.

\begin{algorithm}[t]
    \caption{Prediction-aware lifecycle scheduling event.}
    \label{alg:lifecycle-scheduling-event}
    \KwIn{Ready frontier $\mathcal{R}_t$, near-ready frontier $\mathcal{N}_t$,
    runtime state $\mathcal{S}_t$, forecaster $f_\theta$}
    \KwOut{A reserved lifecycle plan or \textsc{Defer}}

    $\mathcal{R} \gets \operatorname{RankReady}(\mathcal{R}_t,\mathcal{S}_t)$\;
    \ForEach{$x\in\mathcal{R}$}{
        $\mathcal{B}\gets\operatorname{Safe}
        (\Pi(x,\mathcal{S}_t),f_\theta)$\;
        \If{$\mathcal{B}\neq\emptyset$}{
            $b^*\gets\arg\min_{b\in\mathcal{B}}\widehat{J}(b)$\;
            \Return{$\operatorname{Reserve}(b^*,\mathcal{S}_t)$}\;
        }
    }
    $\mathcal{N}\gets\{x\in\mathcal{N}_t\mid
    \hat{t}_{\mathrm{ready}}(x)-t\le\hat{t}_{\mathrm{load}}(x)+\delta\}$\;
    \ForEach{$x\in\operatorname{RankNear}(\mathcal{N},\mathcal{S}_t)$}{
        $\mathcal{B}\gets\operatorname{Safe}
        (\Pi_{\mathrm{pfx}}(x,\mathcal{S}_t),f_\theta)$\;
        \If{$\mathcal{B}\neq\emptyset$}{
            $b^*\gets\arg\min_{b\in\mathcal{B}}\widehat{J}(b)$\;
            \Return{$\operatorname{Reserve}(b^*,\mathcal{S}_t)$}\;
        }
    }
    \Return{\textsc{Defer}}\;
\end{algorithm}

\textsc{RankReady} is the interface to the upstream workflow policy; it may use
critical-path slack, tenant weights, or FIFO without changing lifecycle
admission. $\Pi$ contains only semantically distinct actions, while
\textsc{Safe} applies compatibility and calibrated peak-memory checks.
$\widehat{J}$ compares predicted workflow delay with load, reconstruction, and
future-reuse costs. This separation permits a different upstream ordering policy
without weakening lifecycle safety.

\subsection{Boundary Relative to Prior Systems}

Parrot exposes request dependencies and prompt-prefix relationships to support
application-centric placement and reuse~\cite{lin2024parrot}. Kairos ranks
requests using workflow-derived remaining-latency distributions and dispatches
them using memory demand~\cite{chen2025kairos}. Murakkab separates declarative
workflow structure from execution configuration and uses profiles to choose
models and hardware under SLOs~\cite{chaudhry2025murakkab}. SAGA treats an agent
workflow as the scheduling unit to preserve KV continuity and provide
workflow-level fairness~\cite{guo2026saga}.

These systems motivate exposing workflow structure but operate at different
decision boundaries. The narrow claim here is that resource prediction turns
each activation into a small set of lifecycle plans, and that admission selects
only a plan whose preparation path is safe. Cross-workflow ordering and victim
selection remain policy choices unless coupled to a new objective or guarantee.
