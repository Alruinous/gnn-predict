# Workflow 数据集与 GNN 调度边界调研 20260613

## 背景

本文记录对论文 Murakkab: Resource-Efficient Agentic Workflow Orchestration in Cloud Platforms 的阅读结论，以及它对当前项目 workflow 模块的可借鉴部分。

论文地址: https://arxiv.org/html/2508.18298v2

当前项目的 GNN 预测器面向本地部署模型的系统性能预测。输入是模型结构、ONNX 图特征、runtime 和 GPU 类型，输出是部署耗时、运行耗时、显存、功耗等指标。workflow 模块中，GNN 不负责主 agent 的质量、推理逻辑、外部 provider 延迟或业务答案正确性。

## 论文使用的数据来源

论文没有提出一个可直接训练系统性能预测器的新数据集。它把数据来源拆成几类:

| 数据来源 | 类型 | 论文中的作用 | 是否适合直接用于本项目 GNN |
| --- | --- | --- | --- |
| VideoMME | 视频问答 benchmark | 评估 Video Q/A workflow 的回答质量 | 不适合 |
| HumanEval | 代码生成 benchmark | 评估 Code Generation workflow 的代码质量 | 不适合 |
| MATH | 数学问答 benchmark | 评估 Math Q/A workflow 的答案质量 | 不适合 |
| Azure LLM serving traces | 请求到达 trace | 模拟多租户请求负载和流量变化 | 不适合直接使用 |
| Workflow 结构与配置组合 | 作者构造 | 定义 Video Q/A、Code Generation、Math Q/A 的 DAG 和参数空间 | 可借鉴结构 |
| 模型/硬件 profile | 作者采集 | 得到模型在硬件上的延迟、能耗、吞吐等系统指标 | 方法可借鉴 |

准确说，论文不是纯自己造数据集。它使用公开 benchmark 和公开 trace，但把这些数据组合成自己的 workflow evaluation suite。真正与系统调度直接相关的 model profile 是作者自己采集的。

## 为什么不直接使用这些数据集

当前项目的 GNN 预测器需要的数据是:

```text
模型结构 / ONNX 图 / runtime / GPU 类型
  -> 部署耗时 / 运行耗时 / 显存 / 功耗
```

VideoMME、HumanEval 和 MATH 提供的数据更接近:

```text
输入问题 / 视频 / 代码题 / 数学题
  -> 答案是否正确 / 任务质量
```

两者标签口径不同。公开 benchmark 可以说明一个 workflow 在业务上是否有效，但不能告诉项目中某个 ONNX 图在 V100 或 A100 上的部署耗时、显存峰值或功耗。因此它们不适合作为当前 GNN 的训练数据。

Azure LLM serving trace 也不能直接使用。它描述的是 LLM 请求到达、负载变化和请求类别，不包含当前项目需要的本地小模型 ONNX 图、GPU 显存、部署耗时和运行耗时。

## 当前项目的合理边界

workflow 中的主 agent 使用外部 LLM provider 接口。它不使用项目内变体模型，也不进入 GNN 预测器。GNN 只作用于本地 tool 节点。

| 节点类型 | 执行方 | GNN 是否预测 | 是否参与本地 GPU 调度 |
| --- | --- | --- | --- |
| `agent` / `planner` | 外部 LLM provider | 否 | 否 |
| `tool` | 本地部署小模型 | 是 | 是 |
| `input` / `output` | workflow 边界 | 否 | 否 |

这个边界的好处:

- GNN 只预测有训练数据支撑的对象。
- 外部 LLM provider 的延迟、限流、费用和排队不污染 GNN target。
- workflow 仍保留 agent 节点，用来表达工具选择和控制流。
- 当 agent 决定调用某个 tool 后，GNN 对该 tool 的候选 GPU 代价做实时预测。

在这个实时场景下，不需要建模工具调用概率。因为 agent 已经决定要调用某个工具，当前工具调用概率就是 1。调用概率只适合预热、长期缓存保留或多租户容量规划；这些不是当前项目的核心边界。

## 论文值得借鉴的部分

### Profile 分层

论文区分 workflow profile 和 model profile。workflow profile 描述质量、SLO、请求形态和配置空间；model profile 描述模型在硬件上的延迟、能耗、吞吐等系统指标。

当前项目的 GNN 更接近 model profile。它应该继续预测工具模型在不同 GPU 上的系统性能，而不是预测 benchmark 任务质量。

### DAG-aware scheduling

论文强调 workflow/DAG 可见性对调度有价值。当前项目可以借鉴这个方向，但应保持轻量:

- 对 ready tool 集合做实时预测。
- 根据显存风险决定并行或分批。
- 根据 `deploy + run` 估计关键路径节点优先级。
- 在显存受限时优先避免 OOM 和 retry。
- 利用 cache hit 降低冷启动成本。

这比全局多租户 MILP 优化更适合当前项目规模。

### 资源约束实验

论文有动态资源可用性实验。当前项目可以缩小成受控场景:

```text
V100 可用显存 4GB / 8GB / 12GB
A100 可用显存 8GB / 14GB / 24GB
某张卡已有缓存 / 无缓存
某张卡不可用
```

这些场景不需要真实 workflow trace，但能检验 GNN-aware 调度是否优于 `static_size`、`a100_first`、`round_robin` 等 baseline。

## 从真实 benchmark 总结工具类型

虽然不能直接使用 VideoMME、HumanEval、MATH 的样本训练 GNN，但可以从它们代表的任务中总结工具类型，再转换为当前项目已有变体模型能够表达的 workflow。

| benchmark / workflow | 原始工具类型 | 项目内可替代 tool 节点 |
| --- | --- | --- |
| VideoMME / Video Q&A | 抽帧、场景理解、目标检测、语音文本理解、多模态回答 | `mobilenet` / `resnet` / `densenet` 图像分类，`yolov5` / `yolov8` 目标检测，`gpt2` 文本分类，`qwen3` / `t5` 生成 |
| HumanEval / Code Generation | 需求理解、代码生成、测试生成、结果判断、解释 | `gpt2` prompt 分类，`qwen3` decode 代码生成，`t5` / `qwen3` 测试或解释生成 |
| MATH / Math Q/A | 题型分类、解题、反思验证、最终答案 | `gpt2` 题型分类，`qwen3` decode 解题，`qwen3` / `t5` verifier 或 finalizer |

真实视频解码、Python 解释器、外部 ASR 和远程 LLM provider 不应硬塞进 GNN 数据集。它们可以作为外部节点或非 GNN 节点记录，但不参与本地 GPU 模型调度预测。

## 建议的 proxy workflow

更准确的命名是 benchmark-inspired workflow proxy dataset。它不是复刻真实 benchmark 数据，而是用真实任务形态构造项目可预测的本地模型负载。

### `videomme_proxy`

```text
input
  -> planner
  -> scene_classifier
  -> object_detector
  -> transcript_classifier
  -> answer_draft
  -> output
```

| node | type | 建议模型 | phase | 作用 |
| --- | --- | --- | --- | --- |
| `planner` | agent | external LLM provider | external | 决定调用哪些本地工具 |
| `scene_classifier` | tool | `mobilenetv2_100` / `resnet18` | inference | 图像或关键帧场景分类 |
| `object_detector` | tool | `yolov5n` / `yolov8n` | inference | 检测关键帧对象 |
| `transcript_classifier` | tool | `gpt2` | inference | 对文本或转写内容做意图/主题分类 |
| `answer_draft` | tool | `qwen3` / `t5` | decode | 本地生成草稿或摘要 |

### `humaneval_proxy`

```text
input
  -> planner
  -> prompt_classifier
  -> code_draft
  -> test_draft
  -> verdict_summarizer
  -> output
```

| node | type | 建议模型 | phase | 作用 |
| --- | --- | --- | --- | --- |
| `planner` | agent | external LLM provider | external | 决定代码任务工具链 |
| `prompt_classifier` | tool | `gpt2` | inference | 识别题目类型或复杂度 |
| `code_draft` | tool | `qwen3` | decode | 生成代码草稿 |
| `test_draft` | tool | `t5` / `qwen3` | decode | 生成测试或检查说明 |
| `verdict_summarizer` | tool | `t5` / `qwen3` | decode | 汇总结果 |

### `math_proxy`

```text
input
  -> planner
  -> problem_classifier
  -> solution_draft
  -> self_reflection
  -> final_answer
  -> output
```

| node | type | 建议模型 | phase | 作用 |
| --- | --- | --- | --- | --- |
| `planner` | agent | external LLM provider | external | 决定是否调用分类、求解、验证工具 |
| `problem_classifier` | tool | `gpt2` | inference | 题型分类 |
| `solution_draft` | tool | `qwen3` | decode | 生成解题过程 |
| `self_reflection` | tool | `qwen3` | decode | 生成验证或反思 |
| `final_answer` | tool | `t5` / `qwen3` | decode | 生成最终答案 |

## 不建议做的事

- 不把 VideoMME、HumanEval、MATH 直接当作 GNN 训练数据。
- 不让 GNN 预测主 agent 的外部 provider 延迟、费用或限流。
- 不把工具调用概率作为当前实时调度的核心输入。
- 不引入完整多租户 trace、全局 MILP、长周期容量规划作为当前阶段目标。
- 不把 workflow YAML 写成真实运行结果记录。

## 建议的项目表述

当前项目可以这样描述 workflow 模块与 GNN 的关系:

```text
主 agent 由外部 LLM provider 执行，负责选择工具和控制流程。
本地 tool 节点由项目内小模型实现，可导出 ONNX 并部署到本地 GPU。
GNN 预测器只作用于这些 tool 节点，实时估计候选 GPU 上的部署耗时、运行耗时、显存和功耗。
workflow 调度器基于预测结果进行选卡、分批、OOM 避免、缓存复用和关键路径优先。
```

论文的价值不在于提供现成数据集，而在于提供数据组织和实验设计思路: 质量 benchmark 与系统性能 profile 分离，workflow DAG 对调度可见，资源约束下用 profile 驱动调度决策。
