# 为什么 serve_fix_20260725 和 serve_0726 差这么多（2026-07-26）

结论：**差异的主导项不是调度策略，是「拿到槽位」到「真正开始生成」之间的握手延迟。**
它在不同 run 之间差 18 倍，并且随积压自我放大，最终被放大成 4.3 倍的端到端延迟差。

## 1. 先排除所有其他解释

两批数据（6 workflow、1×A100+2×V100、120 会话）逐项核对：

| 检查项 | 结果 |
|---|---|
| 修复代码是否合并 | `becb1c5` 在 main 历史中；`main..worktree` 无未合并提交；`src/workflow/` **零差异** |
| 模型 key 结构 | 两批均 4 个 key、热键 70.6% |
| 每个会话的到达时刻 | **逐条一致，最大差 1 毫秒** |
| 工作量 | 输入 814k token、输出 108k token、880 任务，两批相同；分 workflow 也对得上 |
| 显卡速度 | 全部 V100 在 27.0–29.2 tok/s，无坏卡 |
| cache 用的物理卡 | 两次完全相同的 3 张 |

排除干净。

## 2. 瓶颈是单一副本

合并 key 后 Qwen3-4B@8192 占 70.6% 的请求，而调度器每个「模型 + 卡型」只允许一个副本
（`_replica_pairs`），所以这 480 个请求全部挤在**一张 V100** 上。第二张 V100 只服务
17.6%（8B 11.8% + 1.7B 5.9%），在 8B 与 1.7B 之间反复抖动。A100 被 14B 独占。

四个 run 的热副本都精确服务 480 个请求。**吞吐上限完全由这一张卡决定。**

## 3. 决定性指标：授予槽位 → 开始生成

热副本上 480 个请求，从 `acquire_granted` 到 vLLM 真正开始生成的间隔：

| run | 平均间隔 | 累计 | 忙时平均并发(上限3) | 平均延迟 |
|---|---|---|---|---|
| serve_fix FIFO | 2.36s | **1135s** | 1.74 | 703 |
| 新 CACHE | 1.50s | **722s** | 1.80 | 598 |
| serve_fix CACHE | 0.60s | 286s | 1.91 | 408 |
| 新 FIFO | **0.13s** | **61s** | **2.28** | **162** |

**四个 run 完全单调**，跨两批、跨两种策略。

槽位在这段间隔里被占着但没在算。热副本驻留约 2000–2500 秒 × 3 个槽位，浪费 1135 秒
就等于丢掉 15% 的算力。

交叉验证：直接测「热副本空闲、但该模型有请求在排队」的时间，得到
624s / 328s / 77s / 9s——与上表同序、同量级。

## 4. 它会自我放大

在途会话数越多，握手越慢：

| 在途会话数 | serve_fix FIFO | 新 FIFO |
|---|---|---|
| 0–9 | 0.31s | 0.05s |
| 10–19 | 1.26s | 0.09s |
| 20–29 | 1.96s | 0.36s |
| 30–39 | 2.59s | — |
| 40–49 | 3.58s | — |

**正反馈**：积压 → 握手变慢 → 有效批并发下降 → 吞吐下降 → 积压更多。

系统本来就在饱和线附近（热副本需要约 1.6 的并发才能跟上到达，实测 1.74–2.28），
所以这个环路把很小的初始扰动放大成 4.3 倍的延迟差。

## 5. 还有一个调度器之外的基线差

注意上表：**在相同积压水平下，新 FIFO 的握手仍比 serve_fix FIFO 快 6–14 倍**
（0-9 个在途时 0.05s vs 0.31s）。这部分不是反馈环造成的，来自调度器外部——
Ray actor 通信、分词、以及当时机器上并行跑了几个实验的 CPU 争抢。
serve_fix 当时 2 个 run 并行，serve_0726 是 4 个并行，但物理主机分布未记录，无法从
trace 复原。

## 6. 结论与待办

**这套实验目前主要测的是握手延迟的噪声，不是调度策略的好坏。** 策略之间最大约 2 倍的
差距，小于同一策略重复跑的 4.3 倍差距。在控制住第 5 节那个基线差之前，任何策略排名都不可信。

按优先级：

1. **把握手延迟变成一等指标**：每个 run 报告热副本的「授予→开始生成」均值与累计。
   它现在是隐藏的主导变量，必须显式记录。
2. **控制并行度与主机分布**：记录每个 run 同时有几个实验在跑、各 pod 落在哪台物理机。
   同一批对照必须并行度相同。
3. **每个方案重复跑 3 次**，报均值与范围。runbook 之前以「共用到达序列即成对对照」为由
   去掉重复（`97be808`），该理由已被证伪——到达序列一致到 1 毫秒，结果仍差 4.3 倍。
4. **考虑放开单副本限制**：热模型占 70.6% 需求却只能占一张卡，是这个瓶颈的结构性来源。
