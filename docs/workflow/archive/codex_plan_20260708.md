# [Historical Archive] Workflow Runtime Implementation Plan

> This document is the approved design snapshot from 2026-07-08. It is superseded by
> [`docs/workflow/implementation.md`](../implementation.md). Its single-task worker,
> Hugging Face backend, ONNX pipeline, separate deployment profile, and dynamic token
> budget describe an earlier implementation stage and are not current runtime contracts.

**Goal:** Implement the `dev.md` workflow runtime as a general Ray actor + Ray Queue system for agent workflow execution, model lifecycle management, prediction-aware scheduling, token-budget control, and traceable evaluation.

**Architecture:** Workflow graph execution is owned by this repository's runtime, not by LangGraph. Phase 1 agent nodes perform one scheduler-granted model inference and return a LangChain-compatible `AgentState`; future multi-turn LangChain/LangGraph logic remains local to an agent node. The controller and scheduler own DAG state, queues, resource accounting, model-replica lifecycle, prediction, prefetch, eviction, and trace recording.

**Tech Stack:** Python 3.12, `uv`, Ray actors, Ray Queue, Pydantic, LangChain/LangGraph inside agent nodes, Hugging Face Transformers, PyTorch, offline PyG graph features, existing workflow ONNX/cache pipeline, offline GNN prediction cache, pytest, Ruff, ty.

## Confirmed Scope

- Current workflow runtime supports `agent` nodes and registered `function` nodes. Agent nodes execute one model-backed `AgentState` transition. Function nodes execute application-provided Python callables without model-resource acquisition.
- Do not model `input` and `output` as runtime nodes in the current implementation. External submission and result collection are controller/runtime boundary operations, not extra Ray Queue hops.
- Do not add `tool` nodes in this stage. Future tool use should be implemented inside LangGraph/LangChain agent logic and exposed to this runtime as part of an agent node.
- Remove `evaluator` as a workflow node concept. Evaluation belongs to experiment or benchmark code as an evaluation function over workflow outputs and dataset references.
- Runtime code must remain generic and must not be hard-coded to QMSum, MBPP, or a fixed agent graph.
- A function-node implementation may be workload-specific, but the runtime only knows its registered name and generic input/output contract.

Node configuration uses a discriminated contract. An `agent` node requires model and execution configuration and cannot declare a function. A `function` node requires a registered function name, may declare function-specific parameters, and cannot declare model execution or token-budget configuration. Function routing is `broadcast` by default and may be `targeted` when the callable must produce a distinct state for each static successor. Invalid combinations fail during workflow parsing rather than inside a worker.

The runtime receives function implementations explicitly when the workflow is constructed:

```python
WorkflowController(
    workflow,
    functions={"split_qmsum": split_qmsum},
)
```

Workflow YAML names a registered function but does not contain an arbitrary Python import path. Missing registrations fail before queues or actors are created.

## Data Item And Session Semantics

`session_id` identifies exactly one external workflow request. It is similar to a backend request trace id: the internal call chain can fan out, join, load models, retry, and emit many trace events, but all runtime work still belongs to one request. The controller must reject repeated external `submit` calls for the same `session_id`.

External submission carries structured raw request data:

```python
controller.submit(session_id: str, inputs: dict[str, JsonValue])
```

The controller records `session_submitted` before storing or enqueueing the request, writes `inputs` to the Ray object store once, and retains the resulting `session_input_ref` until the session reaches terminal success or failure. Workflow validation requires exactly one static entry node and one static terminal node. The controller enqueues one initial item to the entry node; an artificial input node is not required.

`WorkflowDataItem` is the only data-plane transfer unit between executable nodes:

```python
WorkflowDataItem(
    session_id: str,
    item_id: str,
    source_node: str | None,
    target_node: str,
    message: AgentState,
    session_input_ref: ray.ObjectRef,
)
```

All items in one session reuse the same immutable `session_input_ref`. Long source text is therefore stored once rather than copied through every fan-out branch. Workers pass the reference through unchanged and resolve it only when the current node needs request fields for function execution or prompt rendering.

`item_id` is generated by `WorkflowDataItem` and uniquely identifies that transferred data-item instance. It is used for queue and edge trace, failure provenance, and retry correlation, but it is not a node-execution id or semantic dependency key. `task_id` separately identifies one session-specific node execution; a fan-in task records all consumed `input_item_ids`.

The controller-created initial item uses `source_node=None` and `target_node` equal to the single entry node because the external request has no predecessor inside the workflow DAG. This is the only legal case where `source_node` is absent.

For every item emitted by an executable node, `source_node` and `target_node` are non-empty node names and must identify a real static DAG edge. Fan-in, target-specific fan-out, queue metrics, scheduling decisions, and trace records use this edge-level provenance.

`message` remains `AgentState`. This is intentional: LangGraph/LangChain agents can read prior node outputs, structured results, code execution results, or other agent state without forcing the workflow runtime to model each internal operation as a separate node type. Session inputs do not become ad hoc extra keys in `AgentState`; they remain behind `session_input_ref`, and the worker creates a fresh invocation state after rendering the prompt.

A function node invokes a registered callable with immutable session inputs and source-indexed upstream states. A broadcast function returns one `AgentState`, which follows the same broadcast or terminal-result path as an agent result. A targeted function returns `dict[target_node, AgentState]`; its returned target set must exactly equal the static successor set, and every target receives one item. Entry functions such as QMSum text splitting can therefore emit different chunks to `chunk_0` through `chunk_5` without introducing dynamic fan-in or an artificial input node. A terminal function must use broadcast routing and returns one `AgentState`.

Before invoking an agent node, the worker builds a standard prompt context from session inputs and source-indexed upstream states. The first implementation provides all external input keys plus `content`, `previous_output`, and `node_outputs_json`. `previous_output` is valid only for one dependency; `node_outputs_json` preserves source-node names for fan-in prompts. Prompt-template validation fails before model acquire when a referenced field is unavailable.

Session completion is based on the static workflow DAG. The terminal node is computed as the only node with no successor. A session is complete when that terminal node has produced and persisted its result for the `session_id`.

Workflow parsing validates a non-empty directed acyclic graph before creating queues or actors. It rejects cycles, self-edges, duplicate edges, unknown edge endpoints, and graphs without exactly one zero-indegree entry node and one zero-outdegree terminal node. The validated topological order, adjacency, dependencies, entry node, and terminal node are computed once and shared with the controller and scheduler.

Static fan-in remains source-based: for one target node and one session, each configured upstream source node contributes one item. A repeated item from the same `source_node` to the same `target_node` in the same `session_id` is a program error. This plan does not implement dynamic fan-in where one source emits multiple items to the same target within one session.

## Queues, Fan-Out, Fan-In, And Backpressure

Each executable node owns one bounded input queue. All upstream nodes that feed the same target put items into that target node input queue. `output_queues_map[source][target]` is only a controller-side wiring map: it points a source node to the target node input queue and must not create a second physical queue for the same edge.

Agent nodes and broadcast function nodes send the returned `AgentState` to every static successor. Targeted function nodes use the callable result keyed by target node, allowing different static successors to receive different states. For every successor, the worker creates a new `WorkflowDataItem` with the same `session_id` and `session_input_ref`, a new runtime-generated `item_id`, `source_node` set to the current node, and `target_node` set to that successor. The terminal node has no successor queue and sends its returned `AgentState` to `ResultStoreActor` unchanged.

Fan-in is implemented inside the target worker. The worker stores arrived upstream messages by `session_id` and `source_node`:

```python
store[session_id][source_node] = message
```

When all static dependencies of that target have arrived for the same `session_id`, the worker constructs source-indexed inputs in dependency order, runs the agent or function node once, and clears that session fan-in store.

Queue capacity is node-level, not edge-level. A node `queue_capacity` config controls the capacity of its input queue shared by all upstream sources. When a downstream input queue is full, upstream `put()` blocks and backpressure propagates naturally through the worker chain.

This plan does not implement per-edge queues or multi-queue select/fairness logic.

## Node Execution Concurrency

Each `NodeWorker` is an async Ray actor and executes at most one in-flight session task. Its long-running `run()` uses `input_queue.get_async()`, successor emission uses `put_async()`, and model-replica calls are awaited. These await points keep actor control methods responsive without threaded mutation of worker-local state. The worker does not dequeue another executable item until the current function call or model-replica request has completed and its result has been emitted. Queue buffering and backpressure remain the mechanism for overlapping different workflow nodes and different pipeline stages.

Data queues carry only workflow data. Stop, session cancellation, and lifecycle control use actor methods or scheduler commands and are never encoded as queue items. The controller retains each worker `run()` reference so an unexpected loop exit or exception is observable.

The current runtime does not batch sessions inside one node. Model-backed prediction lookup therefore uses `batch_size=1`, even though the offline prediction cache retains a batch-size dimension. A busy or loading replica causes requests assigned to the same model and GPU kind to wait. Queue pressure alone does not create another same-kind replica; a cross-kind replica is created only when placement or token-budget policy selects that other GPU kind.

Node-level multiple in-flight requests, runtime batch formation, and continuous batching are one next-stage feature implemented together with the vLLM backend. The current Hugging Face pipeline path must not emulate batching by deploying additional model replicas.

## Stop And Drain Semantics

The runtime must support both immediate shutdown and drain shutdown.

`stop_now()` is for development, cleanup, and unrecoverable run-level failures. It closes admission, asks the scheduler to cancel pending work, calls worker control methods so they stop dequeuing new items, cancels worker run tasks, and forcefully terminates worker or replica actors that remain active. It then shuts down the Ray Queue actors. Sessions that have not reached terminal results may remain incomplete. This path prioritizes bounded cleanup time over completing current inference.

`drain_and_stop(timeout_sec: float | None = None)` is for experiments and normal benchmark runs. It closes admission but continues processing already accepted sessions until each has either its terminal result or a failure record. It then waits for result persistence, all trace-batch acknowledgements, `run_finished`, and the final trace flush. Only after persistence succeeds does the controller stop idle workers, evict model replicas, and shut down queue actors. If `timeout_sec` expires, the method fails explicitly instead of silently dropping work; callers may then invoke `stop_now()` to force cleanup.

Neither shutdown path puts STOP items into bounded data queues or propagates control messages through DAG edges.

The controller tracks accepted `session_id` values for admission and input-reference ownership, and registers each accepted session with the scheduler before initial enqueue. The scheduler is the authoritative source for drain completion: every registered session must reach `COMPLETED` or `FAILED`. Empty queues alone are not sufficient because a worker may still be executing or a fan-in store may hold partial inputs.

## Failure Scope

Failures are classified by ownership rather than handled by one global skip or crash rule.

Configuration errors, invalid DAG state, scheduler-state invariant violations, missing required prediction artifacts, scheduler actor failure, and required trace-output failure are run-level failures. They make the experiment runtime unreliable, so the controller stops accepting submissions and fails the whole run.

A node execution failure after its configured retries are exhausted is a session-level failure. The scheduler marks that session `FAILED`, prevents it from producing further downstream work, and records the node failure, while the runtime and unrelated sessions continue. One session failure must not crash the scheduler or stop the whole experiment.

The runtime does not support silently skipping a failed item or completing a session from only a subset of its workflow nodes. A workflow node is a required dependency unless the static workflow itself models an alternative path. Retry exhaustion therefore fails the session; `skip_item` is not a supported exhausted-retry policy in the new runtime.

The first definitive node failure changes the session to `FAILED` idempotently. The scheduler cancels pending acquires and changes not-yet-running node tasks for that session to `CANCELLED`. It rejects later begin or acquire commands for the failed session and asynchronously notifies workers so they can purge partial fan-in state and discard queued items for that session. Correctness does not depend on removing an item from the middle of a Ray Queue; a cancelled item may be discarded when dequeued.

A node task that is already executing is not forcibly interrupted. Its model or function call may finish, after which the worker reports the observation and releases any model-replica lease normally. The scheduler then changes that task to `CANCELLED` and tells the worker not to persist or emit its output. A late successful execution cannot restore a failed session or satisfy downstream dependencies.

This soft-cancellation rule avoids killing a healthy shared model replica because one session failed. The replica still follows its own execution outcome: a normal completion returns it to `IDLE`, while an OOM or severe CUDA failure marks it `SUSPECT`.

## Runtime Component Roles

The managed runtime uses `SchedulerActor`, `NodeWorker`, `ModelReplica`, `ResultStoreActor`, and `TraceWriterActor` plus the controller lifecycle wrapper and scheduler-owned accelerator and model-replica records.

`WorkflowController` is the user-facing lifecycle wrapper. It parses workflow config, builds queues and worker actors, creates the scheduler, result-store, and trace-writer actors, accepts external `submit(session_id, inputs)` calls and owns session-input object references, rejects duplicate sessions, exposes status/result APIs backed by `ResultStoreActor`, and owns `stop_now()` / `drain_and_stop()`. It does not decide model placement, prefetch, eviction, token budget, or prediction policy.

`SchedulerActor` is the core control plane in managed mode. It holds a read-only copy of the static DAG (`adjacency`, `dependencies`, `topological_order`, `entry_node`, `terminal_node`) and mutable session/runtime state. The scheduler uses this state to estimate ready and near-ready tasks, model demand, upstream ETA, terminal completion, and future resource pressure. It owns model-replica lifecycle, accelerator assignment, prediction sources, placement, prefetch, eviction, token-budget decisions, trace-event enrichment, and asynchronous trace-batch submission.

`NodeWorker` is the async data-plane executor shared by agent and function nodes. It awaits its bounded input queue, resolves static fan-in, resolves immutable session inputs, and executes the configured node kind. For an agent node it renders the prompt, requests a grant, and invokes the granted model replica. For a function node it invokes the registered callable without scheduler resource acquisition. It validates broadcast or targeted routing, performs fan-out or terminal-result submission, applies the node retry policy, and reports completion or failure. The worker does not interpret business fields inside `AgentState` and does not inspect global queue state, accelerator state, or eviction policy.

`ModelReplica` is the scheduler-visible inference and lifecycle unit. In the current implementation one Ray actor loads one model on one Ray-assigned GPU with `num_gpus=1`; multiple agent nodes may share that replica. Eviction destroys the replica actor so Ray releases the GPU and the CUDA process. The runtime does not create a permanent actor per physical GPU.

`ResultStoreActor` is the single owner of terminal session results and the single writer of `session_results.jsonl`. It stores the terminal `AgentState` without extracting code, summaries, answers, or message fields; evaluator and benchmark code own that parsing. A terminal result is accepted once per `session_id`, and successful persistence must be acknowledged before the worker calls `finish_node()`.

Terminal-state serialization uses `langchain_core.load.dumpd(state)` followed by ordinary `json.dumps(...)`. The implementation keeps this boundary narrow: assert that LangChain did not emit an unsupported `not_implemented` marker, then let JSON serialization or file I/O fail naturally. Do not add `default=str`, pickle fallback, broad exception recovery, or workload-specific field conversion. A state-serialization failure fails that session; result-file write or flush failure fails the run.

`TraceWriterActor` is the single writer of `workflow_trace.jsonl`. It accepts scheduler-produced event batches, appends and flushes them in order, and returns an acknowledgement. It does not derive scheduling decisions or receive unstructured worker payloads.

`AcceleratorRecord` is ordinary scheduler state built from `AcceleratorConfig`. It identifies a physical resource and records the replica currently assigned to it, if any. The current implementation enforces one model replica per GPU. The record is not an actor and does not run inference.

The scheduler keeps DAG structure because prediction-aware prefetch requires future dependency knowledge. For example, if `reducer` depends on `chunk_a`, `chunk_b`, and `chunk_c`, and two chunks are running with predicted finish times, only a DAG-aware scheduler can estimate when `reducer` will become ready and whether loading its model now can overlap upstream work.

The scheduler is the unique source of truth for per-session node-task lifecycle and session completion. The controller owns request admission and immutable input references. A node worker owns only local queue and fan-in state. The result store owns terminal payloads and result-file persistence. The trace writer owns trace-file I/O. A model replica owns only model execution state.

The state types describe different objects and must not be merged:

```text
NodeTaskState    -> one (session_id, node_id) execution
NodeWorkerState  -> one long-lived node worker
ModelReplicaState -> one resident model deployment
```

After successful output emission, the session-specific node task becomes `COMPLETED`, while its long-lived node worker returns to `IDLE`. A completed task record remains terminal so dependency and session-completion checks do not lose history.

## Managed Execution Protocol

`NodeWorker` owns one common execution lifecycle and dispatches node-specific work to ordinary `execute_agent(...)` and `execute_function(...)` functions selected from the discriminated node config. The current implementation does not introduce a stateful node base-class hierarchy.

After static fan-in is ready, every node calls `begin_node(session_id, node_id, input_item_ids)`. The scheduler validates that the session is still active, creates or claims the session-specific node task, and returns its `task_id`. A failed session rejects the begin command so the worker discards the item without invoking the node.

A function node enters `RUNNING` and invokes its registered callable directly. An agent node enters `ACQUIRING`, renders and validates its prompt, and calls `request_acquire(task_id, ...)`. A grant changes the agent task to `RUNNING`; resource, placement, token-budget, and model-lifecycle policy remain scheduler-owned.

Both node kinds report the end of actual execution through one interface:

```python
decision = scheduler.complete(
    task_id=task_id,
    runtime_report=runtime_report,
    acquire_id=acquire_id,  # Required for agent, None for function.
)
```

`complete()` records execution status, duration, and node-kind-specific metadata. For an agent task it also closes the granted acquire and removes its running-task record. On normal agent completion the replica changes from `BUSY` to `IDLE`; on OOM or severe CUDA failure it changes to `SUSPECT`.

If execution succeeds while the session remains active, `complete()` changes the node task from `RUNNING` to `EMITTING` and returns `emit_output=True`. If the session has already failed, it changes the late task to `CANCELLED`, returns `emit_output=False`, and still releases any model lease. Execution failure changes the task and session to `FAILED`; it never satisfies downstream dependencies.

`complete()` does not unload model weights, release replica accelerators, enqueue outputs, persist the terminal result, satisfy downstream dependencies, or mark a successful node task `COMPLETED`. Unknown, duplicate, or node-kind-incompatible `task_id` and `acquire_id` combinations are program errors.

When `emit_output=True`, the worker emits every required successor item or submits the single terminal `AgentState` to `ResultStoreActor`. Successor queue writes may block because of backpressure. Terminal submission awaits the result store's persistence acknowledgement. After all required output operations succeed, the worker calls `finish_node(task_id, output_report)`.

`finish_node()` validates the task, changes `NodeTaskState` from `EMITTING` to `COMPLETED`, records output metadata, updates completed dependencies used by near-ready prediction, and marks the session `COMPLETED` when its single terminal node finishes. It does not change replica or accelerator state. Output emission or terminal-result persistence failure calls `fail_node(...)` and fails the session.

The principal task transitions are:

```text
agent:    PENDING -> ACQUIRING -> RUNNING -> EMITTING -> COMPLETED
function: PENDING -------------> RUNNING -> EMITTING -> COMPLETED
failure:  non-terminal state -> FAILED or CANCELLED
```

The successful agent-node sequence is:

```text
begin_node -> request_acquire -> grant -> replica inference
-> complete               # ModelReplica BUSY -> IDLE; NodeTask RUNNING -> EMITTING
-> enqueue or persist
-> finish_node            # NodeTask EMITTING -> COMPLETED; NodeWorker -> IDLE
```

The successful function-node sequence is:

```text
begin_node -> execute_function
-> complete               # No model lease; NodeTask RUNNING -> EMITTING
-> enqueue or persist
-> finish_node            # NodeTask EMITTING -> COMPLETED; NodeWorker -> IDLE
```

Model unloading is a separate asynchronous lifecycle decision:

```python
scheduler.evict(replica_id)
```

Only eviction destroys the replica backend and releases its assigned accelerators. It is not a required part of inference completion.

## Model Replica Scope

The scheduler stores each deployment as a `ModelReplicaRecord` with `replica_id`, `model_key`, `accelerator_ids: tuple[str, ...]`, lifecycle state, and a backend handle. Current configuration and validation require exactly one accelerator id per replica. The tuple-shaped ownership contract prevents scheduler APIs from assuming that a deployable replica must always be single-GPU.

Multiple agent nodes can share the same replica when their weight-loading configuration is compatible. Sharing means reusing one resident model deployment; it does not imply request batching. The current implementation permits at most one live or loading replica for each `(model_key, gpu_kind)` pair. The same model may therefore have one V100 replica and one A100 replica resident and executing concurrently, but it cannot have two V100 replicas or two A100 replicas. Requests assigned to a busy or loading pair wait.

Continuous batching and multi-GPU model execution are not part of the current implementation. A future vLLM backend may implement one replica with an engine core and multiple internal GPU workers using tensor or pipeline parallelism. The workflow scheduler continues to grant and evict the replica as one unit and does not implement distributed model execution itself.

## Model Pool And Accelerator Identity

`ModelPool` uses the current sharing key:

```text
model_name + model_path + dtype
```

Agent nodes with the same sharing key may reuse an idle `ModelReplica` on the GPU kind selected for the task. Request-level settings such as `prompt_template`, `system_prompt`, `max_new_tokens`, `temperature`, `do_sample`, and `enable_thinking` do not affect weight compatibility. `gpu_kind` is not part of `model_key`; it is part of deployment identity and the uniqueness index `(model_key, gpu_kind)`.

A current-stage replica is bound to one accelerator. Runtime code must not treat `cuda:N` as a globally unique resource id. Accelerator identity is represented by `AcceleratorConfig`:

```python
class AcceleratorConfig(BaseModel):
    hostname: NonEmptyStr
    gpu_kind: Literal["v100", "a100"]
    local_index: NonNegativeInt
    total_mem_mb: PositiveInt

    @property
    def accelerator_id(self) -> str:
        return f"{self.hostname}/{self.gpu_kind}:{self.local_index}"
```

Examples:

```text
gpu-node-0/v100:0
gpu-node-0/v100:1
gpu-node-1/a100:0
```

The controller resolves configured hostnames to live Ray nodes and validates each node GPU count before scheduling starts. The scheduler chooses a hostname and GPU kind, reserves a free accelerator record, and creates a replica actor with hard node affinity and `num_gpus=1`. The replica reports its Ray-assigned physical GPU id after startup; that id is bound to the corresponding configured record before the load is accepted. Actor creation order does not define GPU identity.

Inside the current single-GPU replica actor, CUDA execution uses the Ray-isolated process-local device `cuda:0`; host-level `cuda:N` strings are never passed through node execution config. Prediction-cache and deployment-profile lookup use `gpu_kind`, because hardware class rather than a concrete device determines the offline profile key.

## Model Replica States And Eviction Policy

Model replicas use these states:

```text
LOADING
IDLE
BUSY
EVICTING
SUSPECT
```

`LOADING` means the replica backend is starting and loading weights. `IDLE` means the replica is resident and can be granted. `BUSY` means one task is executing. `EVICTING` means the backend is being destroyed. `SUSPECT` means OOM or a severe CUDA failure occurred; the replica must not be reused and should be evicted.

Valid transitions are:

```text
LOADING -> IDLE
IDLE -> BUSY
BUSY -> IDLE
BUSY -> SUSPECT
IDLE -> EVICTING
SUSPECT -> EVICTING
EVICTING -> removed
```

Only `IDLE` and `SUSPECT` replicas are legal victims of normal scheduling eviction. `BUSY` and `LOADING` replicas must not be evicted by placement, prefetch, or reuse policy. Forced run-level `stop_now()` cleanup may terminate replicas in any state. Accelerator ownership sets of live replicas must never overlap.

The default eviction policy is `future_reuse_distance`. For each legal victim, the scheduler estimates the earliest future demand for that replica's `(model_key, gpu_kind)` pair from pending acquires, running upstream task ETA, static DAG dependencies, active session state, and token-budget placement. The victim score is:

```text
reuse_distance_sec - reload_cost_sec
```

The scheduler evicts the legal victim with the largest score. A `(model_key, gpu_kind)` pair with no future demand in active sessions has infinite reuse distance and is preferred for eviction. Missing reload cost falls back to profiled or static default load time. Missing future ready time is treated as unknown.

If no legal victim has a computable score, the policy falls back to `longest_idle`. The fallback still cannot evict `BUSY` or normal `LOADING` replicas.

## Accelerator Resource Accounting

Accelerator resources are static and config-owned. The scheduler does not discover GPUs at runtime and does not continuously poll NVML or `nvidia-smi` for scheduling decisions.

Each configured accelerator has one scheduler-owned `AcceleratorRecord` and may be assigned to at most one replica. Current-stage placement uses a single-model peak check:

```text
required_peak_mb = predicted_vram_mb + eps_mem_mb + oom_penalty_mb
fits = required_peak_mb <= total_mem_mb
```

A load or prefetch can use an unassigned accelerator only when the predicted peak fits. An accelerator assigned to the same idle model replica is a reuse candidate. An accelerator assigned to a different model becomes available only after the scheduler selects and completes a legal replica eviction. Idle VRAM from the deployment profile may be recorded for analysis but is not used to pack multiple models onto one GPU.

Startup validation is fail-fast. The runtime must reject configs where a hostname is not visible in the Ray cluster, accelerator ids are duplicated, local indexes conflict on the same host, configured GPU counts disagree with live Ray node resources, `gpu_kind` is unsupported, `total_mem_mb` is invalid, or a replica cannot be started on its selected host.

Runtime OOM remains a real execution failure path. OOM marks the model replica `SUSPECT` and triggers scheduler cleanup, but normal scheduling does not depend on continuous GPU probing.

## Offline Prediction And Profile Artifacts

The scheduler reads final prediction artifacts. It does not load PyG `Data`, target scalers, feature scalers, ONNX files, or a GNN checkpoint during normal workflow execution.

Offline scripts own the heavy prediction pipeline:

```text
cache.yaml -> ONNX cache -> PyG graph-feature cache -> GNN checkpoint -> prediction cache
```

The runtime consumes only:

```text
prediction cache + deployment profile manifest
```

Prediction cache entries keep prompt and generation dimensions separate:

```text
model_name + gpu_kind + batch_size + sequence_length + decode_output_length
```

`sequence_length` represents the prompt/input bucket after the agent prompt template is applied. `decode_output_length` represents the candidate generation budget bucket. Runtime scheduling may derive `total_context_tokens = sequence_length + decode_output_length`, but the persisted prediction key must not collapse the two dimensions into one total-token key because prefill and generation have different latency behavior and the existing GNN features already model them separately.

The prediction cache stores final scheduler-facing values such as predicted run duration, predicted peak VRAM, predicted power, predictor metadata, and cache version. Missing prediction entries are fail-fast in the current implementation. The runtime must not export ONNX, build PyG data, run the GNN, or update prediction cache online.

Model deployment time and idle model memory come from an offline profile artifact such as `example/workflow/profile.yaml`. A standalone script profiles loading models from the shared model directory used by deployment. Profile entries are keyed by:

```text
model_name + model_path + dtype + gpu_kind
```

The deployment profile is scoped by GPU kind rather than hostname because worker nodes are expected to have similar performance and read from the same shared model directory. `hostname` remains part of `AcceleratorConfig` for actor placement, but not part of deployment profile lookup.

Deployment cost priority is:

```text
profile load_sec_p95 -> profile load_sec_median -> static default
```

The current prediction cache should reuse the existing bucket grid from `config/workflow/cache.yaml` and the existing key semantics from `WorkflowModelFeatureKey`. Do not introduce a parallel graph-feature registry.

The current cache uses `phase=decode`. This follows the existing data generation convention where `run_decode()` calls `model.generate(max_new_tokens=...)`, so decode records act as a full-generation proxy. Runtime prediction must document this convention and must not claim strict single-token decode prediction.

## Scheduler Request And Grant State Machine

`SchedulerActor` is an async Ray actor. Its long-running `run()` coroutine is the only code path that mutates scheduling state. Public actor methods and model-lifecycle watchers submit typed commands to an actor-local `asyncio.Queue`; they do not modify the model pool, accelerator ledger, session state, or task state independently.

The command queue is an in-process control mailbox, not a Ray Queue and not a data-plane queue. Pending resource requests remain ordinary scheduler-owned Python structures:

```python
command_queue: asyncio.Queue[SchedulerCommand]
pending_acquires: dict[str, PendingAcquire]
pending_order: deque[str]
grants: dict[str, GrantInfo]
running_tasks: dict[tuple[str, str], RunningTask]
```

The controller starts `scheduler.run.remote()` once and retains its `ObjectRef` so loop failure is observable. The loop waits for either an incoming command or the next scheduling deadline, drains commands already available, applies them in arrival order, runs one short scheduling decision pass, emits non-blocking actions, and waits again.

Normal scheduling is event-driven. Commands include session registration, acquire request, acquire cancellation, model-execution completion, node completion or failure, model-load completion or failure, eviction completion or failure, and shutdown. Multiple commands that arrive together may be applied before one decision pass so a burst of worker reports does not cause repeated full DAG scans.

Time-dependent scheduling uses explicit deadlines. For a near-ready task, the scheduler derives:

```text
prefetch_at = upstream_eta - model_load_sec - eps_time_sec
```

The loop wakes at the nearest `prefetch_at`, acquire timeout, eviction timeout, or shutdown deadline even when no external event arrives. A configurable `max_tick_interval_sec` defaults to `0.5` seconds and acts only as a fallback wake-up. Events and exact deadlines may wake the loop earlier; the fallback is not the normal prefetch timing mechanism and does not perform live GPU observation.

`tick_once()` is the short synchronous decision pass called only by `run()`. It must not await model inference or loading, call blocking `ray.get()` or `ray.wait()`, block on Ray Queue operations, sleep, or perform file I/O. It reads current scheduler state, computes grants and lifecycle actions, updates reservations before emitting those actions, and returns control to the actor event loop after a bounded amount of work.

Model loading and eviction remain asynchronous. Their `ObjectRef` watchers await completion outside `tick_once()` and submit a typed completion command back to `command_queue`; watchers do not mutate replica or accelerator records directly. This makes `LOADING -> IDLE`, load failure, and eviction completion immediate event-driven transitions rather than transitions that depend on an unrelated worker request.

The scheduler must not implement a blocking `acquire()` method inside the actor. A long-running acquire would prevent the worker from observing timeout and cancellation independently. The worker-facing protocol remains non-blocking request plus polling:

```python
task_id = scheduler.begin_node(...)
acquire_id = scheduler.request_acquire(task_id, ...)
grant = wait_for_grant(scheduler, acquire_id, timeout_sec)
scheduler.complete(task_id, ..., acquire_id=acquire_id)
```

`request_acquire(task_id, ...)` validates an active agent task, submits a command that creates a `PendingAcquire`, appends its id to `pending_order`, wakes `run()`, and returns `acquire_id` after the command has been accepted into scheduler state.

`poll_grant(acquire_id)` returns `GrantInfo | None`. `GrantInfo` identifies `replica_id`, its backend handle, and `accelerator_ids`. When a grant is returned, the scheduler has already reserved the replica and marked it `BUSY` for that acquire.

`cancel_acquire(acquire_id)` submits a cancellation command when worker-side waiting times out. When `run()` applies it, a still-pending request is removed. If the acquire was already granted, cancellation fails explicitly so the worker cannot silently leak a busy replica.

`complete(task_id, runtime_report, acquire_id=None)` submits agent or function execution completion and wakes `run()`. Applying that command updates node-task state and runtime history and closes a model lease when `acquire_id` is present. Downstream dependency and session progress change only when the worker later calls `finish_node(...)` after successful output emission or terminal-result persistence.

The worker should use a helper that polls `poll_grant` with a short sleep interval and calls `cancel_acquire` on timeout. This keeps polling logic out of node execution code.

## Prediction-Aware Scheduling Algorithm

The implementation maps the paper algorithm in `docs/draft/workflow.tex` to the runtime state machine as follows:

```text
C_ready  -> PendingAcquire created by a worker after fan-in and prompt construction
C_near   -> NearReadyTask estimated by the scheduler from DAG state and running task ETA
Dispatch -> GrantInfo stored by scheduler and returned through poll_grant
LoadOrPrefetch -> non-blocking ModelReplica backend creation
```

`run()` advances scheduling after applying commands or reaching a deadline by calling `tick_once()`. The decision pass must remain short-running and must not block on model loading or inference.

Commands, including completed or failed model-lifecycle events from asynchronous watchers, are applied before `tick_once()`. The decision pass then runs in this order:

1. Process `SUSPECT` replicas and pending eviction cleanup.
2. Collect ready tasks from `pending_acquires`.
3. Collect near-ready tasks from static DAG dependencies, completed nodes, and running task ETA.
4. Grant ready tasks that can reuse an idle compatible replica.
5. Start loads for ready tasks that have no reusable idle replica.
6. Start prefetch loads for near-ready tasks only when the deploy window is useful.

Ready work has priority over near-ready work:

```text
ready grant > ready load > near-ready prefetch
```

Ready task ordering is `topological_order(node)` followed by acquire creation time FIFO inside the same node. Near-ready task ordering is estimated ready time followed by topological order.

If the selected `(model_key, gpu_kind)` replica is `LOADING` or `BUSY`, requests assigned to that pair remain queued. The scheduler never starts a second replica for the same pair. It may use or load the same model on another GPU kind only when placement or token-budget policy independently selects that kind, not merely because the first replica is busy.

Near-ready prefetch may trigger eviction, but only through the normal legal-victim rules and default `future_reuse_distance` policy. Prefetch must not evict resources needed by already ready tasks.

A tick may grant multiple ready tasks across different idle replicas. At most one load or prefetch may exist for each `(model_key, gpu_kind)` pair. Eviction is limited to at most one victim per accelerator per tick; after eviction, the next tick recomputes placement from fresh scheduler state.

## Task Runtime Reports And Scheduler History

Workers report runtime observations through `scheduler.complete(...)`. Do not add a second metrics queue for the current implementation. Reports are discriminated by node kind: function reports contain callable duration and input/output size metadata, while agent reports additionally contain model, accelerator, token, and acquire fields.

The agent completion report contains the fields scheduler decisions need:

```python
class AgentTaskRuntimeReport(BaseModel):
    acquire_id: str
    task_id: str
    session_id: str
    node_id: str
    input_item_ids: list[str]
    model_key: str
    accelerator_id: str
    gpu_kind: str
    input_tokens: int
    granted_max_new_tokens: int
    output_tokens: int
    hit_token_limit: bool
    started_at: float
    finished_at: float
    duration_sec: float
    status: Literal["success", "failed", "oom"]
    error_type: str | None = None
```

`hit_token_limit` is `True` when `output_tokens >= granted_max_new_tokens`. If a later backend exposes an explicit stop reason, the runtime should use that reason instead of the length heuristic.

The scheduler keeps lightweight rolling history keyed by `node_id + model_key + gpu_kind`. The required first-stage aggregates are:

```text
output_tokens_p90
hit_limit_rate
duration_sec_ema
oom_count
```

This history is scheduler state, not a prediction-cache update. It is used for placement preference, near-ready input-token estimates, and OOM penalty in the current run. Experiment trace output may persist the raw reports, but scheduler decisions must not mutate the offline prediction cache.

## Token Budget And OOM Behavior

Token budget is a deterministic feasibility search over prediction cache buckets. It is not an online GNN call and not a free-form generation policy.

Each agent node declares a token budget range:

```yaml
token_budget:
  min_max_new_tokens: 128
  default_max_new_tokens: 512
  max_max_new_tokens: 1024
```

For a ready task, the worker computes exact `input_tokens` from the final prompt before `request_acquire`. For a near-ready task, the scheduler estimates input length from upstream output-token history and prompt-template overhead. The scheduler maps input length to the smallest cached `sequence_length` bucket that is greater than or equal to the estimated input length.

Input tokens and output tokens share the same KV-cache capacity pressure after generation starts, but they are not equally controllable. Input tokens are fixed by the request. Output token budget is the scheduler-controlled variable. For each candidate accelerator, the scheduler searches cached `decode_output_length` buckets within `[min_max_new_tokens, max_max_new_tokens]` and chooses the largest feasible output budget satisfying:

```text
total_context_tokens = sequence_length_bucket + decode_output_length_bucket
predicted_vram_mb + eps_mem_mb + oom_penalty_mb <= accelerator.total_mem_mb
```

If the feasible budget is larger than `default_max_new_tokens`, the task is upscaled on that accelerator. If it is smaller than `default_max_new_tokens` but still at least `min_max_new_tokens`, the task is downscaled. If no accelerator can satisfy `min_max_new_tokens`, the task fails explicitly with `token_budget_infeasible`.

Placement should not always prefer the accelerator with the largest possible output budget. If a V100 can grant `default_max_new_tokens` and history for this node has low `hit_limit_rate`, the scheduler should prefer the cheaper/smaller accelerator. If V100 placement repeatedly hits the granted token limit or can only downscale below the default while A100 can grant a larger budget, A100 placement has real quality headroom and should be preferred. GPU-kind selection happens before replica reuse, so an idle V100 replica does not override an A100 decision. The V100 replica may remain resident for later V100-suitable work and is evicted independently by `future_reuse_distance`.

`GrantInfo` must carry the final `granted_max_new_tokens`, the configured budget range, the selected prediction bucket, and a token budget action:

```text
fixed
upscaled
downscaled
infeasible
```

The worker and the granted `ModelReplica` backend call must use `granted_max_new_tokens`, not the node default. If `input_tokens` exceeds the largest available `sequence_length` bucket, or if the selected bucket is missing from the prediction cache, the scheduler fails fast instead of clamping silently.

OOM during execution remains a real failure path. The replica becomes `SUSPECT`, the scheduler records the failure, and normal cleanup/eviction logic applies. The scheduler may keep an in-memory `oom_penalty_mb` for the affected `model_key + gpu_kind + sequence_length + decode_output_length` bucket in the current run:

```text
effective_vram_mb = predicted_vram_mb + eps_mem_mb + oom_penalty_mb
```

The runtime must not write this penalty back to the offline prediction cache. A task that OOMs after a granted prediction may retry acquire once with the updated penalty; if it OOMs again, the session records a failure for that node.

## Trace Schema And Experiment Outputs

Trace records are runtime facts, not evaluator results. The runtime should collect detailed execution facts because this is a research system and later experiment analysis may need metrics that were not known before the run. The trace must avoid storing large text blobs, large objects, or full intermediate `AgentState` values by default.

Agent and function nodes use the same queue and task lifecycle events. Task events identify the node kind; function-node events record callable duration and input/output size metadata while model, accelerator, and token-budget fields remain absent. End-to-end session latency starts at controller API entry before `ray.put()` and initial enqueue, so preprocessing and runtime transport overhead remain measurable. A LangGraph baseline can register the same callable as a normal graph node and use the same timing boundary.

Workers do not write trace files and do not own a separate trace Ray Queue. They attach locally observed event records and timestamps to existing scheduler commands such as `begin_node()`, `complete()`, `finish_node()`, and failure reports. Model execution observations also reach trace through the existing completion report. The scheduler enriches these records with authoritative session, task, acquire, replica, and accelerator identities and assigns a monotonically increasing run-local `event_seq`.

At the end of each command batch or scheduling pass, the scheduler submits accumulated trace events through non-blocking `TraceWriterActor.append_batch.remote(...)`. It retains the returned `ObjectRef`; an asynchronous watcher sends trace-write success or failure back through the scheduler command queue. Trace writing therefore never blocks `tick_once()`, and a write failure remains observable by the scheduler.

Drain completion includes trace completion. After all accepted sessions are terminal, the scheduler waits until every submitted trace batch is acknowledged, records `run_finished`, and requires the trace writer's final flush to succeed before shutdown completes. Trace-write or flush failure is a run-level failure. `ResultStoreActor` remains separate so high-volume trace appends cannot delay terminal-result persistence.

Trace timestamps and durations have separate meanings. An event producer records `TraceEvent.ts = time.time()` when the event occurs so events from different actors can be placed on an approximate shared wall-clock timeline. The scheduler-assigned `event_seq` records ingestion and JSONL order only; it does not claim that events occurred in that order.

Precise durations are computed by the actor that performs the operation using two local `time.perf_counter()` readings and are reported directly as `duration_sec`. ModelReplica measures model load and inference duration, and NodeWorker measures function and node-local processing duration. Analysis must not subtract `perf_counter()` values from different processes or reconstruct precise duration from cross-host wall-clock events.

End-to-end session latency is measured in the controller process from API entry before `ray.put()` through terminal-result persistence acknowledgement, using the controller's local `perf_counter()`. Queue-wait and other metrics whose endpoints necessarily occur on different hosts may use wall-clock timestamps as an approximation and inherit the experiment platform's clock-synchronization accuracy. The runtime assumes ordinary cluster clock synchronization and does not implement NTP/PTP checks, offset estimation, or online clock correction.

Each workflow run writes to an experiment-provided output directory:

```text
<output_dir>/
  workflow_trace.jsonl
  session_results.jsonl
  run_summary.json
```

`output_dir` is passed by the experiment script or controller construction. It must not be embedded in workflow YAML. Every trace event carries `run_id`, so filenames do not need timestamps. Do not add default rotation or gzip compression in the current implementation because plain JSONL is easier to inspect during experiments.

`workflow_trace.jsonl` is the authoritative event log and is written only by `TraceWriterActor`. It is append-only and contains one JSON object per runtime event in scheduler-assigned `event_seq` order. The first-stage event set is:

```text
run_started
run_finished
session_submitted
session_completed
session_failed
item_enqueued
item_dequeued
fanin_wait
fanin_ready
item_emitted
acquire_requested
acquire_granted
acquire_cancelled
model_load_started
model_load_finished
model_load_failed
model_reused
model_evicted
model_suspect
task_started
task_completed
task_failed
task_retried
token_budget_selected
token_budget_infeasible
prefetch_started
prefetch_skipped
prefetch_finished
scheduler_tick

```

All trace events share a common envelope:

```python
class TraceEvent(BaseModel):
    run_id: str
    event_id: str
    event_seq: NonNegativeInt
    event_type: str
    ts: float
    session_id: str | None = None
    item_id: str | None = None
    task_id: str | None = None
    node_id: str | None = None
    source_node: str | None = None
    target_node: str | None = None
    model_key: str | None = None
    replica_id: str | None = None
    accelerator_id: str | None = None
    gpu_kind: str | None = None
    acquire_id: str | None = None
    payload: dict[str, object] = Field(default_factory=dict)
```

Long text payloads are represented by metadata instead of full content:

```text
text_sha256
text_char_len
input_tokens
output_tokens
preview_head_chars
```

`preview_head_chars` is optional and should be disabled or very small by default. Complete intermediate node outputs and complete intermediate `AgentState` objects are not written to trace by default.

`session_results.jsonl` is written only by `ResultStoreActor` and stores the single terminal-node `AgentState` for each completed session. Each row contains `run_id`, `session_id`, terminal `node_id`, `serialization_format=langchain_dump`, the installed LangChain Core version, and the complete serialized terminal state needed by benchmark or evaluator scripts. The runtime does not impose a code, summary, answer, or message-extraction schema. Evaluation functions read this file and dataset references outside the runtime and own workload-specific parsing.

`run_summary.json` is a convenience artifact generated after drain finishes. It is derived from trace and terminal results, not a replacement for `workflow_trace.jsonl`. It should include run-level counts and timing summaries such as submitted/completed/failed sessions, per-node task counts, token budget action counts, OOM counts, model load/reuse/evict counts, and active/resident GPU-second summaries.

Trace writing is required by default. If an asynchronous append acknowledgement or final flush fails, the scheduler marks the workflow run failed because an untraceable experiment is not useful for this project. A future config may allow `trace_required: false`, but the default implementation treats trace failure as a run-level failure and performs normal session and model-resource cleanup.
