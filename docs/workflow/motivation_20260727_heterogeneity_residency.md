# 动机实验：GPU 上驻留哪些模型，是不是一个真问题（2026-07-27）

## 0. 这个实验在问什么

读了三篇多 Agent / LLM workflow 服务的论文——Parrot（OSDI'24）、Ayo、Kairos（arXiv 2508.06948）——
它们能决定的事情都是两件：**下一个执行哪个请求**，以及**把请求送到哪个已有实例**。
**没有一篇把"随着时间推移，哪些模型占用着 GPU"当成可以决定的事情。**
Kairos 甚至把这写成了明确的前提：所有 agent 共用同一个大模型，实例事先静态部署在同构 GPU（4 张 A40）上。

但真实的多 Agent 应用普遍让不同角色用不同规模的模型（小模型出草稿、大模型精修）。
这时同一时刻被需要的模型不止一个，"哪些模型驻留在 GPU 上"就成了一个必须做的决定。于是问：

> 当各个角色用不同模型时，"少了模型生命周期管理"这件事，
> 在总完成时间和模型驻留时间上到底浪费了多少？还是说其实无所谓？

**四个问题，每一个的答案都可能是"无所谓"，从而否掉这条研究线**：

1. 同一时刻真正被需要的模型数，会超过 GPU 卡数吗？如果通常只有一两个，那前提就是对的。
2. 如果超过，模型加载占掉多少时间？如果只占百分之几，不值得做。
3. 这份开销能靠"换一种请求排序"消掉吗？如果能，那它属于上面三篇论文已经解决的范围。
4. 有没有可以利用的余量？也就是"下一个要用哪个模型"能否提前知道、以及那时有没有空闲的卡？

## 1. 怎么设计的：只改"每个角色用哪个模型"

工作流的图结构、数据集、请求到达序列、服务参数、GPU 池**全部固定不变**；
唯一变化的是**每个角色节点挂哪个模型**。这样测到的一切差异都只能归因于这一项。

- **单模型配置**：所有 agent 节点都用 Qwen3-8B。这就是 Kairos 论文的前提（共用一个大模型）。
- **五模型配置**：五个角色分别用 Qwen3 的 0.6B / 1.7B / 4B / 8B / 14B。
- GPU 池固定 3 张卡（1 张 A100 80GB + 2 张 V100 32GB）。

中间规模的卡数不另外跑真机，改用第 3 节的离线计算一次给出整条曲线。

### 三条工作流

数据集固定（QMSum 会议摘要 / MBPP 代码题 / GSM8K 数学题），编排方式是为这个实验设计的。
三张图各自对应一种在文献中常见的多 Agent 模式：

```
moa_gsm8k        分发 → 五个求解节点 → 投票汇总 → 精修          多模型集成 + 精修
repair_mbpp      写代码 → 跑测试(工具) → {诊断, 评审} → 修复 → 再跑测试(工具)
mapreduce_qmsum  切分 → 七个分块摘要 → 合并                      分而治之的长文摘要
```

节点名字受函数契约约束（分发函数固定发往 `solve_0..4`；初测函数只接受 `coder` 的产出；
终测函数只接受 `tester` 和 `repair` 的产出），**但每个 agent 节点挂哪个模型纯粹由配置决定，
改它不需要动任何代码**。

构建代码：`src/experiment/workflow/motivation_workflows.py`；
导出配置：`scripts/workflow/export_motivation_workflows.py`。

| 角色 | 单模型配置 | 五模型配置 |
|---|---|---|
| 五个求解节点 | 8B ×5 | 0.6B / 1.7B / 4B / 8B / **14B** |
| 精修、修复、合并 | 8B | 8B |
| 写代码 | 8B | **14B** |
| 诊断 / 评审 | 8B | 1.7B / 4B |
| 七个分块摘要 | 8B | 4B |

**两种配置下工作流的名字必须相同**：到达时刻是用工作流名字做随机种子生成的，
名字不同就会拿到不同的请求到达序列，对照就不成立了。配置文件名里才带区分。

### 所有模型共用一套服务参数

每个模型全局只有一套服务配置：上下文窗口 8192、并发序列数 3、批处理 token 上限 24576、显存占用率 0.98。

这么做有两个原因。第一，系统内部用"模型 + 整套服务配置"的哈希来判断两个请求能不能共用同一个
已加载的实例；服务配置只要有一点不同，就会被当成两个不同的部署，跨工作流的复用就静悄悄地失效了。
第二，运维上本来就是给每个模型发布一套服务配置供所有调用方共用。
8192 覆盖了所有角色的最长输入，所以选哪一档显存预算完全由请求的实际长度决定。

**QMSum 切成 7 块而不是 6 块**：实测最长的一块提示词是 5739 个 token，落在 6144 这一档内——
这是 Qwen3-8B 在 V100 上被离线测过的最大一档。切 6 块时最长的那 1.1% 会超到 7168 档，
而 Qwen3-8B 在 V100 上没有这一档，这些请求就只能跑到 A100 上去；
这种差异只在单模型配置下出现，会造成一个与"用几个模型"无关的假差异。

### 上机前的离线核算

拿实测的硬件剖析数据（每个模型在每种卡、每种输入长度下的加载耗时与峰值显存）逐一核算：

| 模型 | 最坏输入下能放进哪种卡 |
|---|---|
| Qwen3-0.6B / 1.7B / 4B / 8B | V100 和 A100 都行 |
| Qwen3-14B | **只能放 A100**（V100 上的显存上界 33.2 GB 超过 32 GB） |

所以单模型配置只有 1 种模型部署（3 张卡绰绰有余）；五模型配置有 5 种，
其中 14B 只能落在唯一那张 A100 上。

各角色输入长度实测：QMSum 分块中位数 1798、最长 5739；MBPP 写代码最长 244；GSM8K 求解最长 160。

## 2. 三篇论文怎么复现的

审稿人一定会问"你复现得对不对"，所以这里把取了什么、刻意没做什么、以及为什么，逐条写清楚。

### 2.1 只取"请求排序规则"，其他一概不实现

这个实验只研究一件事：**GPU 上随时间驻留哪些模型**。
三篇论文在别的方面各有优化和创新，但那些作用在别的维度上；
**如果一并实现，它们带来的性能变化会和模型生命周期的信号混在一起，这条线就没法单独测出来了。**

所以基线做到最简：所有对照组共用完全相同的放置、准入、批处理、换出和背压逻辑，
**唯一不同的是待授予请求按什么顺序排队**。

| 论文 | 本实验取用的规则 | 实现方式 |
|---|---|---|
| **Parrot**（OSDI'24） | 按到达先后，先到先服务 | 项目里现成的 `fifo` 策略，零改动 |
| **Kairos**（arXiv 2508.06948） | 剩余关键路径最短的先做 | 项目里现成的 `kairos` 策略，零改动 |
| **Ayo**（备选，本轮未跑） | 拓扑深度浅的先做 | 尚未实现，需新增一个策略分支 |

**明确没有实现的机制**：

- Parrot 的 Semantic Variable、前缀共享、整张 DAG 的联合优化。
- Ayo 的细粒度数据流拆解、子请求级重排。
- Kairos 的分布式优先级嵌入、按 0.5 秒时隙做 KV 显存打包的分派器。

**这不是系统之间的性能对比。** 本实验不主张"我们比 Parrot 或 Kairos 快"，也不能被这样解读；
它测的是：这几种排序规则各自面对同一份模型驻留压力时，加载开销有没有区别。

### 2.2 Parrot 的规则怎么落到 `fifo` 策略

`fifo` 策略下，同一条工作流内部直接按请求序号排；
各工作流权重相等时，跨工作流的合并会退化成全局到达顺序（这一点在代码注释里已写明）。
所以 `fifo` 就是先到先服务。

分派那一侧我们统一用项目自己的放置逻辑，而不是 Parrot 的轮询。
这一点对所有对照组都一样，因此不构成组间差异。

### 2.3 Kairos 的规则怎么落到 `kairos` 策略

`kairos` 策略按"从当前节点到终点的剩余关键路径耗时"升序排，即剩余耗时最短的先做。

论文原文的做法要复杂一些：为每个 agent 构造一个"剩余执行延迟"的**概率分布**，
两两求 Wasserstein 距离，用多维标度法把它们嵌入到一条直线上，
再放一个"零延迟"的参照分布来确定方向，越靠近这个参照点的优先级越高。

**我们用"按剩余耗时的点估计排序"来近似它，这个近似是可以证明的**：
对一个取值非负的分布，它到"零延迟"这个参照点的 Wasserstein-1 距离，
恰好等于**它自己的期望值**。也就是说，论文里"离零延迟参照点多远"这个量，
数学上就等于"剩余延迟的平均值"。按它在直线上排序，等价于按剩余延迟平均值排序，
也就是最短剩余优先。

剩下的差别只有平均值从哪来：论文用跨会话累积的经验分布，我们用离线剖析数据算出的关键路径点估计。

### 2.4 我们额外送给基线什么

**这三篇论文都没有模型生命周期管理。** Kairos 更是明确假设所有 agent 共用同一个大模型、
实例事先静态部署在同构 GPU（4 张 A40）上，全文不涉及模型的加载、换出和异构模型。

在五模型配置下（5 种模型、3 张卡），忠于原文的静态预部署根本启动不了。
为了让基线能跑起来，**我们把本项目的最近最少使用（LRU）换出机制白送给了它们**。因此：

- 五模型配置下的所有测量，都是在**对基线有利**的条件下做的；
- 如果在这种条件下，两种排序规则的加载开销仍然接近，那就说明这份开销和排序规则无关。

## 3. 从运行记录里算什么

分析代码 `src/experiment/workflow/motivation_residency.py`，只依赖运行记录，四组指标：

1. **同时被需要的模型数**：某一时刻，有多少种不同的模型部署正有请求在排队或在生成。
   由此得到峰值、时间加权分布、以及"超过 N 张卡"的时间占比，并按卡型拆开。
   另外算一个**最优替换的加载次数**：把实际发生的授予顺序当成访问序列，
   假设一个能预知未来的替换策略（每次淘汰"下次使用最晚"的那个），在 N 张卡下要加载几次。
   一次运行记录就能给出整条卡数曲线，不用真的去跑不同卡数。
2. **加载开销**：加载次数、加载占用的 GPU 秒数、占生成时间的比例。
3. **排序规则的影响**：同一配置下两种排序规则把第 2 组指标全量对比。
4. **可利用的余量**：每次加载都归因到它解锁的那个请求；
   算出"这个节点要用哪个模型"是从什么时刻起就已经确定的（即它的直接前驱开始执行的时刻），
   得到**需求提前量**；再看这段提前量是否长过加载本身，以及那段时间里有没有一张合格的卡是空闲的。

**两处刻意的简化**（已写在代码注释里）：某个模型"能用哪些卡"取的是这次运行中实际观测到它落过的卡；
一张卡只要没有生成任务在跑就算可用，不计算把原有模型腾走的代价。
所以第 4 组是**理想情况下的上限**，不是一个真能排出来的调度方案。

出报告：`scripts/workflow/motivation_report.py --root <输出目录>`，生成汇总表和四张数据表。
汇总表里带一列到达序列摘要，三组运行这一列相同才说明对照成立。

### 5.2 问题一：同时被需要的模型数会超过卡数吗

时间加权的"同时被需要的模型数"分布（单位：秒）：

| | 1 种 | 2 种 | 3 种 | 4 种 | 5 种 | 超过 3 张卡的时间占比 |
|---|---|---|---|---|---|---|
| 单模型 + 先到先服务 | 1475 | — | — | — | — | 0% |
| 五模型 + 先到先服务 | 19 | 201 | 285 | 322 | 179 | **49.8%** |
| 五模型 + 最短剩余优先 | 46 | 145 | 337 | 378 | 235 | **53.7%** |

按卡型拆开：**需要 V100 的模型峰值有 4 种，而只有 2 张 V100；需要 A100 的只有 1 种，正好 1 张 A100。**
压力全部落在 V100 一侧，和上机前的核算完全一致——
14B 只能放 A100，因此它独占那张卡，实测在两组五模型运行里都**只加载 1 次、全程不被换出**；
其余 22 次加载全发生在两张 V100 上。

**假设有一个能预知未来的最优替换策略，在不同卡数下要加载几次**（每组都是 360 次访问）：

| | 1 张 | 2 张 | **3 张（实际）** | 4 张 | 5 张 | 6 张 |
|---|---|---|---|---|---|---|
| 单模型 + 先到先服务 | 1 | 1 | **1** | 1 | 1 | 1 |
| 五模型 + 先到先服务 | 110 | 33 | **19** | 10 | 5 | 5 |
| 五模型 + 最短剩余优先 | 133 | 39 | **16** | 6 | 5 | 5 |

→ **单模型配置下不管几张卡都只需加载 1 次，"驻留的模型集合是固定的"这个前提完全成立。**
五模型配置下，即使能预知未来，3 张卡上仍要付 16–19 次加载；
要到 **5 张卡**（正好等于模型种类数）才降到纯粹的开机预热 5 次。
所以这不是"再加一张卡就消失"的假问题。

### 5.3 问题二：加载开销有多大

- **单模型配置：加载 1 次、72 GPU 秒，占生成时间的 2.8%** —— 低于"不值得做"的门槛。
- **五模型配置：加载 23 次、1195–1240 GPU 秒，占生成时间的 54.6%–56.9%。**

请求从提出到拿到模型，这段等待时间花在哪里（每组各 360 次请求）：

| | 总等待 | 等自己要用的模型加载 | 被别的模型的加载挡住 | 其他 |
|---|---|---|---|---|
| 单模型 + 先到先服务 | 47990s | 3.9% | 0.0% | 96.1% |
| 五模型 + 先到先服务 | 18594s | 40.1% | 45.4% | 14.5% |
| 五模型 + 最短剩余优先 | 21569s | 33.9% | 43.4% | 22.7% |

→ 五模型下 **约 85% 的等待压在某次模型加载后面**，其中一多半还是被**别的**模型的加载挡住的；
单模型下这一项只有 3.9%，且完全没有被别人挡住的情况。

⚠️ **总等待的绝对值不能跨配置比较**：单模型那组的 47990s 反而更高，
原因是它只起了一个模型实例、只用了 1 张卡（见 5.6），排队容量只有五模型组的三分之一。
可比的是**构成比例**，也就是"等待里有多大比例压在模型加载后面"。

### 5.4 问题三：换一种请求排序能不能消掉

| | 加载次数 | 加载占用 GPU 秒 | 总完成时间 | 总等待 |
|---|---|---|---|---|
| Parrot 的规则（先到先服务） | 23 | 1195 | 1015s | 18594s |
| Kairos 的规则（最短剩余优先） | 23 | 1240 | 1148s | 21569s |
| 差异 | **0** | **+3.8%** | +13.0% | +16.0% |

→ **两种已发表的排序规则确实改变了总完成时间（差 13%），却几乎没有动到加载开销
（次数完全相同，GPU 秒差 3.8%）。** 这就是问题三的答案：这份开销和请求排序无关。

### 5.5 问题四：有没有可利用的余量

| | 可归因的加载 | 提前量够长的比例 | 提前量够 **且** 当时有空闲卡 | 理想上限可隐藏的加载时间 |
|---|---|---|---|---|
| 五模型 + 先到先服务 | 23 | 43.5% | 30.4% | 319 / 1195 GPU 秒（26.7%） |
| 五模型 + 最短剩余优先 | 23 | 60.9% | 34.8% | 398 / 1240 GPU 秒（32.1%） |

"提前量"是指：一个节点要用哪个模型，从它的前驱开始执行那一刻起就已经确定了；
这个时刻到真正开始加载之间的间隔，如果长过加载本身，就说明信息上来得及提前准备。

→ 大约**一半的加载在需要之前就已经可以预知**；这些里面约 **三分之二** 同时还有一张合格的卡是空闲的。
理想上限下可以把 **27%–32%** 的加载时间藏起来。**信息和容量都不是单独的瓶颈**，两者各筛掉一部分。

单模型那组唯一的一次加载发生在第一个会话启动时，没有前驱可依，因此这一行不适用。

### 5.6 必须声明的干扰因素

**单模型配置只用了 3 张卡里的 1 张。** 实测显示它全程只有一个 Qwen3-8B 实例
（在先到先服务和最短剩余优先这两种排序下，副本扩容路径不启用），
而两组五模型运行都用满了 3 张卡。Kairos 论文里是每张 GPU 各起一个共用模型的实例。

后果和处理方式：

- **跨配置的总完成时间和延迟不可比**：单模型组的 1482s 反而长于五模型组的 1015s，
  这是实例个数的差异造成的，不能读成"模型用得少反而更慢"。本文不使用这个对比。
- **加载开销的对比不受影响，而且是偏保守的**：把单模型配置复制到 3 张卡上最多再加 2 次加载
  （共 3 次），和五模型的 23 次仍差近一个数量级。

其他边界：一张卡只跑一个模型实例——这是运行时的硬性质而不是实验假设，
每张加速卡的记录里至多绑定一个模型副本，显存可行性判据也按整卡算，论文的实验设置一节须正面声明它；
三篇论文只取了排序规则（见第 2 节），**不能读成系统之间的性能对比**；
五模型配置下这两种排序规则是被额外送了一个换出机制才跑得起来的；
5.5 节是理想上限，5.2 节的最优替换次数是给定实际授予顺序下的下限；只跑了一个到达随机种子。

### 5.7 少了模型生命周期管理，在总完成时间和驻留时间上浪费了多少

**(a) 总完成时间里，有多少是全场停下来等加载**
"全场无生成"指三张卡上一个生成请求都没在跑的墙钟时间。

| | 总完成时间 | 全场无生成 | 其中有卡在加载 |
|---|---|---|---|
| 单模型 + 先到先服务 | 1482s | 286s（19.3%） | 72s（**4.9%**） |
| 五模型 + 先到先服务 | 1015s | 298s（29.4%） | 289s（**28.5%**） |
| 五模型 + 最短剩余优先 | 1148s | 383s（33.4%） | 370s（**32.3%**） |

→ 五模型下 **总完成时间的 28%–32% 是整个集群停下来等模型加载**；单模型下只有 4.9%。
这是总完成时间可优化空间的**上限**——加载若能瞬时完成，这段时间至多全部转成有效生成。

**(b) 模型驻留在卡上的时间，有多少是空占着**

这里的驻留从模型加载完成算到开始换出或运行结束，不包含加载和换出本身。

| | 驻留 GPU 秒 | 其中真在生成 | 驻留但闲置 |
|---|---|---|---|
| 单模型 + 先到先服务 | 1404 | 1195 | 209（**14.9%**） |
| 五模型 + 先到先服务 | 1807 | 949 | 858（**47.5%**） |
| 五模型 + 最短剩余优先 | 2159 | 1021 | 1138（**52.7%**） |

→ 五模型下**约一半的真实驻留时间没有生成任务在跑**；单模型下约为 15%。

**(c) 这部分空间可以由哪些机制取走（都是理想上限）**

| 机制 | 五模型 + 先到先服务 | 五模型 + 最短剩余优先 |
|---|---|---|
| 更聪明的换出（按能预知未来的最优替换算，3 张卡） | 少加载 4 次 = 208 GPU 秒（占加载开销 17.4%） | 少 7 次 = 377 GPU 秒（30.4%） |
| 提前加载（提前量够且当时有空闲卡） | 藏起 319 GPU 秒（26.7%） | 藏起 398 GPU 秒（32.1%） |

两者部分重叠（省掉的加载就不必再藏），不能直接相加。
注意**换出算法本身的空间有限**（最多省 4–7 次加载），大头在提前加载，
以及减少 858–1138 GPU 秒的驻留空闲。

**(d) 以上都是上限，不是实测收益。** 这一轮三组运行都没有模型生命周期管理，
所以只能说"空间有这么大"，不能说"某个机制真能拿到多少"。要坐实需要补一组带该机制的实测。

### 5.8 一个约束性的读数

实际发生了 23 次加载，而能预知未来的最优替换是 16–19 次：
**单纯换一个更好的换出算法，最多只能省下 23 次里的 4–7 次。**
所以在这个负载上，"换出决策"本身的余量有限；
加载开销之所以能占到生成时间的 55%，主要来自工作集和卡数的结构性错配。
能动的方向是提前加载（5.7 节给出 27%–32% 的上限）、跨工作流复用和放置，
而不是单纯改进替换算法。这一条同样是本实验的结论，写论文时不该回避。

## 6. 结果怎么解读

| 如果观察到 | 说明 | 实测落点 |
|---|---|---|
| 两种配置的加载开销都很小 | 三篇论文把驻留模型当固定集合是对的，这条线终结 | 否：单模型 2.8%，五模型 55% |
| 开销随模型种类上升，但换个排序就能消掉 | 属于已有工作的范围，不是新维度 | 否：两种排序的加载次数完全相同 |
| 开销随模型种类上升，且和排序无关 | 存在一个已有工作没覆盖的决策维度 | **是** |
| 卡数一到实际值，最优替换次数就趋近于零 | 问题是卡配少了，不是驻留决策 | 否：3 张卡时最优仍需 16–19 次，要 5 张才降到预热 |
| 提前量够长的比例很低 | 这个维度就算重要也没有信息可用 | 部分：43%–61%，约一半 |
| 提前量够但当时没有空闲卡 | 信息充足而容量稀缺，瓶颈位置就定位了 | 两者各筛掉一部分，都不是单独的瓶颈 |

**结论**：把"GPU 上驻留哪些模型"当成固定集合这个前提，在所有角色共用一个模型时成立、开销可忽略；
在角色用不同模型时失效——加载占掉生成时间的 55%、占掉请求等待的 85%、
占掉总完成时间的 28%–32%，真实模型驻留时间约有一半没有生成任务，
而且**这一切和两篇论文提出的请求排序规则都无关**。
这是一个已有工作没有覆盖的决策维度。它的可动余量主要不在换出算法（最优也只省 4–7 次），
而在提前加载（理想上限 27%–32%）和复用 / 放置。
