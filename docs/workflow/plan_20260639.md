# Workflow runtime 重构与实现计划

本文只记录计划，不执行实现。

## 背景依据

本计划基于以下本地资料和当前源码现状整理：

- `docs/dev/workflow_plugin_20260626.md`
- `docs/workflow/experiment_20260626.md`
- `docs/workflow/experiment_20260629.md`
- `src/workflow/` 当前实现

注意：当前工作区没有找到 `docs/workflow/deploy_20260629.md`。后续如果该文档存在于其他分支或未同步目录，需要再合并其中决策。

## 已确认方向

当前不继续在旧 `workflow` 模块上小修小补，而是借 GNN 预测器、BufferNode 和有限 GPU 调度需求，进行一次破坏性重构。

核心方向是实现一个 workflow runtime 控制器。该控制器持有：

- workflow DAG 描述
- BufferNode 实例
- 全局 GPU 资源池
- GNN 资源预测服务
- 模型加载、释放、预取、驱逐状态
- trace 和实验指标记录器

用户倾向将该控制器命名为 `Workflow`。由于当前 `src/workflow/schema.py` 中已有 Pydantic 配置类 `Workflow`，实现时建议重命名旧配置类为 `WorkflowSpec` 或 `WorkflowConfig`，把新的运行时控制器命名为 `Workflow`。这是破坏性变更，但符合当前重构目标。

## 过往实验教训

之前并行度实验暴露出几个必须在实现中直接处理的问题：

- 不能只记录端到端耗时，必须记录节点级 trace，否则无法判断等待损失来自哪里。
- 输入 token 上限和输出 token 上限必须机器可读记录，不能只写在实验说明里。
- `sequence_length_hit_rate` 表示输入被截断或命中输入上限的比例。
- `max_new_tokens_hit_rate` 表示生成输出达到 `max_new_tokens` 上限的比例，通常意味着输出可能被硬截断。
- 输出上限过小会让实验结论失真，必须先做小样本预检。
- 数据规模过大时必须先跑 smoke test，再扩大到正式样本。
- BufferNode 的主要收益不是消除同一个 session 内 fan-in 依赖，而是让不同 session 跨样本流水线推进。
- 在资源受限场景下，调度器必须显式管理模型生命周期，否则 chunk agent 完成后仍然占卡，merge agent 无法及时启动。

## 当前源码问题

当前 `src/workflow` 的主要问题如下：

- `schema.Workflow` 只是配置模型，不是运行时控制器。
- `execution.py` 混合了 CLI、dataset loader、LangGraph runner、本地 Qwen backend、parallel runner、evaluator 和 summary 汇总，边界过宽。
- `parallel` mode 只是 sample 内 ready node 并发，执行完一条 sample 才进入下一条，无法获得 20260626 离线模拟中的跨样本流水线收益。
- `scheduler.py` 是静态设备选择器，不具备全局资源池、模型释放、预取、驱逐和 session 级调度能力。
- `handlers.py` 中的 `NodeHandler` Protocol 过于抽象，不能表达模型生命周期、资源申请、token budget 调整等实际能力。
- `scheduled_tool_nodes.py` 更偏 ReAct tool 包装，不适合作为新的静态 DAG runtime 主线。
- `evaluation_20260612.py` 属于意义不清的历史代码，应迁移必要逻辑后删除。
- `gnn_predictor.py` 已有可复用的 `WorkflowGnnPredictor`，但当前只支持图输入预测，尚未封装成 runtime 节点/服务接口。

## 目标系统形态

目标系统不是简单添加一个队列，而是实现预测驱动的数据流 runtime：

```text
WorkflowSpec -> Workflow(runtime controller)
             -> BufferNode / ComputeNode
             -> ResourcePool
             -> GnnPredictionService
             -> ModelRuntimeBackend
             -> TraceRecorder
```

其中：

- `WorkflowSpec` 负责描述 DAG、节点、边、模型、prompt、执行参数。
- `Workflow` 负责全局调度和资源管理。
- `BufferNode` 负责 session 聚合、有界缓冲、背压、ready item 生成。
- `ComputeNode` 负责实际执行模型、工具或 evaluator。
- `ResourcePool` 负责 GPU 资源申请、占用、释放、驱逐。
- `GnnPredictionService` 提供统一预测接口。
- `TokenBudgetController` 根据预测结果动态调整 `sequence_length` 和 `max_new_tokens`。
- `TraceRecorder` 统一记录队列、调度、预测、模型生命周期、token 和质量指标。

## GNN 预测器接口

GNN 预测器应封装成 runtime 服务节点或服务对象，开放稳定接口：

```python
class ResourcePredictor:
    def predict(self, features: ResourceFeatures) -> ResourcePrediction:
        ...
```

输入 `ResourceFeatures` 至少包含：

- `node_name`
- `model_name`
- `device_name`
- `gpu_name`
- `phase`
- `batch_size`
- `sequence_length`
- `max_new_tokens`
- `input_token_count`
- `prompt_token_count`
- `model_parameters`
- 可选 ONNX graph 特征

输出 `ResourcePrediction` 至少包含：

- `run_duration_sec`
- `deployment_duration_sec`
- `gpu_mem_used_mb`
- `memory_delta_gb`
- `gpu_power_watts`
- `confidence`
- `safety_margin`
- `raw_metrics`

默认 checkpoint 暂时使用：

```text
output/gnn_full_retrain_20260612/gnn_model_scaled_20260612/checkpoints/best_model.pt
```

默认配置使用：

```text
output/gnn_full_retrain_20260612/effective_config.yaml
```

该 checkpoint 只能作为 smoke test 和保守 baseline。它不能自动证明 Qwen 推理资源预测已经足够精确。

## Token budget 控制

每个本地生成式节点执行前必须经过 token budget 控制：

1. 根据 prompt 估算或真实 tokenize 得到 `input_token_count`。
2. 构造 GNN 输入特征。
3. 预测显存、耗时和风险。
4. 根据当前 GPU 可用显存和 safety margin 调整：
   - `sequence_length`
   - `max_new_tokens`
5. 如果预测仍然超过资源限制，则进入等待、降级、跳过或失败策略。

必须记录：

- 原始 `sequence_length`
- 实际 `sequence_length`
- 原始 `max_new_tokens`
- 实际 `max_new_tokens`
- 输入上限是否命中
- 输出上限是否命中
- 预测显存
- 实测显存
- 调整原因

## BufferNode 设计

BufferNode 是数据流边界，不是普通 LangGraph node 的薄包装。

每个 buffer item 至少包含：

- `session_id`
- `item_id`
- `source_node`
- `target_node`
- `payload`
- `created_at`
- `enqueue_at`
- `ready_at`
- `metadata`

BufferNode 必须支持：

- 有界队列
- 背压
- session 聚合
- fan-in 输入齐全后触发
- 多 session 并发推进
- drain 等待
- 失败重试
- 失败记录

对于 `chunk_a/chunk_b/chunk_c -> merge` 场景，merge BufferNode 需要按 `session_id` 收集 3 个 chunk 结果。只有同一 session 的必需输入全部到齐，merge item 才能进入 ready queue。

## 有限 GPU 调度场景

需要显式支持以下场景：

```text
3 张 GPU
3 个 chunk agent
1 个 merge agent
merge 依赖 3 个 chunk agent 的同 session 输出
```

调度目标：

- chunk agent 可先占满 3 张卡。
- runtime 根据 GNN/历史 ETA 预测每个 chunk 完成时间。
- 当已有 chunk 完成但最后一个 chunk 尚未完成时，控制器可以释放已完成 chunk agent 的 GPU。
- 如果 merge agent 的模型加载耗时较长，控制器可以在预计输入即将齐全前预取 merge 模型。
- 当 merge 输入齐全时，应尽量避免再等待模型冷启动。

这要求每个模型节点支持生命周期接口：

```python
class ManagedNode:
    def prepare(self, allocation: ResourceAllocation) -> None: ...
    def run(self, item: RuntimeItem) -> RuntimeResult: ...
    def release(self) -> None: ...
    def estimate(self, features: ResourceFeatures) -> ResourcePrediction: ...
```

旧 `NodeHandler` Protocol 应删除或替换为更具体的接口。

## 调度策略

第一阶段只做可解释的启发式策略，不引入复杂 MILP 或 RL。

候选策略：

- `fifo`: ready item 按到达顺序执行。
- `history_eta`: 使用历史 token/耗时统计估算 ETA。
- `gnn_margin`: 使用 GNN 预测值加 safety margin。
- `workflow_future`: 结合 DAG 下游依赖、ETA、模型加载成本和未来复用概率。

最小实现优先级：

1. `fifo`
2. `history_eta`
3. `gnn_margin`
4. `workflow_future`

## 模型生命周期

模型状态建议定义为：

- `not_loaded`
- `loading`
- `loaded_idle`
- `running`
- `evicting`
- `evicted`
- `failed`

资源池需要维护：

- 每张 GPU 的总显存
- 当前可用显存
- 已加载模型
- 正在运行的节点
- pending prefetch
- pending eviction
- 冷启动耗时历史

驱逐策略第一版应支持：

- 保留当前 running 模型。
- 优先驱逐已完成且短期无 ready item 的 chunk agent。
- 优先保留即将被 fan-in 触发的 merge agent。
- 避免刚驱逐又立即加载的无效驱逐。

## 实现阶段

### Phase 0: 清理和命名

目标：建立清晰边界，不改变实验语义。

任务：

- 将旧 `schema.Workflow` 重命名为 `WorkflowSpec` 或 `WorkflowConfig`。
- 新增 runtime 控制器 `Workflow`。
- 拆分 `execution.py`：
  - dataset/evaluation CLI
  - prompt rendering
  - local model backend
  - legacy DAG runner
  - summary metrics
- 删除或隔离 `evaluation_20260612.py`。
- 删除 `handlers.py` 中虚的 Protocol，或替换为 runtime 所需接口。
- 保留旧测试，必要时批量改名适配。

验收：

- 现有 workflow loader 和 validation 测试通过。
- 旧 parallel 实验仍可运行，或者明确迁移到 `legacy` 路径。

### Phase 1: BufferNode 最小闭环

目标：先证明真实 runtime 可以执行跨样本流水线。

任务：

- 实现 `RuntimeItem`、`SessionState`、`BufferNode`。
- 实现有界队列和背压。
- 实现 fan-in session 聚合。
- 实现 drain。
- 实现失败重试记录。
- 实现不依赖 GNN 的 `fifo` 调度。

验收：

- 构造 fast producer / slow consumer 单元测试。
- 验证 bounded queue 最大长度不超过容量。
- 验证所有已接收 item 最终完成或有失败记录。
- 复现 QMSum 2-way/3-way workflow 的 buffered runner smoke test。

### Phase 2: ResourcePool 与模型生命周期

目标：让 runtime 真正管理 GPU，而不是静态写死 device。

任务：

- 实现 `ResourcePool`。
- 实现 `ResourceAllocation`。
- 实现模型 `prepare/run/release` 生命周期。
- 改造 `LocalQwenTextGenerationBackend` 支持按节点加载和释放。
- 增加模型冷启动、释放、复用 trace。
- 支持手动限制可用 GPU 数，例如只启用 3 张卡。

验收：

- 3 chunk + 1 merge + 3 GPU 的模拟测试通过。
- chunk 完成后可以释放 GPU。
- merge 可以在资源释放后加载并执行。

### Phase 3: GNN 预测服务接入

目标：将 GNN 预测器作为 runtime 服务接入，但先不让它承担强 OOM 保证。

任务：

- 新增 `ResourcePredictor` 接口。
- 封装现有 `WorkflowGnnPredictor`。
- 支持默认 checkpoint 配置。
- 支持无 GNN 时 fallback 到静态或历史估算。
- 将预测结果写入 trace。

验收：

- 使用默认 checkpoint 完成 smoke test。
- 预测失败时 workflow 不崩溃，可降级到 fallback。
- trace 中能看到每次调度使用的预测值。

### Phase 4: Token budget 控制

目标：解决输入输出 token 上限导致 OOM 或截断的问题。

任务：

- 新增 `TokenBudgetController`。
- 执行前 tokenize prompt。
- 根据预测显存和可用资源调整 `sequence_length`、`max_new_tokens`。
- 支持保守 safety margin。
- 记录 hit rate 和调整原因。

验收：

- 使用最长 QMSum 样本做预检。
- 不再因未记录 token hit 导致实验不可解释。
- `prompt_only` 和真实 generation 上限控制可区分。

### Phase 5: ETA-aware prefetch / eviction

目标：提升有限 GPU 下 fan-in 后 merge 启动速度。

任务：

- 为每个 running item 维护 ETA。
- 上游 BufferNode 向下游报告 ETA。
- 控制器根据 merge 输入齐全预计时间和加载耗时决定预取。
- 实现 workflow-aware eviction。

验收：

- 对比 `no_prefetch`、`eager_prefetch`、`eta_prefetch`。
- 记录 ready-to-start wait、无效预取、无效驱逐。
- 验证 3 GPU 场景下 merge 等待时间下降。

### Phase 6: 实验复现与报告

目标：用新 runtime 复现实验并生成可解释结论。

任务：

- 复现 `native_parallel` baseline。
- 跑 `buffered_no_gnn`。
- 跑 `buffered_eta`。
- 跑 `buffered_gnn`。
- 跑 token budget/OOM 风险实验。
- 生成 JSONL trace 和 markdown summary。

验收：

- 明确报告 total、mean、p95、GPU busy/idle、queue wait、blocked time。
- 明确报告质量指标，避免只优化速度。
- 明确报告 token hit rate、OOM、空输出、judge error。

## 需要用户确认的事项

以下事项影响系统实现，需要后续确认：

- 新运行时控制器是否最终命名为 `Workflow`，并将旧 schema 类改名为 `WorkflowSpec`。
- 旧 `execution.py` 的 CLI 是否保留兼容入口，还是迁移到新的命令。
- `evaluation_20260612.py` 是否确认直接删除，还是先迁移其中仍被测试依赖的逻辑。
- GPU 资源池第一版是否只支持单机多卡，不支持跨机器。
- 模型释放是否允许真实卸载模型并清理 CUDA cache，还是第一版只做逻辑释放和测试替身。
- OOM 处理策略默认是 fail-fast、retry with smaller budget，还是 skip current item。
- token budget 降级时最低可接受 `sequence_length` 和 `max_new_tokens` 是多少。

## 暂不处理

第一版不处理：

- 分布式队列。
- 跨机器调度。
- Exactly-once。
- 持久化大规模流数据。
- 强化学习调度。
- MILP 全局最优调度。
- 动态 ReAct tool call 主线。
- 证明 GNN 对 Qwen 推理已经具备最终精度。

## 实现顺序

推荐按以下顺序推进：

1. Phase 0 清理命名和模块边界。
2. Phase 1 BufferNode 最小闭环。
3. Phase 2 ResourcePool 和模型生命周期。
4. Phase 3 GNN 预测服务接入。
5. Phase 4 Token budget 控制。
6. Phase 5 ETA prefetch 和 eviction。
7. Phase 6 正式实验复现。

每一阶段完成后都必须先跑小规模测试并检查 trace，再进入下一阶段。
