# workflow 调度场景设计

一个用户 session 对应一种 workflow 组合。agent 节点使用外部 LLM
provider，工具节点使用本地部署的小模型提供服务。GNN 预测器不需要覆盖
workflow 的全部调度问题，也不必强行使用所有预测目标。更有价值的问题是：
哪些预测信号会真实影响 agent workflow 的端到端体验、可用性和资源成本。

本文用于指导创新点构思。重点不是罗列功能，而是识别 GNN 预测器在 agent
workflow 中最容易形成差异化价值的场景。

## 关键影响因素

优先考虑以下因素：

- 部署耗时：工具模型是否已经在加速卡上，决定 session 冷启动和首次工具调用延迟。
- OOM 隐患：工具模型能否成功部署和执行，通常比细粒度性能优化更影响系统可用性。
- 推理耗时：影响 agent 调用工具后的等待时间，也影响多个工具节点的执行顺序。
- 显存占用：决定模型缓存、驱逐、复用和有限资源下的并发能力。
- 功耗与能耗：适合构造节能或低碳方向，但应服务于明确场景，而不是单独作为指标堆叠。
- 加速卡类型：同一工具模型在不同 GPU 上的部署成本、显存风险和推理效率可能不同。

其他预测目标可以作为辅助信号，而不是创新点主线。例如 GPU 利用率、SM active
和 SM occupancy 更适合作为并发、共置或资源浪费的解释信号；CPU 和主机内存
只有在工具节点确实会造成主机侧瓶颈时才需要强调。

## 工具节点驱逐与复用

每个 session 都有自己的工具节点组合。当新 session 到达系统时，已有加速卡
上可能已经部署了部分工具模型。此时调度问题不是“运行哪个模型”，而是“保留
哪些模型、驱逐哪些模型、复用哪些模型”。

例如，一个 session 需要使用 `qwen3` 生成摘要并使用 `gemma4` 做复核；
下一个 session 需要复用 `qwen3`，但把复核节点切换到 `llama`。在这种情况
下，`qwen3` 可以复用，`gemma4` 可能需要被驱逐并替换为 `llama`。

这个方向适合突出部署耗时和显存占用。传统缓存策略通常只考虑最近访问时间或
显存大小，而 agent workflow 还需要考虑模型重新部署的代价。如果一个模型部署
很慢、未来 session 复用概率高、显存占用又可接受，那么即使它最近没有被调用，
也可能值得保留。

可构思的创新点：

- 用 GNN 预测重部署成本，改进工具模型缓存驱逐策略。
- 在多 session workflow 中区分“显存大但重部署便宜”和“显存适中但冷启动很慢”的模型。
- 用预测显存峰值识别驱逐后仍可能 OOM 的替换方案，避免无效换入。

## 工具节点冷启动优化

workflow 初始化时，工具节点可能都需要冷启动。冷启动会直接影响用户第一次收到
工具结果的时间，也会影响 agent 是否愿意调用更重的本地工具模型。

这个方向的关键不是把所有工具都提前部署，而是判断哪些工具值得提前部署。对
高概率会被调用、部署耗时长、显存风险低的工具，可以考虑预部署；对低概率调用、
部署便宜或显存风险高的工具，可以等 agent 明确需要时再部署。

可构思的创新点：

- 根据 GNN 预测的部署耗时和显存风险，选择 session 初始化时的预部署工具集合。
- 在多个加速卡类型之间选择冷启动位置，避免把工具部署到推理快但部署慢或显存紧张的设备上。
- 把工具冷启动成本暴露给 agent，让 agent 在多个语义近似工具之间选择低成本路径。

这里不需要把所有预测目标都纳入决策。冷启动场景最核心的是部署耗时、显存峰值
和加速卡类型；功耗可以作为节能场景的补充，而不是必须项。

## OOM 风险感知调度

agent workflow 的工具节点往往是按需调用的。agent 决定需要多个工具时，系统
不能假设这些工具都能同时部署或并行执行。相比单纯优化推理耗时，先避免 OOM
更实际，因为 OOM 会导致工具调用失败、重试、甚至整个 session 超时。

GNN 预测器在这里可以承担风险评估角色：在工具执行前估计模型部署和推理阶段的
显存峰值，判断当前加速卡是否适合运行该工具。如果风险高，可以选择换卡、串行
执行、延后执行，或让 agent 使用轻量替代工具。

可构思的创新点：

- 在 agent 调用工具前预测 OOM 风险，降低失败重试带来的端到端延迟。
- 对多个 ready 工具节点按显存风险排序，先执行低风险或关键路径节点。
- 在显存紧张时选择轻量替代工具，而不是盲目调用最强模型。

这个方向比单纯预测 `run_duration` 更贴近 agent workflow 的可用性问题，也更容易
与本地小模型部署场景形成区别。

## 节能与功耗感知调度

节能方向适合用于多 session 或长时间运行的 agent workflow。单个工具节点的功耗
预测如果脱离调度动作，意义有限；它需要和执行顺序、选卡、模型复用或工具选择
结合起来。

可构思的创新点：

- 在不增加明显延迟的前提下，把高功耗工具错峰执行，降低瞬时功耗峰值。
- 在多个可选工具模型之间选择能耗更低的模型，特别是当语义收益接近时。
- 对频繁调用的工具优先保留缓存，减少反复部署带来的额外能耗。
- 在 V100/A100 等不同加速卡之间选择能耗更优的执行位置，而不是只看推理速度。

节能场景应避免写成“预测功耗所以节能”。更合理的表述是：GNN 预测器提供
工具模型在不同设备和 runtime 下的功耗/耗时估计，调度器据此选择能耗与延迟
折中更好的执行方案。

## 有限资源下的工具执行顺序

当加速卡资源不足以同时运行所有工具节点时，agent 仍可能一次性提出多个工具
需求。系统需要决定哪些工具先运行，哪些后运行。

这里的关键因素是推理耗时、部署耗时、显存风险和 workflow 依赖关系。对于
关键路径上的工具，优先执行可以缩短整体等待时间；对于已缓存工具，优先执行
可以减少冷启动；对于显存风险高的工具，串行执行可能比并行失败后重试更优。

可构思的创新点：

- 用 GNN 预测的耗时和显存风险对 ready 工具节点排序。
- 把部署耗时纳入工具执行顺序，避免短推理但长冷启动的节点拖慢 session。
- 在资源不足时区分必要工具和可选工具，让 agent 基于预测成本调整工具调用计划。

这个方向不需要上来就设计完整调度器。创新点可以集中在“GNN 预测信号如何改变
agent 工具调用的优先级和资源风险判断”。

## 构思边界

构思创新点时应优先围绕部署耗时、OOM 隐患、显存占用、推理耗时和节能收益展开。
这些因素直接影响 agent workflow 的用户体验和系统成本。

不建议把所有 GNN 预测目标都写成同等重要的调度目标。利用率、SM 指标、CPU
和主机内存更适合作为解释或辅助约束。只有当它们能明确改变工具选择、选卡、
驱逐、冷启动或执行顺序时，才值得成为主线创新点。
