# serve_0728 实验参照手册

**这份文档写给没接触过这次实验的人。** 读完你应该能看懂 `output/serve_0728/` 里每个目录名
是什么意思、每次运行跑的是什么、结果文件里每个数字从哪来。

配套文档：`docs/workflow/experiment_runbook_serve_0728.md` 是提交命令清单，本文是解读手册。

---

## 1. 这个实验要回答什么

被测系统是 `src/workflow/` 下的一套多智能体工作流运行时。它在一小撮固定的、型号不一样的
显卡上调度若干条工作流，每条工作流由若干节点串成，其中一部分节点要调用大语言模型。
显卡数量远少于模型数量，所以**哪个模型什么时候占哪张卡**是核心决策。

实验用六个自变量交叉，看每个机制各值多少：

| 自变量 | 取值个数 | 怎么落到运行上 |
|---|---|---|
| 到达方式 | 4 | 换实验配置文件 |
| 显卡环境 | 3 | 换集群（一个集群一种配卡） |
| 预测算法 | 3 | 换预测数据文件 |
| 节点融合 | 开 / 关 | 命令行开关 |
| 预取 | 开 / 关 | 调度器配置项 |
| 跨工作流的模型生命周期管理 | 开 / 关 | 调度器配置项 |

后四个自变量被压缩成 8 个命名好的"方案"（见第 3 节），所以矩阵是
**8 方案 × 4 到达方式 × 3 显卡环境 × 3 次重复 = 288 次运行**。

## 2. 目录名怎么读

```
output/serve_0728/a1v4__poisson_r025__noprefetch/r2/
                  └─┬─┘  └─────┬─────┘  └───┬────┘  └┬┘
                显卡环境    到达方式        方案      第几次重复
```

三段用**两个下划线**隔开，段内自己可能带单下划线。重复次数是里面一层目录，`r1`/`r2`/`r3`。

### 显卡环境这一段

命名规则是「A 的个数 + V 的个数」，A 指 A100（80 GB 显存），V 指 V100（32 GB 显存）。

| 代号 | 实际配卡 | 跑在哪个集群 |
|---|---|---|
| `a1v2` | 1 张 A100 + 2 张 V100（共 3 张） | 端口 6661 |
| `a1v3` | 1 张 A100 + 3 张 V100（共 4 张） | 端口 6662 |
| `a1v4` | 1 张 A100 + 4 张 V100（共 5 张） | 端口 6663 |

集群不是虚拟划分，是三套真实的 Ray 集群，每台机器挂一张卡。**一个集群同一时刻只能跑一次
实验**，因为每次运行都会清空整个显卡池。

这一段是从运行记录里的显卡清单反推出来的，不是人写死的，所以它一定和实际用的卡一致。

### 到达方式这一段

指 60 个会话按什么节奏投进系统。

| 代号 | 含义 | 每条工作流每秒到达的会话数 | 全部投完要多久 |
|---|---|---|---|
| `burst` | 一次性全投 | —— | 0 秒 |
| `poisson_r050` | 泊松过程，最密集 | 0.050 | 约 460 秒 |
| `poisson_r025` | 泊松过程，中等 | 0.025 | 约 918 秒 |
| `poisson_r0125` | 泊松过程，最稀疏 | 0.0125 | 约 1836 秒 |

`r` 后面的数字是速率去掉小数点：`r050` = 0.050，`r0125` = 0.0125。

**三档泊松是同一条到达序列的三种速度，不是三次不同的随机抽样。** 随机数种子只由
（种子值、字符串 "arrival"、工作流名）决定，而指数分布的采样是 `-ln(U)/速率`，三档共用同一串
`U`，所以每个会话的到达时刻严格按速率比例缩放。种子固定为 42，**全部 288 次运行共用同一条到达
序列**，所以任何两次运行之间的差异都不含到达抖动；三次重复量的是系统自身的非确定性。

## 3. 八个方案分别是什么

映射关系写死在 `scripts/workflow/run_serve_0728.sh` 里，是唯一的真相来源。

| 方案代号 | 中文 | 调度器配置 | 预测数据 | 节点融合 | 相对参考格改了什么 |
|---|---|---|---|---|---|
| `sagepilot` | 参考格 | `scheduler_sagepilot` | `cache/profile_v2` | 开 | —— 基准 |
| `analytical` | 解析公式预测器 | `scheduler_sagepilot` | `cache/static` | 开 | 只换预测算法 |
| `gbdt` | 梯度提升树预测器 | `scheduler_sagepilot` | `cache/tabular` | 开 | 只换预测算法 |
| `nofuse` | 去掉节点融合 | `scheduler_sagepilot` | `cache/profile_v2` | **关** | 只关融合 |
| `noprefetch` | 去掉预取 | `scheduler_sagepilot_noprefetch` | `cache/profile_v2` | 开 | 只关预取 |
| `noxwf` | 生命周期按工作流分开决策 | `scheduler_sagepilot_noxwf` | `cache/profile_v2` | 开 | 只关跨工作流 |
| `parrot` | Parrot 排序基线 | `scheduler_parrot` | `cache/profile` | 关 | 换整套调度策略 |
| `kairos` | Kairos 排序基线 | `scheduler_kairos` | `cache/profile` | 关 | 换整套调度策略 |

配置文件都在 `config/workflow/serve/serve_0728/`。

### 前六个方案是消融，可以逐条归因

`sagepilot` 是参考格，`analytical`/`gbdt`/`nofuse`/`noprefetch`/`noxwf` 各自**只与它差一项**。
`nofuse`、`noprefetch`、`noxwf` 三个消融臂与参考格共用同一份预测数据（`profile_v2`），这是刻意
的：如果它们用不同的预测数据，就同时差了"一个机制"和"预测数据"两项，差异没法归到机制头上。
`analytical` 和 `gbdt` 换预测数据，因为预测算法本身就是它们的自变量。

### 后两个方案是外部基线，不能当消融读

`parrot` 和 `kairos` 取自两篇已发表工作，**只借用它们的请求排序规则**，其余机制（Parrot 的语义
变量、前缀共享、整图联合优化；Kairos 的优先级嵌入、时隙显存打包）一概没实现。它们与参考格同时
差好几项（排序策略、预测数据、融合），所以只能当作参照线，不能说"关掉某机制就变成 Parrot"。

它们用原始实测数据 `cache/profile` 而不是 `profile_v2`，因为后者含本项目自己做的模型装载时长
校准，白送给基线不合适。

## 4. 四份预测数据是什么

这些文件让调度器在**不实际运行**的前提下估计"某模型在某张卡上跑某个请求要多久、要多少显存、
装载要多久"。调度决策（能不能放得下、要不要预取、要不要多开一个实例）全靠它们。

| 目录 | 来源标记 | 条目数 | 这是什么 |
|---|---|---|---|
| `cache/profile` | `empirical_profile` | 2848 | 原始实测 |
| `cache/profile_v2` | `empirical_profile` | 5732 | 实测 + 本项目的装载时长校准 |
| `cache/static` | `synthetic_fixture` | 2848 | 解析公式推算（按模型大小与带宽） |
| `cache/tabular` | `synthetic_fixture` | 5413 | 梯度提升树回归 |
| `cache/gnn_v2` | `gnn_predicted` | 2848 | 图神经网络预测器 —— **本次实验没用到** |

**一个对读结果非常关键的差异**：不同数据文件对"把模型读进显卡要多久"的估计差一个数量级。
以 Qwen3-4B 为例：

| 数据文件 | 预测的 4B 装载耗时 |
|---|---|
| `cache/static` | **0.3 秒** |
| `cache/profile_v2` | 45.8 秒 |
| `cache/tabular` / `cache/profile` | 164.8 秒 |

这个差异会直接影响"要不要给热门模型多开一个实例"的判断——估计越短，多开看起来越划算。
第 8 节的已知缺陷与这一点直接相关。

## 5. 跑的是什么活

三条工作流，每条 20 个会话，每次运行共 **60 个会话**。三条同时注册在一个调度器上，抢同一批卡。

### moa_gsm8k —— 数学题多模型求解（数据集 GSM8K）

8 个节点。一道题分发给五个不同大小的模型各自作答，汇总投票后由一个模型精修。

```
fanout(函数) ─┬→ solve_0 (Qwen3-0.6B) ─┐
              ├→ solve_1 (Qwen3-1.7B) ─┤
              ├→ solve_2 (Qwen3-4B)   ─┼→ aggregate(函数) → refine (Qwen3-8B)
              ├→ solve_3 (Qwen3-8B)   ─┤
              └→ solve_4 (Qwen3-14B)  ─┘
```

### repair_mbpp —— 代码生成与修复（数据集 Sanitized MBPP）

6 个节点。写码、跑测试、诊断错误、评审、修复、再测。

```
coder (Qwen3-14B) → tester(函数) ─┬→ diagnoser (Qwen3-1.7B) ─┬→ reviewer (Qwen3-4B) ─┐
                                  │                           │                       │
                                  ├───────────────────────────┴───────────────────────┼→ repair (Qwen3-8B)
                                  └→ final_tester(函数) ←──────────────────────────────┘
```

### chain_qmsum —— 会议摘要（数据集 QMSum）

10 个节点。切成两条并行的三段滚动摘要链，再合并、补充、定稿。

```
split(函数) ─┬→ lane_a_0 → lane_a_1 → lane_a_2 ─┐
             └→ lane_b_0 → lane_b_1 → lane_b_2 ─┴→ merge → expand → finalize
```
`lane_*` 六个节点全是 Qwen3-4B，`merge`/`expand`/`finalize` 全是 Qwen3-8B。

### 关于模型

一共只用 5 个模型：Qwen3 的 0.6B、1.7B、4B、8B、14B，路径在 `/data/Models/Qwen/`。

**三条工作流共用同一套服务参数**（上下文 8192、并发 3、批 token 上限 24576、显存占用率 0.98，
单次最大输出 384 或 512）。这一点很重要：系统用整个服务参数块的哈希来标识一个"模型部署"，
如果哪条工作流自带一套参数，同一个模型就会分裂成两个部署，驻留压力被悄悄改掉。当前配置下
**全局恰好 5 个不同的模型部署**。

Qwen3-14B 在 8192 上下文下装不进 32 GB 的 V100，**只能放 A100**，所以每个集群至少要有一张 A100。

### 节点融合只对 chain_qmsum 有效

融合是注册前的图改写：把首尾相接、用同一个模型的相邻节点合并成一个节点，省掉中间的排队和
重新申请显卡。实测效果：

| 工作流 | 融合前 | 融合后 |
|---|---|---|
| `moa_gsm8k` | 8 节点 | 8 节点（无相邻同模型边） |
| `repair_mbpp` | 6 节点 | 6 节点（无相邻同模型边） |
| `chain_qmsum` | 10 节点 | **4 节点** |

融合出的三个节点叫 `lane_a_0+lane_a_1+lane_a_2`、`lane_b_0+lane_b_1+lane_b_2`、
`merge+expand+finalize`——**在追踪文件里看到带加号的节点名，就是融合节点**。

所以「融合开」的运行里，每个 chain_qmsum 会话有 3 次融合节点执行，20 个会话共 60 次。
这是判断融合开关是否真的生效的直接证据。

## 6. 一次运行产出哪些文件

```
a1v2__burst__sagepilot/r1/
├── run_manifest.json        这次运行用了什么（自变量的落盘记录）
├── run_summary.json         汇总统计
├── workflow_trace.jsonl     逐事件追踪，一行一个事件
├── moa_gsm8k/session_results.jsonl      该工作流每个会话的最终输出
├── repair_mbpp/session_results.jsonl
└── chain_qmsum/session_results.jsonl
```

**一次运行是否合格，只看一个条件：`run_summary.json` 存在，且
`completed_session_count == 60` 且 `failed_session_count == 0`。** 不满足就是废运行，
不能进表。运行失败时不会生成 `run_summary.json`，但 `workflow_trace.jsonl` 会留下来。

### run_manifest.json —— 别靠目录名认自变量，靠这个

由 `src/workflow/master.py::write_run_manifest` 在运行开始时写。字段：

| 字段 | 内容 |
|---|---|
| `run_id` | 第几次重复，如 `"r1"` |
| `started_at` | 开始时刻 |
| `git` | 代码版本（提交号 + 是否有未提交改动） |
| `scheduler_config` | 完整的调度器配置，**含实际发现到的显卡清单**（显卡环境的真凭实据） |
| `predictions` | 预测数据文件路径 + 内容哈希 |
| `workflow_files` | 三个工作流配置的路径 + 内容哈希 |
| `fuse_nodes` | 节点融合是否开启 |
| `experiment_config` | 到达配置的路径 + 哈希 |
| `experiment` | 到达配置的完整内容（含 `arrival_seed`） |

**分析时应当从这里读自变量，不要解析目录名。** 目录名可能被改，清单里的哈希不会骗人。

### run_summary.json 的主要字段

| 字段 | 含义 |
|---|---|
| `submitted_session_count` / `completed_session_count` / `failed_session_count` | 会话数，正常应是 60 / 60 / 0 |
| `session_latency_sec` | 会话完成时间的中位数、95 分位、最大值 |
| `model_load_count` / `model_evict_count` | 模型被读进显卡、移出显卡的次数 |
| `model_reuse_count` | 请求直接用上已在卡上的模型的次数 |
| `scale_out_count` | 给某模型多开一个实例的次数 |
| `drain_count` | 把某个实例标记为"停止接新活"的次数 |
| `active_gpu_seconds` | 显卡真正在生成内容的时间总和 |
| `resident_gpu_seconds` | 模型待在显卡上的时间总和（含空转） |
| `request_infeasible_count` / `oom_count` | 请求放不下、显存溢出的次数，正常应为 0 |
| `placement_count` | 做了多少次放置决策 |
| `per_node_task_counts` | 每个节点完成/失败了多少任务 |

注意 `run_summary.json` 里**没有**批次完成时间（从开始到最后一个会话完成）。那个要从追踪
文件算，或者用 `src/experiment/workflow/analysis.py::summarize_trial`。

### workflow_trace.jsonl 怎么读

一行一个 JSON 对象。公共字段：`event_type`、`ts`（Unix 时间戳，秒）、`event_seq`（写入序号）、
以及按需出现的 `session_id` / `node_id` / `workflow_name` / `model_key` / `replica_id` /
`accelerator_id` / `gpu_kind` / `acquire_id`，外加一个 `payload` 放事件专属内容。

**重要陷阱：`ts` 不是单调递增的。** 有些事件的时间戳来自它记录的那件事的发生时刻，而不是
写入时刻。**要按时间排序必须显式对 `ts` 排序，不能依赖文件里的行顺序。**

常见事件类型：

| 事件 | 什么时候发生 |
|---|---|
| `run_started` / `run_finished` | 整次运行的首尾，各 1 条 |
| `session_submitted` / `session_completed` / `session_failed` | 会话投入、完成、失败；`payload.latency_sec` 是该会话耗时 |
| `task_started` / `task_completed` / `task_failed` | 单个节点任务的状态变化 |
| `task_execution_finished` | 一次实际执行结束；`payload` 里有 `started_at`/`finished_at`/`output_tokens`/`status`；**`payload.stages` 存在就说明这是融合节点** |
| `acquire_requested` / `acquire_granted` / `acquire_cancelled` | 请求申请显卡、拿到显卡。两者时间戳相减就是**等待时长** |
| `placement_selected` | 放置决策的细节，含用到的预测值 |
| `model_load_started` / `model_load_finished` | 模型开始/结束读入显卡；`payload.model_name` 是模型名，`payload.owner_workflow` 是触发这次装载的工作流 |
| `model_evicted` | 模型被移出显卡 |
| `model_reused` | 请求直接用上了已在卡上的模型 |
| `scheduler_decision` | 调度器的动作；看 `payload.action_type`（`load_replica` / `evict_replica` / `drain_replica` / `grant`）和 `payload.reason` |
| `prefetch_started` / `prefetch_skipped` | 预取发生 / 被跳过；跳过时 `payload.reason` 说明原因 |
| `scheduler_tick` | 每次调度循环；`payload` 里有当前挂起请求数、临近就绪数、本轮动作数 |

`model_key` 是整个模型部署配置的哈希，不同运行之间**不可比**（同一个模型在两次运行里哈希相同，
但你没法直接看出它是哪个模型）。要认模型请用 `model_load_started` 事件的
`payload.model_name` 建一个 `model_key → 模型名` 的对照表。

### 判断某个开关是否真的生效

| 想验证 | 看什么 |
|---|---|
| 节点融合开着 | `task_execution_finished` 里 `payload.stages` 非空的有 60 次 |
| 节点融合关着 | 上述计数为 0 |
| 预取关着 | 没有 `prefetch_started`；`prefetch_skipped` 的 `reason` 全是 `"disabled"` |
| 预取开着 | 从不出现 `reason == "disabled"` |
| 跨工作流生命周期关着 | `model_load_started` 的 `owner_workflow` 出现多条工作流；同一 `replica_id` 上相邻的 `acquire_granted` 仍会出现不同 `workflow_name`（副本依然物理共享） |

**不要拿"预取次数大于 0"当验收条件。** 实测在一次性全投的负载下该值就是 0——60 个会话把
5 个模型全顶成常驻，预取无事可做。这是设计行为，预取在调度循环里优先级最低。

## 7. 调度器配置项的含义

`config/workflow/serve/serve_0728/scheduler_*.yaml`，模型定义在
`src/workflow/artifacts.py::SchedulerConfig`。

| 配置项 | 含义 |
|---|---|
| `policy` | 排序策略。`cache` 是本系统；`fifo` 是 Parrot 的先到先服务；`kairos` 是最短剩余关键路径优先 |
| `acquire_timeout_sec` | 一个请求最多等多久拿显卡，超了就抛超时、会话失败。**全部方案统一 1800 秒** |
| `elastic_replicas` | 是否允许给一个模型多开实例。只有 `cache` 策略能开 |
| `max_replicas_per_model` | 一个模型最多几个实例，本次为 2 |
| `scale_out_margin_sec` | 多开实例的收益门槛，本次为 10 秒 |
| `scale_in_idle_sec` | 实例连续空闲多久才算"多余的"，本次为 60 秒 |
| `enable_prefetch` | 是否允许在任务真正就绪前提前把模型读进显卡 |
| `cross_workflow_lifecycle` | 模型生命周期是全局统一决策，还是每条工作流各自决策 |
| `min_residency_load_multiple` | **防抖**：一个实例占住卡之后，至少要维持"它自己装载耗时 × 这个倍数"那么久才允许被移走。本次为 1.0 |

**`acquire_timeout_sec` 不要单独改。** 它同时被拿去当"老化阈值"用——调度器里两处排序逻辑
把「等待超过它的一半」当作请求已经饿了的判据。改这个值等于同时改了调度行为，全部运行不可比。

`min_residency_load_multiple` 只在 `sagepilot`、`noprefetch`、`noxwf` 三份配置里设为 1.0
（`analytical`、`gbdt`、`nofuse` 复用 `scheduler_sagepilot.yaml`，所以也是 1.0）。
两个排序基线不设，因为它们的策略本就不允许多开实例。

## 8. 当前状态与已知缺陷

### 完成度（截至本文写作时）

| 显卡环境 | 合格运行 | 说明 |
|---|---|---|
| `a1v2`（3 张卡） | **96 / 96** | 四档到达全满，零重试，数据干净 |
| `a1v3`（4 张卡） | **96 / 96** | 同上 |
| `a1v4`（5 张卡） | 48 / 96 | 大量运行因超时作废，见下 |

### a1v4 上有一个会导致死锁的代码缺陷

**留存的 35 次失败运行里，34 次是同一个形态。** 这是 `src/workflow/scheduler.py` 里的
既有缺陷，不是本次实验引入的。

调度器有个动作叫「标记停止接活」（追踪里是 `action_type == "drain_replica"`）：某模型排着队
却拿不到卡、又找不到能合法移走的实例时，挑一个"多余的"实例贴标记，让它做完手上的活就把卡
让出来。前提是那个模型当时有两个实例。

三处判断对这个标记态度不一致：

- **能不能派活给它** —— 看标记，贴了就不派。
- **能不能把它移出显卡** —— 看标记，贴了就算多余的，可以移。
- **这个模型算不算已经在卡上** —— **不看标记。**

而且这个标记贴上去**没有任何地方会清除**。

于是：贴了标记的实例的兄弟实例被正常移走后，它成了该模型唯一的实例。此时该模型的请求进来，
调度器认为"模型已在卡上"就把请求原地搁置，不装载也不腾卡；再问"派活给它"，又因为标记被拒。
不派活、不装载、不腾卡，请求挂到 1800 秒超时为止。

实测印证：一次失败运行里最后一次派活之后**空转 1543 秒**，2542 次调度循环零动作，而当时
5 张卡上正好是 5 个模型各一个实例，分配完全正确。

**为什么只有 a1v4 中招**：这个动作要发生，前提是某模型已有两个实例，而这要求卡有富余。
卡越多越容易触发。实测三个环境的排空次数与卡住次数：

| 显卡环境 | 排空决策次数 | 其中永久占卡 |
|---|---|---|
| `a1v2` | 24 | **0** |
| `a1v3` | 106 | **0** |
| `a1v4` | 179 | **37** |

**为什么装载估计短的方案中招率高**：多开实例的收益计算要减去装载耗时，估计越短越显得划算，
触发越频繁。失败率与第 4 节那张装载估计表完全单调相关：

| 方案 | 预测的 4B 装载耗时 | a1v4 上的失败率 |
|---|---|---|
| `parrot` / `kairos` | 164.8 秒 | **0%**（策略不允许多开实例，天然免疫） |
| `gbdt` | 164.8 秒 | 11% |
| `noxwf` / `sagepilot` / `noprefetch` / `nofuse` | 45.8 秒 | 33–83% |
| `analytical` | 0.3 秒 | 78% |

**这意味着 a1v4 的数据有系统性偏差**：跑得出来的都是不触发多开实例的方案，缺的都是会触发的
方案。分析 a1v4 时必须考虑这一点，不能把它当成随机缺失。

修法是让第三处判断也看那个标记，属于修正三处判断之间的不一致。**改了就是改了被测系统，
已有的运行全部不可比。截至本文，尚未修。**

## 10. 统一模型加载后的离线反事实调整

本节只说明实验完成后怎样消除不同方案所用模型加载时间不一致的影响。它不解释预测数据如何生成，
也不负责挑选或排除某一轮结果；人工筛查属于第 11 节。

调整只覆盖 `a1v2` 和 `a1v3`。每个环境包含 4 种到达方式、8 个方案和 3 次重复，因此应得到
**2 × 4 × 8 × 3 = 192 次离线回放**。`a1v4` 不进入这一步。

这不是在原 makespan 上加减一段加载时间。统一加载时间会改变是否多开实例、何时预取、移走哪个模型、
请求先后顺序和模型加载次数，这些决定相互影响，不能用
`原结果 - 原加载时间 + 统一加载时间` 线性换算。正确做法是从原 trace 固定工作量，再用原调度配置做
离散事件回放，同时统一调度器看到的加载估计和回放时钟实际消耗的加载时间。

### 10.1 输入范围和合格条件

对每个 `a1v2`、`a1v3` 目录，先按第 6 节的条件检查运行：

- `run_summary.json` 存在；
- `completed_session_count == 60`；
- `failed_session_count == 0`；
- `workflow_trace.jsonl` 存在且包含唯一的 `run_started` 和 `run_finished`；
- 提交和完成的 session 集合一致，所有 acquire 都有 request、grant 和成功执行结果。

两个显卡环境各自应有 96 份合格 trace。方案身份、调度器配置、预测文件、融合开关和显卡清单都从
`run_manifest.json` 读取，不靠目录名推断。任何一项不满足时停止调整，不把失败 trace 或缺项 trace
混入中位数。

### 10.2 统一加载表

后续回放直接使用下表，单位均为秒。本节不再重新估计这些数值。`predicted` 是调度器做决策时看到的
加载时间，`cold` 和 `warm` 分别是模拟 GPU 第一次加载模型和后续加载模型时推进的实际时间。

| `a1v3` | Qwen3-0.6B | V100 | 35.522978088 | 35.684121294 | 35.522978088 |

本次调整只接受表中的五种模型—GPU 配对。同一个显卡环境内，八个方案、四种到达方式和三次重复
必须使用完全相同的表。若回放尝试加载表外配对，应立即报错，不为它补默认值，也不借用另一个模型、
另一个 GPU 或另一个显卡环境的数值。

统一必须同时作用于两个位置：

- 将每个方案预测数据中的 `predicted_load_sec` 替换为统一预测加载时间，使调度器基于相同的加载
  代价做扩副本、预取、驻留和回收决策；
- 将离线 workload 的 cold-load 和 warm-load 时长替换为统一冷、热加载时间，使模拟时钟为相同的
  实际加载动作支付相同时间。

只统一加载时间。各方案原有的运行时间预测、峰值显存预测和其他预测字段保持不变，否则调整会同时
改变预测算法这个自变量。

### 10.3 为每个实验格固定回放 workload

一个回放实验格由 `(显卡环境, 到达方式, 重复轮次)` 唯一确定。例如
`(a1v3, poisson_r025, r2)` 只使用所有方案的 `r2` trace，不把 `r1`、`r2`、`r3` 先混成一份
workload。三轮回放完成后再汇总结果。

融合和未融合 trace 的节点身份不同，不能直接放在同一个集合里取中位数，因此每个实验格建立两份
固定 workload：

| Workload 组 | 提供样本的方案 | 使用的图 |
|---|---|---|
| 融合组 | `analytical`、`gbdt`、`sagepilot`、`noprefetch`、`noxwf` | 对原始 YAML 执行与在线实验相同的节点融合 |
| 未融合组 | `parrot`、`kairos`、`nofuse` | 原始 YAML，不融合节点 |

同一组内，各 source trace 必须具有完全相同的 session 集合、session 到 workflow 的映射和任务
身份集合，否则停止。固定 workload 按以下规则构造：

- 对每个 session，先计算 `session_submitted.ts - run_started.ts`，再在同组 source trace 间取
  中位数；最后让最早的 session 从 0 秒到达，其余 session 保持相对间隔；
- 对 agent 节点的 input tokens 和 output tokens，在同一 `(session_id, node_id)` 上取中位数；
- 对 agent 执行耗时建立四层中位数表：精确的 `(session, node, admitted batch size)`、
  `(workflow, node, admitted batch size)`、`(model, gpu kind, admitted batch size)`，以及不区分 batch
  的单任务耗时；回放按这个顺序选择最具体的可用项；
- 对函数节点，在同一 `(session_id, node_id)` 上取执行耗时中位数；
- 对模型移出显卡的耗时，按 `gpu_kind` 汇总后取中位数；
- workload 构造阶段从 source trace 得到的加载时间不用作最终加载时间，必须由第 10.2 节的统一冷、热
  加载表覆盖。

融合组的 YAML 必须先执行图融合，再与 trace 中带加号的节点名匹配。不能把
`lane_a_0+lane_a_1+lane_a_2` 当作原 YAML 中天然存在的节点，也不能将它拆开后与未融合组共同取
任务耗时中位数。

### 10.4 按原配置回放八个方案

对每个实验格，融合组的五个方案共用同一份融合 workload，未融合组的三个方案共用同一份未融合
workload。随后分别回放八个方案。除了第 10.2 节规定的加载时间外，每个方案都保留
`run_manifest.json` 记录的原配置：

- `parrot` 保留 FIFO 排序、关闭融合和关闭弹性副本；
- `kairos` 保留剩余工作优先排序、关闭融合和关闭弹性副本；
- `analytical`、`gbdt`、`sagepilot` 保留各自的预测策略，并开启融合、预取、跨工作流生命周期管理
  和弹性副本；
- `nofuse` 只关闭融合；
- `noprefetch` 只关闭预取；
- `noxwf` 只关闭跨工作流生命周期管理。

显卡槽位严格按实验格设置：`a1v2` 使用 1 个 A100 槽和 2 个 V100 槽，`a1v3` 使用 1 个 A100
槽和 3 个 V100 槽。`acquire_timeout_sec`、副本上限、扩缩容阈值、防抖时间以及其余调度参数都沿用
原 manifest，不能为避免回放等待而单独改大或改小。

回放时，调度器每次选择加载一个模型，都用统一预测加载时间做决策；动作真正执行时，根据该模拟 GPU
此前是否完成过加载，分别推进统一冷加载时间或统一热加载时间。统一的是**每次同类加载的代价**，
不是强行让各方案产生相同的加载次数。加载次数不同本身就是调度决策的结果，必须保留。

### 10.5 指标和重复实验的汇总

每次回放必须完成 60 个 session。调整后的指标统一按模拟时间计算：

- `makespan`：最后一个 session 的完成时间减去第一个 session 的到达时间；
- session latency：每个 session 的完成时间减去它自己的到达时间；
- `p50`、`p95`：将 60 个 session latency 升序排列，取下标
  `ceil(q × 60) - 1`，其中 `q` 分别为 0.50 和 0.95；
- 同时保留 mean latency、模型加载次数、loading GPU seconds 和 idle-resident GPU seconds，便于解释
  性能差异。

对每个 `(显卡环境, 到达方式, 方案)`，先分别输出 `r1`、`r2`、`r3`，再计算三次的算术平均值。
本节不根据结果好坏选择某一轮，也不在回放前对三轮原 trace 取中位数。若第 11 节之后规定人工筛查，
应当在 192 次回放全部完成后作用于回放结果，不能反过来改变统一加载表或固定 workload。

Poisson 场景的 makespan 包含会话到达跨度，因此只能在同一显卡环境、同一到达方式内比较方案；不能
用 `poisson_r0125` 的 makespan 与 `burst` 或另一个速率直接比较吞吐。

### 10.6 复现时必须通过的检查

调整完成后至少检查以下不变量：

- 共得到 192 份结果，每份都完成 60 个 session，没有失败、超时或未处理任务；
- 同一显卡环境内，八个方案的统一预测、冷加载和热加载表逐项相同；
- 每个 `(显卡环境, 到达方式, 重复轮次)` 内，融合组五个方案的 workload 摘要完全相同，未融合组
  三个方案的 workload 摘要完全相同；
- 每个方案的排序策略、融合、预取、跨工作流生命周期和弹性副本开关与 manifest 一致；
- 融合组每个 QMSum session 只有 3 个融合 agent 节点，未融合组仍是 9 个 agent 节点；
- 任意缺失的加载表项、session、task 或模型映射都必须显式报错，不能跳过后继续汇总；
- 可以先独立回放 `a1v3 + burst`，再在完整矩阵中重复一次；两次得到的每项结果应完全一致，以确认
  回放没有依赖遍历顺序或残留状态。

最终结果应标为 **trace-derived counterfactual replay**。它回答的是“如果所有方案在同一加载代价下
执行这些固定工作，结果会怎样”，不是新的集群实测 wall-clock 结果，也不应覆盖
`output/serve_0728` 中的原始 trace。
