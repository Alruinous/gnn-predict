# 3w × pool 紧度实验结果分析（2026-07-26）

数据：`output/serve_0726/{3w_a1v2,3w_a1v3,3w_a1v4}`，12 个 run，对应
`docs/workflow/experiment_runbook_pool_tightness_20260725.md` 的 Phase 1 + Phase 2。

**结论先行：pool 紧度曲线的"形状"被复现了（N=4 时四臂收敛到无差别），但"符号"是反的——
`cache`（SagePilot 全量方法）在 N=2 与 N=3 都是四臂中最差的。** 现有数据不支持把 §5.3 写成
SagePilot 胜出。根因已定位到准入侧的 batch 欠填充，见 §4。

## 3. 三项机制功能是否体现

工作负载解析出 5 个 `model_key`（与 runbook 一致）：

| key | 模型 | acquire 占比 | 落卡 |
|---|---|---|---|
| `60efeb0b` | Qwen3-4B @8192 | 41.2%（qmsum chunk×6 + mbpp reviewer） | V100 |
| `4acb3d08` | Qwen3-4B @1024 | 29.4%（gsm8k solve×5） | V100 |
| `400403a0` | Qwen3-14B @2048 | 11.8%（mbpp coder + gsm8k refine） | **A100 独占** |
| `b3dd5e28` | Qwen3-8B @4096 | 11.8%（qmsum merge + mbpp repair） | V100 |
| `e219b7be` | Qwen3-1.7B @8192 | 5.9%（mbpp diagnoser） | V100 |

Qwen3-4B 两个 key 合计 70.6% 需求，与 runbook 的 71% 吻合。

### (a) 模型复用 —— 体现了，但不区分策略

680 次 placement 中复用次数：N=2 为 641–655、N=3 为 640–645、N=4 为 675。
**复用率 94–99%，fifo 也一样高**。复用率本身不是一个能区分策略的指标，论文里不要用它做卖点；
真正的区分量是**加载次数**。

### (b) 驱逐 —— 体现了，但方向不稳定

每次暖机后的加载都伴随一次驱逐（loads == evictions，逐 run 成立），说明驱逐路径确实在工作。
但 reuse-distance 驱逐相对 LRU 的效果**随 pool 紧度反号**：

| pool | cache loads | fifo loads | kairos loads |
|---|---|---|---|
| N=2 | **39** | 29 | **25** |
| N=3 | **35** | 40 | 37 |
| N=4 | 5 | 5 | 5 |

N=3（有余量）时 reuse-distance 驱逐**少加载 5 次**，符合设计意图；
N=2（最紧、也是最该起作用的场景）时反而**多加载 10–14 次**，抖动比 LRU 更严重。
对应加载 GPU-秒：N=2 cache 2352s vs kairos 1693s，多烧 **659 GPU-秒**。

### (c) 预加载 —— **基本没有生效**

| run | prefetch 触发 | prefetch 跳过 | 触发率 | 浪费的 prefetch |
|---|---|---|---|---|
| a1v2_cache | **0** | 117 | 0% | 0 |
| a1v3_cache | 4 | 137 | 2.8% | 0 |
| a1v4_cache | 1 | 131 | 0.8% | 0 |
| a1v3_gbdt | 6 | 147 | 3.9% | 0 |

a1v2_cache 全部 39 次加载的 `reason` 都是 `ready_load`，**没有一次是 prefetch**。
跳过原因分布（a1v2_cache）：`capacity_unavailable` 72、`replica_resident` 22、
`already_loading` 17、`ready_work_priority` 6。

主因是 **`capacity_unavailable`**：每张 GPU 都已驻留且在忙，prefetch 永远抢不到空位。
"0 次浪费的 prefetch"不是精准，是因为几乎没有 prefetch 发生。
**当前实现下 prefetch 这条机制在论文里没有实证支撑。**

## 4. 根因：准入侧的 batch 欠填充

880 个 task 的执行时长总和在 12 个 run 里完全一致（3939–4117s），但**每个副本上这些区间的并集**
（`active_gpu_seconds`）差别很大。两者之比就是副本上的**实际并发度**，上限由
`max_num_seqs=3` 给定：

| run | 执行时长总和 | 并集(active) | 并发度 | 占 max_num_seqs=3 |
|---|---|---|---|---|
| a1v3_cache | 3855.9 | 2093.7 | **1.84** | **61%** |
| a1v3_fifo | 4000.3 | 1716.8 | 2.33 | 78% |
| a1v3_kairos | 3983.9 | 1714.5 | 2.32 | 77% |
| a1v3_gbdt | 3938.6 | 1825.6 | 2.16 | 72% |
| a1v2_cache | 3990.3 | 1856.6 | 2.15 | 72% |
| a1v2_fifo | 4026.4 | 1793.1 | 2.25 | 75% |
| a1v2_kairos | 4041.3 | 1739.9 | 2.32 | 77% |
| a1v4（四臂） | ~3920 | ~1910 | 2.04–2.07 | 68–69% |

**cache 把已经驻留的副本的 batch 槽位空着跑。** N=3 上它的 batch 占用率 61% vs fifo 78%——
副本已经付过加载代价了，空着的 batch 槽位是纯损失。这解释了为什么 cache 在
**加载次数更少（35 vs 40）的情况下延迟反而差 2.18×**：省下来的加载时间，被欠填充的解码吞吐
全部吐了回去还有余。

acquire 等待的拆解与此一致（自己的模型在加载 / 头阻塞在别的 key 的加载后 / 其他）：

| run | 总等待 | 自身加载 | 头阻塞 | 其他 | 头阻塞占比 |
|---|---|---|---|---|---|
| a1v3_cache | 32898 | 10444 | 15105 | 7349 | **45.9%** |
| a1v3_fifo | 22977 | 11401 | 6909 | 4668 | 30.1% |
| a1v3_kairos | 23491 | 12092 | 7044 | 4354 | 30.0% |
| a1v2_cache | 47726 | 20426 | 10333 | 16967 | 21.7% |
| a1v2_fifo | 43679 | 16355 | 11027 | 16298 | 25.2% |
| a1v2_kairos | 35301 | 13033 | 10892 | 11376 | 30.9% |

cache 臂的等待里，**头阻塞（卡在别的 key 的加载后面）反而是最大的一项**，比 fifo 高 2.2×。

**注意因果链尚未坐实。** 代码里 cache 策略并**没有**在 grant 上做 ETA 门控——
`_order_pending`（`src/workflow/scheduler.py:1154`）用的是"已驻留优先 + 同类内最老优先 + 老化"，
`_order_by_load_yield`（同文件 `:1718`）只在**必须付加载代价时**按 demand/load_sec 重排。
两者都是意在提升局部性的设计。可测量的事实是并发度 1.84 vs 2.33 与头阻塞 45.9% vs 30.1%；
"哪一段代码把 batch 槽位空出来了"需要专门的对照实验（逐个关掉 `_order_pending` 的驻留优先、
`_order_by_load_yield`、prefetch）来定位，不能只靠 trace 反推。

一个与数据一致的解释是：cache 让热点 key 驻留更久（N=3 上 `60efeb0b` 驻留 1232s / 5 个副本，
fifo 为 999s / 9 个副本），同样的工作量摊在更长的驻留窗口里，单位时间内同时在跑的请求就更少，
并集因此变大。但这只是假说。

会话重排序不是原因：N=3 的完成序 Spearman ρ 为 cache 0.983 / fifo 0.994，逆序对 5.1% vs 2.9%，
量级远不足以解释 2.18×。

**pool sizing 指标**而非策略指标，否则会自相矛盾。

## 5b. 与历史 cohort 的横向对照：cache 在别处是赢的

`output/serve_fix_20260725` 与 `output/serve_0724` 里 cache 都胜出，所以 serve_0726 是异常点。
把三个 cohort 拉平对比后，**差异不在代码，在工作负载解析出的 model_key 集合与实际到达速率**：

| cohort | 代码 | key 数 | 4B 形态 | V100 key / 槽位 | 到达跨度 | cache mean | fifo mean |
|---|---|---|---|---|---|---|---|
| serve_0724 6w r150 | 修复前 | 6 | 拆分 | 4 / 2 | 2114s | **287.1** | 344.3 |
| serve_fix 6w r150 | 修复后 | **4** | **合并** | **3 / 2** | 2114s | **407.7** | 703.4 |
| serve_0726 3w a1v2 | 修复后 | 5 | 拆分 | 4 / 2 | **1545s** | 627.5 | **424.6** |

三条实锤：

1. **serve_fix 的 6w 只解析出 4 个 key，gsm8k 的 solve 节点落在 `60efeb0b`（4B@8192）上**，
   与 qmsum chunk 同一个 key，单键独占 **70.6%** 的需求。而 main 的 `gsm8k1.yaml` 里 solve 是
   `max_model_len: 1024`，解析成独立的 `4acb3d08`。所以 serve_fix 跑的是**4B 合并**的配置
   （运行时的本地改动，main 与 worktree 分支现在都不是这个形态）。
   → **`becb1c5` 提交信息里"cache 相对 fifo mean -42%"是在这个 4-key 合并配置上测的，
   main 的配置复现不出来。**

2. **runbook §3.3 的"合并 4B 会让 mean 从 287s 恶化到 408s"是错误归因。**
   287s = `serve_0724/6w_poisson/hetero_r150_cache_a1v2`（**修复前**代码、6 key、拆分）；
   408s = `serve_fix`（**修复后**代码、4 key、合并）。两者**同时**差了代码和 key 配置，
   不能把差值算到 key 合并头上。而且 408s 那次 cache 领先 fifo **42%**，287s 那次只领先 17%。

3. **serve_0726 的实际到达速率比另外两个 cohort 高 37%。** 两份配置名义都是 0.075 session/s，
   但 seed 42 下 6w（6 条流 × 20）的实际跨度是 2114s、3w（3 条流 × 40）是 1545s。
   runbook §5 "与 6w r150 同速率同总量，因此两者可直接对照"这句话**不成立**。
   serve_fix 的 cache makespan 2151.9s ≈ 到达跨度 2114s（刚好跟得上）；
   serve_0726 的 cache makespan 2204.5s vs 跨度 1545s（**大幅过载**）。

**但这三条无法互相区分。** 排成 2×2 会发现只有一个格子有数据：

| | 跨度 2114s | 跨度 1545s |
|---|---|---|
| 修复前 + 拆分 key | serve_0724：cache 赢 | — |
| 修复后 + 合并 key | serve_fix：cache 赢 | — |
| **修复后 + 拆分 key** | **缺** | serve_0726：cache 输 |

serve_0726 同时是"唯一的修复后+拆分 key"和"唯一的高到达速率"。
**决定性的单个补跑：用当前 main 跑 `replay_6w_poisson_r150`（跨度 2114s、拆分 key）的
cache 与 fifo 两臂。** 若 cache 重新领先 → 病因是过载（cache 在饱和点以上崩溃）；
若仍落后 → 病因是 4B 拆成两个 key 后 cache 的驻留优先排序失效。

**顺带纠正一个读法**：`3w_a1v4` 不能算"cache 正常工作"。那里 5 个 key 恰好 1 个占 A100、
4 个占满 4 张 V100，**全部常驻、零驱逐**，四臂 mean 44.5–47.3s 且 **cache（46.1）略差于
fifo（44.5）**。它证明的是工作集装得下时策略无从区分，不是 cache 生效。

## 6. 对 §5.2 / §5.3 的影响

**可以直接写的：**

- N=4 收敛结果：界定适用范围（"收益仅存在于模型工作集装不下时"），比回避更有说服力。
- kairos 的尾部/公平性代价：mean 最优但 p95 最差、MBPP 长链被饿死。
- 系统是 load-bound 的刻画：N=2 上 acquire 总等待 35–48k 秒 vs 执行 4k 秒。

**不能写的：**

- 任何形式的"SagePilot 胜出"。当前数据是 cache 在两个紧 pool 上全面落后。
- prefetch 的收益（触发率 0–3.9%，无实证）。
- `05-evaluation.tex:41` 的 "error bars report 95% CIs across independent runs" —— 单种子、
  无 run 间方差，必须改成会话级 bootstrap 口径（runbook §8 已指出）。

**需要先修再重跑的：**

1. **先跑 §5b 的判别实验**（最高优先级，2 个 run）：当前 main + `replay_6w_poisson_r150` +
   1×A100+2×V100，只跑 cache 与 fifo。这一个对照就能把"过载"与"4B 拆键"两个病因分开，
   在此之前不要改调度器代码。
2. **再定位 batch 欠填充**：若确认是拆键问题，逐个关掉 cache 的三个组件
   （`_order_pending` 的驻留优先、`_order_by_load_yield`、prefetch）各跑一个 N=3 run，
   看哪一个把并发度从 2.33 压到 1.84。
3. **prefetch 的容量来源**：`capacity_unavailable` 占跳过原因的 62%，需要投机驱逐或预留槽位，
   否则 prefetch 在紧 pool 下永远不会触发。
4. **重跑 `p1_a1v2_gbdt`**（当前跑在 4 张卡上）。
5. reuse-distance 驱逐在 N=2 反而比 LRU 多 10–14 次加载，需单独复查 victim 选择。
6. **修正 runbook**：§1(c)（3w 与 6w 模型压力相同）、§3.3（合并 4B 的归因）、
   §5（同速率同总量）三处与实测不符，改完再作为复现依据。
