# Workflow Proxy 数据集生成方案 20260613

## 目标

本文记录基于 Murakkab 论文公开 benchmark 场景生成 workflow proxy 数据集的方案。

数据集目标不是训练 GNN。它只提供一组稳定、可复现、任务来源合理的 workflow YAML，用于验证当前项目中 GNN-aware 工具节点调度是否有效。

GNN 仍只使用项目已有模型 profile 数据训练。workflow proxy 数据集只描述:

- agent workflow 的 DAG 结构。
- 本地 tool 节点的模型任务、模型名、构造参数和 runtime。
- 每个 workflow 的来源场景、结构标签和工具类型统计。

## 核心边界

主 agent 使用外部 LLM provider，不使用项目内变体模型。GNN 不预测 agent 节点，也不负责 agent 的资源调度。

| 节点类型 | 执行方 | GNN 是否预测 | 是否参与本地 GPU 调度 |
| --- | --- | --- | --- |
| `agent` / `planner` | 外部 LLM provider | 否 | 否 |
| `tool` | 本地部署小模型 | 是 | 是 |
| `input` / `output` | workflow 边界 | 否 | 否 |

生成的数据集中，只有 `tool` 节点映射到项目支持的变体模型。`agent` 节点只表达工具选择和控制流。

## 数据集目录

采用单目录结构，不再拆分 `train`、`dev`、`eval`、`stress` 或按负载压力分类。

```text
data/workflows/proxy_20260613/
  workflow_000001.yaml
  workflow_000002.yaml
  workflow_000003.yaml
  ...
  manifest.json
  distribution.md
```

这样做的原因:

- workflow YAML 不是 GNN 训练样本，不能叫 train split。
- 当前 scheduler 没有需要专门调参的数据集。
- 负载压力不是目录分类，只是 workflow 的一个可统计属性。
- 后续如需筛选场景，直接按 `manifest.json` 中的元数据过滤。

## 数据来源与转写方式

论文使用 VideoMME、HumanEval 和 MATH 作为任务质量 benchmark，也使用 Azure LLM serving traces 模拟请求负载。当前项目不直接使用这些原始样本或 trace。

本方案只从公开 benchmark 总结工具节点场景，再替换成项目内支持的本地模型变体。

| benchmark 场景 | 原始工具类型 | 项目内 tool 替代 |
| --- | --- | --- |
| VideoMME / Video Q&A | 场景理解、目标检测、转写文本理解、多模态回答 | 图像分类、目标检测、文本分类、生成 |
| HumanEval / Code Generation | 需求理解、代码生成、测试生成、结果判断 | 文本分类、代码草稿生成、测试草稿生成、摘要 |
| MATH / Math Q&A | 题型分类、解题、反思验证、最终答案 | 文本分类、解题生成、验证生成、答案生成 |

不纳入 GNN 的部分:

- 真实视频解码。
- Python 解释器执行。
- 外部 ASR。
- 外部 LLM provider。
- benchmark 答案正确率。

这些不属于当前项目的本地小模型 GPU 负载。

## 依据层级

公开 benchmark 和系统评测基准只能提供部分依据，不能提供 workflow proxy 中每个模型族的精确出现比例。

| 依据来源 | 能支撑什么 | 不能支撑什么 |
| --- | --- | --- |
| VideoMME | 视频问答需要视觉理解、音频/字幕信息、长视频理解和问答汇总。论文说明数据覆盖 6 个领域、30 个视频类型，并包含字幕和音频信息。 | 不能说明本项目应该用多少 `resnet`、`yolov5` 或 `qwen3` 节点。 |
| HumanEval | 代码生成 benchmark 以 prompt completion 和单元测试评估功能正确性，能支撑代码草稿、测试生成和结果判断这类工具角色。 | 不能说明代码 workflow 中 `qwen3` 与 `t5` 的比例。 |
| MATH | 数学题包含完整 step-by-step solution，能支撑题型分类、解题、反思验证和最终答案生成。 | 不能说明数学 workflow 中每种生成模型的比例。 |
| MLPerf Inference | 系统评测通常按代表性任务选择模型和数据集，例如图像分类、目标检测、语言、推荐等任务，而不是让所有模型平均出现。 | 不能直接给出本项目 workflow proxy 的模型采样比例。 |
| 项目 profile / monitor 配置 | 能说明哪些模型族已经有或计划有系统 profile 数据，哪些模型更适合进入 GNN 调度评估。 | 不能单独决定 workflow proxy 必须使用哪些模型。 |

因此，下文所有比例都不是论文统计出的经验分布，而是首版工程配额。它们用于防止生成数据过度集中在某一种工具或模型上，并保证场景可复现。若后续要求更严格，应把比例改为由真实 workflow 日志或真实工具调用统计推导。

参考资料:

- VideoMME: https://arxiv.org/html/2405.21075v1
- HumanEval: https://github.com/openai/human-eval
- MATH: https://arxiv.org/abs/2103.03874
- MLPerf Inference: https://mlcommons.org/benchmarks/inference-datacenter/

## 首版规模

首版建议生成 120 个 workflow。规模不追求大，重点是覆盖任务结构、工具类型、模型族和 runtime 范围。

| 来源场景 | 占比 | 数量 | 目的 |
| --- | ---: | ---: | --- |
| VideoMME proxy | 40% | 48 | 覆盖视觉分类、检测、文本理解和生成组合 |
| HumanEval proxy | 30% | 36 | 覆盖生成式 decode 和链式工具结构 |
| MATH proxy | 30% | 36 | 覆盖分类、解题、反思和最终答案链路 |

如果后续需要更强统计稳定性，可以保持相同比例扩展到 360 个 workflow，但首版不需要。

## Tool 节点数量分布

| tool 节点数 | 占比 | 数量 |
| --- | ---: | ---: |
| 2 | 20% | 24 |
| 3 | 45% | 54 |
| 4 | 25% | 30 |
| 5 | 10% | 12 |

tool 节点数只表示本地可调度小模型数量。`input`、`planner` 和 `output` 不计入 tool 数量。

## DAG 结构分布

| 结构 | 占比 | 数量 | 适用场景 |
| --- | ---: | ---: | --- |
| `chain` | 45% | 54 | MATH、HumanEval |
| `fan_out` | 35% | 42 | VideoMME 多工具并行 |
| `filter_then_heavy` | 20% | 24 | 快速分类后接重工具复核 |

YAML 中不表达真实条件分支。`filter_then_heavy` 只是用链式 DAG 表示 fast filter 后可能运行 heavier checker 的结构。

## 模型族配额

下面的占比是首版生成配额，不是公开数据集统计结果。

| 工具类型 | 候选模型 | 首版配额 |
| --- | --- | ---: |
| 图像分类 / 场景理解 | `mobilenetv2_100`, `resnet18`, `resnet50`, `densenet121`, `efficientnet`, `vit`, `swin` | 24% |
| 目标检测 | `yolov5n`, `yolov9t`, `yolov11n`; `yolov8n` 仅在 profile 覆盖确认后使用 | 16% |
| 文本分类 / 题型识别 | `gpt2`, `bert` | 22% |
| 草稿生成 / 解题 / 反思 | `qwen3`, `t5` | 28% |
| 汇总 / finalizer | `t5`, `qwen3` | 10% |

模型选择必须限制在当前项目可构建、可导出 ONNX、可被 workflow exporter 转成图数据的范围内。

workflow proxy 数据集不追求让每个模型族平均出现。它不是 GNN 训练集，目标不是覆盖全部模型来提升预测泛化，而是为每个工具角色选择语义合理、项目可运行、profile 覆盖可信的代表模型。

GNN profile 数据集和 workflow proxy 数据集的职责不同:

| 数据集 | 模型覆盖目标 | 用途 |
| --- | --- | --- |
| GNN profile 数据集 | 尽量覆盖更多模型族、算子形态和 runtime | 训练 GNN 预测器，提高系统指标预测泛化 |
| workflow proxy 数据集 | 只选择任务语义合理的本地 tool 模型 | 验证实时调度、选卡、OOM 避免和缓存复用 |

因此，有些模型可以只出现在 GNN profile 数据中，不出现在 workflow proxy 数据集中。例如推荐模型 `deepfm`、`dcn`、`dcnv2`、`edcn` 对 VideoMME、HumanEval、MATH 三类 benchmark proxy 没有自然对应工具，首版不应硬放进去。

同一工具类型下的模型也不平均采样。下面是生成启发式，不是论文给出的经验比例:

| 工具类型 | 子类 | 模型 | 首版配额 |
| --- | --- | --- | ---: |
| 图像分类 | 轻量 CNN | `mobilenetv2_100`, `efficientnet` | 40% |
| 图像分类 | 标准 CNN | `resnet18`, `resnet50`, `densenet121` | 40% |
| 图像分类 | 视觉 Transformer | `vit`, `swin` | 20% |
| 目标检测 | 主线检测模型 | `yolov5n`, `yolov9t`, `yolov11n` | 100% |
| 文本生成 | 本地生成工具 | `qwen3` | 65% |
| 文本生成 | 摘要 / 改写 / finalizer | `t5` | 35% |

`config/monitor/monitor_v100.yaml` 只能说明曾经或计划对某些模型族做监控采集配置，不能直接推出 workflow proxy 数据集必须使用这些模型。`enabled: true` 不等于任务语义适合进入 workflow；`enabled: false` 或未出现在该文件中，也不等于模型永远不可用。最终选择仍以三件事为准:

- 工具场景是否自然需要这种模型。
- 当前项目是否能稳定构建并导出该模型。
- V100/A100 profile 数据是否足够支撑 GNN 预测和调度评估。

例如项目存在 `config/arch/yolov10_variants.yaml`，但 `config/monitor/monitor_v100.yaml` 没有 `yolov10` 目标配置；首版 workflow proxy 不使用 `yolov10`。类似地，`monitor_v100` 中出现的模型也不自动进入 workflow proxy，它们可以继续服务于 GNN profile 数据集的覆盖和泛化。

## Phase 分布

| phase | 占比 | 说明 |
| --- | ---: | --- |
| `inference` | 55% | 分类、检测、判别类工具 |
| `decode` | 35% | 代码、数学解题、摘要、最终回答 |
| `prefill` | 10% | 本地生成工具的输入编码压力 |

`prefill` 不用于主 agent。主 agent 是外部 provider 节点。

视觉工具:

| input shape | 占比 |
| --- | ---: |
| `[1, 3, 224, 224]` | 35% |
| `[2, 3, 224, 224]` | 20% |
| `[4, 3, 224, 224]` | 15% |
| `[1, 3, 640, 640]` | 20% |
| `[2, 3, 640, 640]` | 10% |

文本工具:

| sequence length | 占比 |
| --- | ---: |
| 128 | 25% |
| 256 | 35% |
| 512 | 30% |
| 1024 | 10% |

decode 工具:

| decode max output length | 占比 |
| --- | ---: |
| 32 | 20% |
| 64 | 35% |
| 128 | 30% |
| 256 | 15% |

runtime 范围应尽量落在项目现有 profile 数据覆盖过的 batch、shape、sequence length 和 decode length 附近，避免把 workflow 数据集变成纯 OOD 压测。

## Workflow 模板

### VideoMME proxy

```text
input
  -> planner
  -> scene_classifier
  -> object_detector
  -> transcript_classifier
  -> answer_draft
  -> output
```

可裁剪为 2 到 5 个 tool 节点。典型 tool:

| node | task | 模型 | phase |
| --- | --- | --- | --- |
| `scene_classifier` | `image_classification` | `mobilenetv2_100` / `resnet18` | `inference` |
| `object_detector` | `object_detection` | `yolov5n` / `yolov9t` / `yolov11n` | `inference` |
| `transcript_classifier` | `text_classification` | `gpt2` / `bert` | `inference` |
| `answer_draft` | `text_generation` | `qwen3` / `t5` | `decode` |

### HumanEval proxy

```text
input
  -> planner
  -> prompt_classifier
  -> code_draft
  -> test_draft
  -> verdict_summarizer
  -> output
```

典型 tool:

| node | task | 模型 | phase |
| --- | --- | --- | --- |
| `prompt_classifier` | `text_classification` | `gpt2` / `bert` | `inference` |
| `code_draft` | `text_generation` | `qwen3` | `decode` |
| `test_draft` | `text_generation` | `t5` / `qwen3` | `decode` |
| `verdict_summarizer` | `text_generation` | `t5` / `qwen3` | `decode` |

### MATH proxy

```text
input
  -> planner
  -> problem_classifier
  -> solution_draft
  -> self_reflection
  -> final_answer
  -> output
```

典型 tool:

| node | task | 模型 | phase |
| --- | --- | --- | --- |
| `problem_classifier` | `text_classification` | `gpt2` / `bert` | `inference` |
| `solution_draft` | `text_generation` | `qwen3` | `decode` |
| `self_reflection` | `text_generation` | `qwen3` | `decode` |
| `final_answer` | `text_generation` | `t5` / `qwen3` | `decode` |

## YAML 约定

目标 YAML 中，`planner` 应表达为外部 agent:

```yaml
- name: planner
  type: agent
  task: react_agent
  description: Chooses local tool nodes for the request.
```

`planner` 不应使用项目内变体模型参数。若当前 schema 仍要求 agent 节点填写 `model` 和 `runtime`，应优先调整 schema；不应把占位模型误解释为需要 GNN 调度的 agent 模型。

tool 节点必须包含:

```yaml
- name: scene_classifier
  type: tool
  task: image_classification
  description: Classifies a sampled image frame.
  model:
    name: mobilenetv2_100
    parameters:
      input_channels: 3
      output_classes: 1000
  runtime:
    batch_size: 1
    input_shape: [1, 3, 224, 224]
    phase: inference
```

YAML 不保存:

- ONNX 图特征。
- 真实耗时、显存、功耗。
- 训练开关。
- fake / real dataset 开关。
- benchmark 原始样本。
- benchmark ground truth。
- 调度结果。

## Manifest 字段

`manifest.json` 记录生成过程和每个 workflow 的元数据。分类信息只存在这里，不体现在目录结构中。

示例:

```json
{
  "dataset": {
    "name": "proxy_20260613",
    "workflow_count": 120,
    "root": "data/workflows/proxy_20260613",
    "source": "benchmark-inspired local-tool workflow proxy dataset"
  },
  "workflows": [
    {
      "file": "workflow_000001.yaml",
      "source_benchmark": "VideoMME",
      "proxy_name": "videomme_proxy",
      "structure": "fan_out",
      "tool_count": 4,
      "tool_tasks": [
        "image_classification",
        "object_detection",
        "text_classification",
        "text_generation"
      ],
      "models": [
        "mobilenetv2_100",
        "yolov9t",
        "gpt2",
        "qwen3"
      ],
      "phases": ["inference", "decode"]
    }
  ]
}
```

## Distribution 文档

`distribution.md` 应记录实际生成后的统计结果，而不是只复制目标比例。

至少包含:

- workflow 总数。
- source benchmark 分布。
- tool 节点数量分布。
- DAG 结构分布。
- task 分布。
- 模型族分布。
- phase 分布。
- input shape / sequence length / decode length 分布。
- 与目标比例的偏差。

## 评估用途

该数据集用于调度行为验证，不用于训练。

可用于比较:

- `gnn_aware`
- `static_size`
- `a100_first`
- `v100_only`
- `round_robin`

可观察指标:

- OOM events。
- retry events。
- session makespan。
- tool JCT。
- cold start sec。
- cache hit。
- energy proxy。

## 不做的事

- 不生成 train / dev / eval split。
- 不按负载压力拆目录。
- 不根据 workflow YAML 训练 GNN。
- 不把工具调用概率作为实时调度输入。
- 不把主 agent 当作本地模型节点。
- 不把 `config/monitor` 中出现的模型列表当作 workflow 模型清单。
- 不使用公开 benchmark 的原始样本作为 GNN label。
- 不把 Azure trace 伪装成项目真实 workflow trace。

## 结论

首版 workflow proxy 数据集应是一组平铺的 YAML 文件，加上 `manifest.json` 和 `distribution.md`。

它的严谨性来自真实 benchmark 的任务结构、项目支持的模型族约束、可复现的生成规则和实际分布记录，而不是来自直接复用公开 benchmark 原始数据。
