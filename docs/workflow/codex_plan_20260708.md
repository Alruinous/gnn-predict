# Workflow Runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. This document is written incrementally from confirmed design decisions.

**Goal:** Implement the `dev.md` workflow runtime as a general Ray actor + Ray Queue system for agent workflow execution, model lifecycle management, prediction-aware scheduling, token-budget control, and traceable evaluation.

**Architecture:** Workflow graph execution is owned by this repository's runtime, not by LangGraph. LangChain/LangGraph are used only inside an agent node. The controller and scheduler own DAG state, queues, resource accounting, model instance lifecycle, prediction, prefetch, eviction, and trace recording.

**Tech Stack:** Python 3.12, `uv`, Ray actors, Ray Queue, Pydantic, LangChain/LangGraph inside agent nodes, Hugging Face Transformers, PyTorch, offline PyG graph features, existing workflow ONNX/cache pipeline, offline GNN prediction cache, pytest, Ruff, ty.

## Confirmed Scope

- Current workflow runtime scope is `agent` nodes only.
- Do not model `input` and `output` as runtime nodes in the current implementation. External submission and result collection are controller/runtime boundary operations, not extra Ray Queue hops.
- Do not add `tool` nodes in this stage. Future tool use should be implemented inside LangGraph/LangChain agent logic and exposed to this runtime as part of an agent node.
- Remove `evaluator` as a workflow node concept. Evaluation belongs to experiment or benchmark code as an evaluation function over workflow outputs and dataset references.
- Runtime code must remain generic and must not be hard-coded to QMSum, MBPP, or a fixed agent graph.

## Data Item And Session Semantics

`session_id` identifies exactly one external workflow request. It is similar to a backend request trace id: the internal call chain can fan out, join, load models, retry, and emit many trace events, but all runtime work still belongs to one request. The controller must reject repeated external `submit` calls for the same `session_id`.

`WorkflowDataItem` is the only data-plane transfer unit between agent nodes:

```python
WorkflowDataItem(
    session_id: str,
    source_node: str,
    target_node: str,
    message: AgentState,
)
```

`item_id` is generated by `WorkflowDataItem` and uniquely identifies that data item instance. It is comparable to an instance id or hash code: useful for trace, failure records, retry correlation, and scheduler acquire/release correlation, but not a semantic dependency key.

`source_node` and `target_node` identify the static DAG edge that carries the item. They are required even when all runtime nodes are agents because fan-in, queue metrics, scheduling decisions, and trace records depend on edge-level provenance.

`message` remains `AgentState`. This is intentional: LangGraph/LangChain agents can read prior node outputs, structured results, code execution results, or other agent state without forcing the workflow runtime to model each internal operation as a separate node type.

Session completion is based on the static workflow DAG. Terminal nodes are computed from the DAG as nodes with no successors. A session is complete when every terminal node has produced a result for that `session_id`.

Static fan-in remains source-based: for one target node and one session, each configured upstream source node contributes one item. A repeated item from the same `source_node` to the same `target_node` in the same `session_id` is a program error. This plan does not implement dynamic fan-in where one source emits multiple items to the same target within one session.

## Queues, Fan-Out, Fan-In, And Backpressure

Each agent node owns one bounded input queue. All upstream agent nodes that feed the same target put items into that target node input queue. `output_queues_map[source][target]` is only a controller-side wiring map: it points a source node to the target node input queue and must not create a second physical queue for the same edge.

Fan-out is implemented by broadcasting one result to every static successor. For every successor, the worker creates a new `WorkflowDataItem` with the same `session_id`, a new runtime-generated `item_id`, `source_node` set to the current node, and `target_node` set to that successor.

Fan-in is implemented inside the target worker. The worker stores arrived upstream messages by `session_id` and `source_node`:

```python
store[session_id][source_node] = message
```

When all static dependencies of that target have arrived for the same `session_id`, the worker constructs the agent input in dependency order, runs the node once, and clears that session fan-in store.

Queue capacity is node-level, not edge-level. A node `queue_capacity` config controls the capacity of its input queue shared by all upstream sources. When a downstream input queue is full, upstream `put()` blocks and backpressure propagates naturally through the worker chain.

This plan does not implement per-edge queues or multi-queue select/fairness logic.

## Stop And Drain Semantics

The runtime must support both immediate shutdown and drain shutdown.

`stop_now()` is for development, cleanup, and unrecoverable failures. It stops accepting new submissions, sends STOP control items to workers, and releases model resources as quickly as the current Ray actor state allows. Sessions that have not reached terminal results may remain incomplete.

`drain_and_stop(timeout_sec: float | None = None)` is for experiments and normal benchmark runs. It stops accepting new submissions but continues processing already accepted sessions until every accepted session has either all terminal results or a failure record. After drain completes, the controller stops workers and releases model instances. If `timeout_sec` expires, the method fails explicitly instead of silently dropping queued work.

The controller must track accepted `session_id` values so drain completion is based on known submitted sessions, not only on empty queues. Empty queues alone are not sufficient because a worker may still be executing or a fan-in store may hold partial inputs.

## Controller, Scheduler, Worker, And Model Instance Roles

The managed runtime uses four explicit roles.

`WorkflowController` is the user-facing lifecycle wrapper. It parses workflow config, builds queues and worker actors, creates the scheduler actor, accepts external `submit(session_id, message)` calls, rejects duplicate sessions, exposes status/result APIs, and owns `stop_now()` / `drain_and_stop()`. It does not decide model placement, prefetch, eviction, token budget, or prediction policy.

`SchedulerActor` is the core control plane in managed mode. It holds a read-only copy of the static DAG (`adjacency`, `dependencies`, `topological_order`, `terminal_nodes`) and mutable session/runtime state. The scheduler uses this state to estimate ready and near-ready tasks, model demand, upstream ETA, terminal completion, and future resource pressure. It owns model instance lifecycle, accelerator accounting, prediction sources, placement, prefetch, eviction, token-budget decisions, and trace emission.

`NodeWorker` is the data-plane executor. It consumes its bounded input queue, resolves static fan-in, builds the prompt, invokes the node agent, performs fan-out, applies retry policy, and reports failures. In managed mode it requests execution resources from the scheduler before invoking the agent and releases them after completion. The worker does not inspect global queue state, accelerator state, or eviction policy.

`ModelInstance` is the GPU-resident execution resource. One actor represents one loaded model copy on one device. It exposes generation and lifecycle methods, reports measured load/inference metadata, and raises typed OOM failures. It does not understand workflow topology or session dependencies.

The scheduler keeps DAG structure because prediction-aware prefetch requires future dependency knowledge. For example, if `reducer` depends on `chunk_a`, `chunk_b`, and `chunk_c`, and two chunks are running with predicted finish times, only a DAG-aware scheduler can estimate when `reducer` will become ready and whether loading its model now can overlap upstream work.

## Managed Execution Protocol

Managed execution uses worker-initiated resource requests.

After a worker receives an item, resolves fan-in, and builds the prompt, it calls `SchedulerActor.acquire(...)`. The scheduler records a pending acquire and grants a model instance only when resource, placement, token-budget, and model lifecycle decisions allow execution.

When execution finishes, the worker calls `SchedulerActor.complete(...)`. `complete` means the task has finished and the granted model instance is no longer occupied by that task. It does not unload model weights or free GPU memory. The scheduler updates task state, marks the instance `IDLE`, records observed tokens/duration/failure metadata, updates session progress, and emits trace events.

GPU memory is released only through scheduler-owned `evict` actions. Eviction may happen after `complete`, but only when the scheduler decides that resource pressure, OOM cleanup, prefetch demand, or future reuse distance justifies unloading an idle instance. Busy or loading instances must not be evicted.

The public protocol names are:

```python
scheduler.acquire(...)
scheduler.complete(...)
```

The scheduler-internal lifecycle action is:

```python
scheduler.evict(instance_id)
```

## Model Instance Scope

A `ModelInstance` actor represents one loaded model copy on one device. Multiple agent nodes can share the same instance when their weight-loading configuration is compatible. Sharing means reusing resident model weights; it does not imply request batching.

Current implementation scope uses serial generation inside each `ModelInstance`: one instance executes one request at a time. If demand exceeds one instance, the scheduler may load additional replicas of the same model on available devices.

Continuous batching is not part of the current implementation. The planned next-stage direction is to introduce a vLLM backend as the real model inference service behind `ModelInstance`, rather than implementing a custom continuous batching engine on top of Hugging Face pipeline. The current `ModelInstance` interface must leave room for that backend swap, but scheduler correctness must not depend on continuous batching.

## Model Pool And Accelerator Identity

`ModelPool` uses the current sharing key:

```text
model_name + model_path + dtype
```

Agent nodes with the same sharing key may reuse the same idle `ModelInstance`. Request-level settings such as `prompt_template`, `system_prompt`, `max_new_tokens`, `temperature`, `do_sample`, and `enable_thinking` do not affect model instance sharing.

A loaded instance is still bound to one accelerator. Runtime code must not treat `cuda:N` as a globally unique resource id. Accelerator identity is represented by `AcceleratorConfig`:

```python
class AcceleratorConfig(BaseModel):
    hostname: NonEmptyStr
    gpu_kind: Literal["v100", "a100"]
    local_index: NonNegativeInt
    local_device: NonEmptyStr
    total_mem_mb: PositiveInt

    @property
    def accelerator_id(self) -> str:
        return f"{self.hostname}/{self.gpu_kind}:{self.local_index}"
```

Examples:

```text
gpu-node-0/v100:0
gpu-node-0/v100:1
gpu-node-1/a100:0
```

Runtime placement and model instance records use `accelerator_id`. Model launch on a host uses `local_device`, such as `cuda:0`. Prediction and graph-feature cache lookup use `gpu_kind`, because `WorkflowModelFeatureKey.gpu_name` describes hardware class rather than a concrete device.

## Model Instance States And Eviction Policy

Model instances use these states:

```text
LOADING
IDLE
BUSY
EVICTING
SUSPECT
```

`LOADING` means the model actor exists and is loading weights. `IDLE` means weights are resident and the instance can be granted. `BUSY` means one task is executing. `EVICTING` means the scheduler is unloading the instance. `SUSPECT` means OOM or a severe CUDA failure occurred; the instance must not be reused and should be evicted.

Valid transitions are:

```text
LOADING -> IDLE
IDLE -> BUSY
BUSY -> IDLE
BUSY -> SUSPECT
IDLE -> EVICTING
SUSPECT -> EVICTING
EVICTING -> removed
```

Only `IDLE` and `SUSPECT` instances are legal eviction victims. `BUSY` instances must not be evicted. `LOADING` instances are not normal eviction victims, except during forced `stop_now()` cleanup.

The default eviction policy is `future_reuse_distance`. For each legal victim, the scheduler estimates the earliest future demand for that instance model key from pending acquires, running upstream task ETA, static DAG dependencies, and active session state. The victim score is:

```text
reuse_distance_sec - reload_cost_sec
```

The scheduler evicts the legal victim with the largest score. A model key with no future demand in active sessions has infinite reuse distance and is preferred for eviction. Missing reload cost falls back to profiled or static default load time. Missing future ready time is treated as unknown.

If no legal victim has a computable score, the policy falls back to `longest_idle`. The fallback still cannot evict `BUSY` or normal `LOADING` instances.

## Accelerator Resource Accounting

Accelerator resources are static and config-owned. The scheduler does not discover GPUs at runtime and does not continuously poll NVML or `nvidia-smi` for scheduling decisions.

Each configured accelerator uses `AcceleratorConfig` and contributes `total_mem_mb` to the scheduler ledger. Placement, load, prefetch, and eviction use this internal ledger only:

```text
ledger_free_mb = total_mem_mb - scheduler_accounted_used_mb
required_mb = predicted_or_profiled_vram_mb + eps_mem_mb
```

A load or prefetch can be placed on an accelerator only when `ledger_free_mb >= required_mb`. If no accelerator has enough ledger space, the scheduler evaluates legal eviction victims and updates the ledger after eviction.

Startup validation is fail-fast. The runtime must reject configs where a hostname is not visible in the Ray cluster, accelerator ids are duplicated, local indexes conflict on the same host, `local_device` is malformed, `gpu_kind` is unsupported, `total_mem_mb` is invalid, or a `ModelInstance` cannot be started on the requested host.

Runtime OOM remains a real execution failure path. OOM marks the model instance `SUSPECT` and triggers scheduler cleanup, but normal scheduling does not depend on continuous GPU probing.

## Offline Prediction And Profile Artifacts

The scheduler reads final prediction artifacts. It does not load PyG `Data`, target scalers, feature scalers, ONNX files, or a GNN checkpoint during normal workflow execution.

Offline scripts own the heavy prediction pipeline:

```text
cache.yaml -> ONNX cache -> PyG graph-feature cache -> GNN checkpoint -> prediction cache
```

The runtime consumes only:

```text
prediction cache + deployment profile manifest
```

Prediction cache entries keep prompt and generation dimensions separate:

```text
model_name + gpu_kind + batch_size + sequence_length + decode_output_length
```

`sequence_length` represents the prompt/input bucket after the agent prompt template is applied. `decode_output_length` represents the candidate generation budget bucket. Runtime scheduling may derive `total_context_tokens = sequence_length + decode_output_length`, but the persisted prediction key must not collapse the two dimensions into one total-token key because prefill and generation have different latency behavior and the existing GNN features already model them separately.

The prediction cache stores final scheduler-facing values such as predicted run duration, predicted peak VRAM, predicted power, predictor metadata, and cache version. Missing prediction entries are fail-fast in the current implementation. The runtime must not export ONNX, build PyG data, run the GNN, or update prediction cache online.

Model deployment time and idle model memory come from an offline profile artifact such as `example/workflow/profile.yaml`. A standalone script profiles loading models from the shared model directory used by deployment. Profile entries are keyed by:

```text
model_name + model_path + dtype + gpu_kind
```

The deployment profile is scoped by GPU kind rather than hostname because worker nodes are expected to have similar performance and read from the same shared model directory. `hostname` remains part of `AcceleratorConfig` for actor placement, but not part of deployment profile lookup.

Deployment cost priority is:

```text
profile load_sec_p95 -> profile load_sec_median -> static default
```

The current prediction cache should reuse the existing bucket grid from `config/workflow/cache.yaml` and the existing key semantics from `WorkflowModelFeatureKey`. Do not introduce a parallel graph-feature registry.

The current cache uses `phase=decode`. This follows the existing data generation convention where `run_decode()` calls `model.generate(max_new_tokens=...)`, so decode records act as a full-generation proxy. Runtime prediction must document this convention and must not claim strict single-token decode prediction.

## Scheduler Request And Grant State Machine

The scheduler must not implement a blocking `acquire()` method inside the actor. A long-running acquire would occupy the scheduler actor and prevent tick, load, evict, poll, or complete calls from running.

The implementation uses non-blocking request and polling while preserving acquire semantics at the worker boundary:

```python
acquire_id = scheduler.request_acquire(...)
grant = wait_for_grant(scheduler, acquire_id, timeout_sec)
scheduler.complete(acquire_id, ...)
```

`SchedulerActor` keeps pending requests in ordinary in-actor Python structures, not Ray queues:

```python
pending_acquires: dict[str, PendingAcquire]
pending_order: deque[str]
grants: dict[str, GrantInfo]
running_tasks: dict[tuple[str, str], RunningTask]
```

`request_acquire(...)` creates a `PendingAcquire`, stores it, appends its id to `pending_order`, triggers `tick_once()`, and returns `acquire_id` immediately.

`tick_once()` is the only method that advances scheduling decisions. It scans pending acquires, running tasks, loading instances, completed dependencies, and near-ready DAG state; creates grants when resources are available; starts non-blocking model loads; and emits eviction actions. It must not block on long `ray.get()` calls.

`poll_grant(acquire_id)` returns `GrantInfo | None`. When a grant is returned, the scheduler has already reserved the instance and marked it `BUSY` for that acquire.

`cancel_acquire(acquire_id)` removes a pending request when worker-side waiting times out. If the acquire was already granted, cancellation must fail explicitly so the worker cannot silently leak a busy instance.

`complete(acquire_id, ...)` reports task completion or failure, updates the instance state, removes the running task, updates session progress and history, emits trace events, and triggers another `tick_once()`.

The worker should use a helper that polls `poll_grant` with a short sleep interval and calls `cancel_acquire` on timeout. This keeps polling logic out of node execution code.

## Prediction-Aware Scheduling Algorithm

The implementation maps the paper algorithm in `docs/draft/workflow.tex` to the runtime state machine as follows:

```text
C_ready  -> PendingAcquire created by a worker after fan-in and prompt construction
C_near   -> NearReadyTask estimated by the scheduler from DAG state and running task ETA
Dispatch -> GrantInfo stored by scheduler and returned through poll_grant
LoadOrPrefetch -> non-blocking ModelInstance creation
```

`tick_once()` advances the scheduler. It must be short-running and must not block on long model loading or inference calls.

Each tick runs in this order:

1. Refresh completed or failed non-blocking model loads.
2. Process `SUSPECT` instances and pending eviction cleanup.
3. Collect ready tasks from `pending_acquires`.
4. Collect near-ready tasks from static DAG dependencies, completed nodes, and running task ETA.
5. Grant ready tasks that can reuse an idle compatible instance.
6. Start loads for ready tasks that have no reusable idle instance.
7. Start prefetch loads for near-ready tasks only when the deploy window is useful.

Ready work has priority over near-ready work:

```text
ready grant > ready load > near-ready prefetch
```

Ready task ordering is `topological_order(node)` followed by acquire creation time FIFO inside the same node. Near-ready task ordering is estimated ready time followed by topological order.

If a compatible instance is already `LOADING`, the scheduler does not start another load for the same model key in the same tick. This prevents duplicate loading storms. Additional replicas are allowed only after there is no same-key loading instance, existing same-key instances are busy, pending pressure remains, and accelerator ledger space permits another load.

Near-ready prefetch may trigger eviction, but only through the normal legal-victim rules and default `future_reuse_distance` policy. Prefetch must not evict resources needed by already ready tasks.

A tick may grant multiple ready tasks if idle instances are available. Model load or prefetch starts are limited to at most one per model key per tick. Eviction is limited to at most one victim per accelerator per tick; after eviction, the next tick recomputes placement from fresh scheduler state.

## Task Runtime Reports And Scheduler History

Workers report runtime observations through `scheduler.complete(...)`. Do not add a second metrics queue for the current implementation.

The completion report contains the fields scheduler decisions need:

```python
class TaskRuntimeReport(BaseModel):
    acquire_id: str
    session_id: str
    node_id: str
    item_id: str
    model_key: str
    accelerator_id: str
    gpu_kind: str
    input_tokens: int
    granted_max_new_tokens: int
    output_tokens: int
    hit_token_limit: bool
    started_at: float
    finished_at: float
    status: Literal["success", "failed", "oom"]
    error_type: str | None = None
```

`hit_token_limit` is `True` when `output_tokens >= granted_max_new_tokens`. If a later backend exposes an explicit stop reason, the runtime should use that reason instead of the length heuristic.

The scheduler keeps lightweight rolling history keyed by `node_id + model_key + gpu_kind`. The required first-stage aggregates are:

```text
output_tokens_p90
hit_limit_rate
duration_sec_ema
oom_count
```

This history is scheduler state, not a prediction-cache update. It is used for placement preference, near-ready input-token estimates, and OOM penalty in the current run. Experiment trace output may persist the raw reports, but scheduler decisions must not mutate the offline prediction cache.

## Token Budget And OOM Behavior

Token budget is a deterministic feasibility search over prediction cache buckets. It is not an online GNN call and not a free-form generation policy.

Each agent node declares a token budget range:

```yaml
token_budget:
  min_max_new_tokens: 128
  default_max_new_tokens: 512
  max_max_new_tokens: 1024
```

For a ready task, the worker computes exact `input_tokens` from the final prompt before `request_acquire`. For a near-ready task, the scheduler estimates input length from upstream output-token history and prompt-template overhead. The scheduler maps input length to the smallest cached `sequence_length` bucket that is greater than or equal to the estimated input length.

Input tokens and output tokens share the same KV-cache capacity pressure after generation starts, but they are not equally controllable. Input tokens are fixed by the request. Output token budget is the scheduler-controlled variable. For each candidate accelerator, the scheduler searches cached `decode_output_length` buckets within `[min_max_new_tokens, max_max_new_tokens]` and chooses the largest feasible output budget satisfying:

```text
total_context_tokens = sequence_length_bucket + decode_output_length_bucket
predicted_vram_mb + eps_mem_mb <= ledger_free_mb
```

If the feasible budget is larger than `default_max_new_tokens`, the task is upscaled on that accelerator. If it is smaller than `default_max_new_tokens` but still at least `min_max_new_tokens`, the task is downscaled. If no accelerator can satisfy `min_max_new_tokens`, the task fails explicitly with `token_budget_infeasible`.

Placement should not always prefer the accelerator with the largest possible output budget. If a V100 can grant `default_max_new_tokens` and history for this node has low `hit_limit_rate`, the scheduler should prefer the cheaper/smaller accelerator. If V100 placement repeatedly hits the granted token limit or can only downscale below the default while A100 can grant a larger budget, A100 placement has real quality headroom and should be preferred.

`GrantInfo` must carry the final `granted_max_new_tokens`, the configured budget range, the selected prediction bucket, and a token budget action:

```text
fixed
upscaled
downscaled
infeasible
```

The worker and `ModelInstance` must use `granted_max_new_tokens`, not the node default. If `input_tokens` exceeds the largest available `sequence_length` bucket, or if the selected bucket is missing from the prediction cache, the scheduler fails fast instead of clamping silently.

OOM during execution remains a real failure path. The instance becomes `SUSPECT`, the scheduler records the failure, and normal cleanup/eviction logic applies. The scheduler may keep an in-memory `oom_penalty_mb` for the affected `model_key + gpu_kind + sequence_length + decode_output_length` bucket in the current run:

```text
effective_vram_mb = predicted_vram_mb + eps_mem_mb + oom_penalty_mb
```

The runtime must not write this penalty back to the offline prediction cache. A task that OOMs after a granted prediction may retry acquire once with the updated penalty; if it OOMs again, the session records a failure for that node.

## Trace Schema And Experiment Outputs

Trace records are runtime facts, not evaluator results. The runtime should collect detailed execution facts because this is a research system and later experiment analysis may need metrics that were not known before the run. The trace must avoid storing large text blobs, large objects, or full intermediate `AgentState` values by default.

Each workflow run writes to an experiment-provided output directory:

```text
<output_dir>/
  workflow_trace.jsonl
  session_results.jsonl
  run_summary.json
```

`output_dir` is passed by the experiment script or controller construction. It must not be embedded in workflow YAML. Every trace event carries `run_id`, so filenames do not need timestamps. Do not add default rotation or gzip compression in the current implementation because plain JSONL is easier to inspect during experiments.

`workflow_trace.jsonl` is the authoritative event log. It is append-only and contains one JSON object per runtime event. The first-stage event set is:

```text

run_finished
session_submitted
session_completed
session_failed
item_enqueued
item_dequeued
fanin_wait
fanin_ready
item_emitted
acquire_requested
acquire_granted
acquire_cancelled
model_load_started
model_load_finished
model_load_failed
model_reused
model_evicted
model_suspect
task_started
task_completed
task_failed
task_retried
token_budget_selected
token_budget_infeasible
prefetch_started
prefetch_skipped
prefetch_finished
scheduler_tick
scheduler_decision
```

All trace events share a common envelope:

```python
class TraceEvent(BaseModel):
    run_id: str
    event_id: str
    event_type: str
    ts: float
    session_id: str | None = None
    item_id: str | None = None
    node_id: str | None = None
    source_node: str | None = None
    target_node: str | None = None
    model_key: str | None = None
    instance_id: str | None = None
    accelerator_id: str | None = None
    gpu_kind: str | None = None
    acquire_id: str | None = None
    payload: dict[str, object] = Field(default_factory=dict)
```

Long text payloads are represented by metadata instead of full content:

```text
text_sha256
text_char_len
input_tokens
output_tokens
preview_head_chars
```

`preview_head_chars` is optional and should be disabled or very small by default. Complete intermediate node outputs and complete intermediate `AgentState` objects are not written to trace by default.

`session_results.jsonl` stores terminal node outputs. Each row contains `run_id`, `session_id`, terminal `node_id`, output metadata, and the terminal output content needed by benchmark or evaluator scripts. Evaluation functions read this file and dataset references outside the runtime.

`run_summary.json` is a convenience artifact generated after drain finishes. It is derived from trace and terminal results, not a replacement for `workflow_trace.jsonl`. It should include run-level counts and timing summaries such as submitted/completed/failed sessions, per-node task counts, token budget action counts, OOM counts, model load/reuse/evict counts, and active/resident GPU-second summaries.

Trace writing is required by default. If the trace writer fails to write or flush an event, the workflow run should fail fast because an untraceable experiment is not useful for this project. A future config may allow `trace_required: false`, but the default implementation should treat trace failure as a run failure.
