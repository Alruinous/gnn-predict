# LLM Workflow 数据集下一步实现步骤 20260619

## 背景

当前 `dataset/` 目录中已经下载了两个首版可用数据集：

| 数据集 | 本地路径 | 当前规模 | 用途判断 |
| --- | --- | --- | --- |
| GSM8K | `dataset/gsm8k/data/train.jsonl`, `dataset/gsm8k/data/test.jsonl` | train 7473, test 1319 | 数学 workflow 首版主集 |
| MBPP sanitized | `dataset/mbpp/sanitized-mbpp.json` | 427 条 | 代码 workflow 首版主集 |

这两个数据集都适合做第一阶段实验。

- GSM8K 有标准最终答案标记 `####`，可以做 numeric exact match。
- MBPP sanitized 有 `test_list`，可以用单元测试做 pass@1。
- 两者难度相对可控，比 MATH、BigCodeBench、VideoMME 更适合作为小模型 workflow 的起点。

当前阶段不应继续扩大数据集范围，也不应直接进入 GNN 调度实验。更重要的是先验证：

```text
小模型 workflow 是否能在 GSM8K / MBPP 上接近单一大模型质量
```

只有质量接近，后续资源开销和调度优化才有可比性。

## 总体顺序

建议采用以下顺序推进：

```text
原始公开数据集
  -> 标准化任务样本
  -> evaluator
  -> quality pilot
  -> workflow evaluation dataset
  -> resource profile 补齐
  -> GNN-aware 调度 replay
```

其中前四步是当前最优先工作。GNN 调度应放在质量门槛之后。

## Step 1: 标准化任务样本

目标是把 GSM8K 和 MBPP 转成统一的任务样本结构，供 evaluator、workflow 生成器和质量实验复用。

建议先不要改原始 `dataset/` 文件。原始数据只读，转换产物单独放在后续实验目录中。

### GSM8K

输入文件：

```text
dataset/gsm8k/data/train.jsonl
dataset/gsm8k/data/test.jsonl
```

原始字段：

| 字段 | 含义 |
| --- | --- |
| `question` | 数学文字题 |
| `answer` | 带推理过程和最终答案的参考答案 |

转换字段：

| 字段 | 来源 |
| --- | --- |
| `sample_id` | split + 行号 |
| `source_dataset` | `gsm8k` |
| `split` | `train` / `test` |
| `task_type` | `math_word_problem` |
| `input_text` | `question` |
| `gold_answer` | `answer` 中最后一个 `####` 后的值 |
| `quality_metric` | `numeric_exact_match` |

注意点：

- `gold_answer` 只用于 evaluator，不写入 workflow YAML。
- 保留原始 `answer` 可以用于诊断，但不应进入模型 prompt 的默认路径。
- 首版 quality pilot 建议只从 test split 抽 200 条。

### MBPP sanitized

输入文件：

```text
dataset/mbpp/sanitized-mbpp.json
```

本地文件实际可按 JSON array 读取。README 中提到 jsonl，但实现时应以本地文件结构为准。

原始字段：

| 字段 | 含义 |
| --- | --- |
| `task_id` | 任务 ID |
| `prompt` | 编程题描述 |
| `code` | 参考解 |
| `test_imports` | 测试依赖 import |
| `test_list` | 断言测试 |

官方切分建议：

| task_id 范围 | 用途 |
| --- | --- |
| 1-10 | few-shot prompt |
| 11-510 | test |
| 511-600 | validation |
| 601-974 | train |

当前本地 sanitized 文件中，官方 test 范围有 257 条。首版可以先使用这 257 条中的 100-200 条做 quality pilot。

转换字段：

| 字段 | 来源 |
| --- | --- |
| `sample_id` | `task_id` |
| `source_dataset` | `mbpp_sanitized` |
| `split` | 按 task_id 范围派生 |
| `task_type` | `python_function_generation` |
| `input_text` | `prompt` |
| `test_imports` | 原字段 |
| `test_list` | 原字段 |
| `quality_metric` | `pass_at_1` |

注意点：

- `code` 是参考解，可用于调试 evaluator，不应进入模型 prompt 的默认路径。
- `test_list` 是 evaluator 输入，不是 workflow tool 节点。
- 代码执行必须做隔离和 timeout。

## Step 2: 先实现 evaluator

质量评估器比 workflow YAML 更优先。没有 evaluator，就无法判断小模型 workflow 是否达标。

### GSM8K evaluator

输入：

```text
question
model_output
gold_answer
```

输出：

```text
exact_match: bool
predicted_answer: str | null
gold_answer: str
error_type: str | null
```

核心逻辑：

- 从模型输出中抽取最终数字答案。
- 归一化逗号、货币符号、空格和简单小数格式。
- 与 `gold_answer` 做 numeric exact match。

首版不需要复杂符号推理。GSM8K 的最终答案通常是明确数字，简单归一化足够支撑 pilot。

### MBPP evaluator

输入：

```text
prompt
model_output
test_imports
test_list
```

输出：

```text
passed: bool
passed_tests: int
total_tests: int
error_type: str | null
error_message: str | null
```

核心逻辑：

- 从模型输出中抽取 Python 代码块或函数定义。
- 在受限环境中执行 `test_imports`、生成代码和 `test_list`。
- 设置 timeout。
- 捕获语法错误、运行错误、断言失败和超时。

安全约束：

- 不允许网络访问。
- 不允许任意文件写入。
- 限制执行时间。
- 限制可用内置函数和危险 import。

如果本地隔离成本较高，首版至少应使用独立子进程加 timeout，后续再升级到更严格沙箱。

## Step 3: 跑 quality pilot

quality pilot 的目标不是一次性取得最好结果，而是快速判断该路线是否成立。

### 对照组

至少包含三组：

| 组别 | 作用 |
| --- | --- |
| 单小模型直接回答 | 判断 workflow 是否真的带来质量提升 |
| 小模型 workflow | 目标方案 |
| 单一大模型 baseline | 质量上限或对照 |

可选增加：

| 组别 | 作用 |
| --- | --- |
| 单一中模型 | 判断收益来自模型规模还是 workflow 结构 |
| 小模型 workflow 无 verifier | 判断 verifier 的边际价值 |
| 小模型 workflow 无 repair | 判断修复阶段的边际价值 |

### GSM8K workflow

首版建议结构：

```text
input
  -> router / prompt_normalizer
  -> solver_draft
  -> arithmetic_checker
  -> repair_solver
  -> final_answer_extractor
  -> output
```

节点角色：

| 节点 | 作用 |
| --- | --- |
| `router / prompt_normalizer` | 统一题目格式，可先用规则或轻量模型 |
| `solver_draft` | 小 LLM 生成解题过程 |
| `arithmetic_checker` | 检查数字计算和最终答案格式 |
| `repair_solver` | 对失败样本做一次修复 |
| `final_answer_extractor` | 抽取最终答案 |

首版可以把 `arithmetic_checker` 和 `final_answer_extractor` 做成规则 evaluator，不必都用 LLM。

### MBPP workflow

首版建议结构：

```text
input
  -> code_draft
  -> unit_test_executor
  -> code_repair
  -> unit_test_executor
  -> final_code_selector
  -> output
```

节点角色：

| 节点 | 作用 |
| --- | --- |
| `code_draft` | 小 LLM 生成函数代码 |
| `unit_test_executor` | 执行 MBPP 测试 |
| `code_repair` | 根据错误信息修复代码 |
| `final_code_selector` | 选择通过测试的版本 |

`unit_test_executor` 是 evaluator / 外部执行器，不是 GNN 要预测的 LLM 模型节点。

### 首版样本量

建议：

| 数据集 | pilot 样本量 |
| --- | --- |
| GSM8K test | 200 |
| MBPP official test subset | 100-200 |

样本选择应固定随机种子并保存 sample id，保证后续调度 replay 使用同一批任务。

### 质量门槛

建议先设明确门槛：

```text
small_workflow_quality >= big_model_quality - 5%
```

如果小模型 workflow 落后超过 5 个百分点，不进入 GNN 调度实验。

失败时优先处理：

- prompt 是否过弱。
- verifier 是否能发现错误。
- repair 是否真的使用错误信息。
- 小模型是否能力不足。
- 样本是否对当前小模型过难。

## Step 4: 生成 workflow evaluation dataset

只有通过 quality pilot 的配置才生成 workflow evaluation dataset。

建议目录：

```text
data/workflows/llm_pilot_20260619/
  tasks/
  workflows/
  manifest.json
  quality_results.json
```

### tasks

保存标准化后的任务样本。

建议分文件：

```text
tasks/gsm8k_test_pilot.jsonl
tasks/mbpp_test_pilot.jsonl
```

这些文件可以包含 gold answer 或 tests，因为它们是 evaluator 输入，不是 workflow YAML。

### workflows

保存每个任务对应的 workflow YAML。

当前 `Workflow` schema 禁止额外顶层字段，因此不要把 `source_dataset`、`sample_id`、`gold_answer`、`quality_result` 直接写进 YAML。

workflow YAML 只描述：

- DAG。
- 节点类型。
- 节点任务。
- 本地模型参数。
- runtime 参数。
- 边依赖。

### manifest

`manifest.json` 负责关联任务样本和 workflow 文件。

建议字段：

```text
workflow_id
workflow_path
source_dataset
sample_id
task_type
quality_metric
pilot_split
selected_workflow_template
```

### quality_results

`quality_results.json` 记录每组对照的质量结果。

建议字段：

```text
run_id
source_dataset
sample_id
model_group
workflow_template
metric_name
metric_value
passed
error_type
latency_sec
```

## Step 5: 补齐 resource profile

通过质量门槛后，再补齐本地小模型 workflow 节点的资源 profile。

重点不是重新训练 GNN，而是确认已有 GNN 能覆盖这些节点的关键 runtime 范围。

优先补齐：

| 维度 | 建议范围 |
| --- | --- |
| model | Qwen3 小规格、T5、GPT-2/BERT、Gemma 小规格 |
| phase | `prefill`, `decode`, `inference` |
| sequence_length | 128, 256, 512, 1024 |
| decode_max_output_length | 32, 64, 128, 256 |
| batch_size | 1, 2, 4 |
| GPU | V100, A100 |

当前 LLM workflow 的关键成本通常在 decode。若 decode profile 不足，GNN-aware 调度的信号会偏弱。

## Step 6: GNN-aware 调度 replay

调度实验只能在质量达标的 workflow 上做。

比较策略：

| 策略 | 作用 |
| --- | --- |
| `round_robin` | 简单负载均衡 baseline |
| `a100_first` | 强卡优先 baseline |
| `static_size` | 静态显存估计 baseline |
| `gnn_aware` | 目标策略 |

评价指标：

| 指标 | 含义 |
| --- | --- |
| avg session makespan | workflow 端到端平均耗时 |
| p95 session makespan | 尾延迟 |
| avg tool JCT | 工具节点平均完成时间 |
| OOM / retry | 可用性风险 |
| cold start count | 部署开销 |
| cache hit rate | 模型复用 |
| peak memory | 显存压力 |
| energy proxy | 能耗代理 |

调度结论必须与质量结果一起报告，避免只优化低质量 workflow。

## 当前推荐的 immediate next step

当前最应该做的是：

```text
GSM8K / MBPP 标准化
  -> evaluator
  -> 200 条级别 quality pilot
```

不要先做：

- 下载 MATH、BigCodeBench、VideoMME。
- 大规模生成 workflow YAML。
- 修改 GNN 训练数据。
- 直接声称小模型 workflow 比单一大模型资源更优。

这些动作都应等 quality pilot 结果出来之后再决定。

## 进入下一阶段的判定

满足以下条件后再进入 workflow dataset 和调度阶段：

| 条件 | 要求 |
| --- | --- |
| GSM8K evaluator 可复现 | 同一输出多次评估结果一致 |
| MBPP evaluator 可隔离执行 | 超时、断言失败和运行错误可区分 |
| pilot 样本固定 | 保存 sample id |
| 小模型 workflow 有质量增益 | 优于单小模型直接回答 |
| 接近单一大模型 | 差距不超过约 5 个百分点 |
| 节点 runtime 可表达 | workflow 节点能映射到现有 `Workflow` schema |

如果任一条件不满足，应先修质量评估或 workflow 结构，不进入 GNN 调度。
