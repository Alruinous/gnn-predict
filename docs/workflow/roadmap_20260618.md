# LLM Workflow 资源预测与调度路线图 20260618

## 目标

本文记录当前项目从“模型资源预测器”推进到“LLM workflow 资源优化调度”的实验路线。

核心目标不是证明小模型一定比大模型聪明，也不是让 GNN 预测答案质量，而是在可验证的质量约束下证明：

```text
小规模 LLM workflow 达到接近单一大模型的任务质量
  -> GNN-aware 调度降低小模型 workflow 的执行开销
  -> 相比朴素调度和单一大模型方案更有资源效率
```

这里的“智能”由公开 benchmark 的任务指标衡量，例如数学题 exact match 或代码题 pass@1。
这里的“开销”由本项目可预测和可采集的系统指标衡量，例如部署耗时、运行耗时、显存、OOM、retry、cold start 和能耗代理。

## 关键判断

用户提出的四步方向是合理主线：

1. 下载公开任务数据集，并从中构建 workflow evaluation dataset。
2. 使用小规模 LLM 组合构建 workflow，同时构建单一大模型 baseline。
3. 对比小模型 workflow 和单一大模型的准确度，确保两者有接近的任务能力。
4. 在质量接近的前提下，用 GNN 优化小模型 workflow 的性能开销，并与朴素调度和单一大模型对照。

需要补充的边界是：公开 benchmark 不直接成为 GNN 训练数据。

三类数据应分开：

| 数据类型 | 作用 | 是否训练 GNN |
| --- | --- | --- |
| 任务 benchmark | 衡量 workflow 或单模型答案质量 | 否 |
| workflow dataset | 描述每个样本对应的 DAG、节点、模型候选和 runtime | 否 |
| resource profile / trace | 提供模型在硬件上的系统指标和请求负载 | 是，或用于 replay |

GNN 只服务于本地模型节点资源预测。它不预测主 agent 的语义能力，也不预测外部 provider 延迟。

## 论文对照

Murakkab 论文的价值在于实验组织方式，而不是提供可直接复用的系统性能数据集。

论文使用了几类数据：

| 数据来源 | 论文用途 | 本项目可借鉴方式 |
| --- | --- | --- |
| VideoMME | Video Q/A workflow 质量评估 | 可作为多模态扩展，不作为首版 LLM-only 主线 |
| HumanEval | Code Generation workflow 质量评估 | 适合构建代码生成 workflow |
| MATH | Math Q/A workflow 质量评估 | 适合构建数学推理 workflow |
| Azure LLM serving traces | 模拟生产请求到达率和 token 规模 | 用于 replay 负载，不用于答案评估 |
| Workflow / model profile | 估计不同配置的质量、延迟、能耗和成本 | 与本项目 GNN 预测器目标最接近 |

本项目应该保留这两个原则：

- 质量 benchmark 与系统性能 profile 分离。
- workflow DAG 对调度器可见，调度器只优化已经达标的 workflow 配置。

## 实验问题

建议把研究问题写成三个层次。

| 层次 | 问题 | 成功信号 |
| --- | --- | --- |
| 质量 | 小模型 workflow 是否接近单一大模型 | accuracy / pass@1 / EM 与大模型差距不超过阈值 |
| 资源 | 达标 workflow 是否比单一大模型更便宜 | makespan、显存、能耗代理或 GPU 占用下降 |
| 调度 | GNN-aware 是否优于朴素调度 | OOM、retry、cold start、p95 makespan 或 energy proxy 改善 |

推荐总假设：

```text
对于可分解的 LLM 任务，小模型 workflow 可以用多阶段 draft / verify / finalizer 达到接近单一大模型的质量。
在质量达标的 workflow 配置上，GNN-aware 调度能利用模型结构和 runtime 预测降低冷启动、OOM 和能耗开销。
```

不建议把假设写成“小模型 workflow 全面优于大模型”。这很容易被任务难度、采样温度和模型能力反例击穿。

## 数据集选择

### 首版主线

首版应优先选择文本任务，避免视频、ASR、外部检索和真实代码仓库环境同时进入系统。

| 优先级 | 数据集 | 任务 | 建议用途 |
| --- | --- | --- | --- |
| 最高 | GSM8K | grade-school math word problems | 数学 workflow 首版主集 |
| 最高 | HumanEval | Python 函数生成 | 代码 workflow 主集 |
| 高 | MBPP sanitized | Python 基础编程题 | 补充 HumanEval 样本量 |
| 高 | MATH | 竞赛数学题 | 数学 workflow 难度扩展 |
| 高 | Azure LLM Inference Dataset 2024 | LLM 请求 token trace | 调度 replay 的负载来源 |

选择理由：

- GSM8K 有标准答案，任务难度适中，适合验证多阶段小模型 workflow。
- HumanEval 和 MBPP 都可用测试用例自动评估代码正确性。
- MATH 更难，可以作为第二阶段压力测试，不适合直接全量作为首版质量门槛。
- Azure trace 有 timestamp、context tokens 和 generated tokens，可用于构造到达率和 token 长度分布。

### 第二阶段扩展

| 数据集 | 任务 | 何时使用 |
| --- | --- | --- |
| BigCodeBench | 更复杂代码生成 | HumanEval / MBPP 跑通后 |
| MuSiQue | 多跳问答 | 引入检索或 evidence selector 后 |
| BFCL | function calling | 引入工具调用准确率评估后 |
| VideoMME | 多模态视频问答 | 本地视觉工具和多模态节点稳定后 |

这些数据集更接近真实 agent workflow，但会引入额外变量。首版不应同时纳入。

## 数据集改造

每个公开数据集需要转成统一任务样本格式。

推荐字段：

```text
sample_id
source_dataset
task_type
input_text
gold_answer
metadata
evaluator
workflow_template
```

不同数据集的转写方式：

| 数据集 | 输入 | 标签 | evaluator |
| --- | --- | --- | --- |
| GSM8K | `question` | `answer` 中 `####` 后的最终数值 | numeric exact match |
| MATH | `problem` | boxed answer 或最终答案 | normalized exact match |
| HumanEval | prompt / function signature / docstring | unit tests | pass@1 |
| MBPP | task description | test cases | pass@1 |
| Azure trace | timestamp、context tokens、generated tokens | 无答案标签 | replay only |

注意事项：

- 不把 ground truth 写入 workflow YAML。
- 不把 benchmark 原始样本伪装成 GNN label。
- 不把 Azure trace 当成真实 workflow 质量数据。
- 代码生成 evaluator 必须沙箱执行，不能直接在主进程运行不可信代码。

## Workflow 构造

### 数学 workflow

首版推荐两种结构。

轻量结构：

```text
input
  -> router
  -> solution_draft
  -> final_answer
  -> output
```

带验证结构：

```text
input
  -> router
  -> solution_draft
  -> self_reflection
  -> final_answer
  -> output
```

节点设计：

| 节点 | 类型 | 作用 | 候选模型 |
| --- | --- | --- | --- |
| router | tool 或 agent | 判断题型、难度或是否需要验证 | BERT、GPT-2、小 Qwen3 |
| solution_draft | tool | 生成解题草稿 | Qwen3、Gemma、T5 |
| self_reflection | tool | 检查步骤和答案一致性 | Qwen3、T5 |
| final_answer | tool | 提取最终答案 | T5、Qwen3 |

### 代码 workflow

首版推荐两种结构。

最小结构：

```text
input
  -> prompt_classifier
  -> code_draft
  -> output
```

带测试结构：

```text
input
  -> prompt_classifier
  -> code_draft
  -> test_draft
  -> repair_or_verdict
  -> output
```

节点设计：

| 节点 | 类型 | 作用 | 候选模型 |
| --- | --- | --- | --- |
| prompt_classifier | tool | 判断题目类型、复杂度和库需求 | BERT、GPT-2 |
| code_draft | tool | 生成代码 | Qwen3、Gemma |
| test_draft | tool | 生成补充测试或解释 | T5、Qwen3 |
| repair_or_verdict | tool | 修复或判断输出 | Qwen3、T5 |

真实 Python 解释器执行不应作为 GNN 预测节点。它是 evaluator 或外部工具节点，记录 wall time 即可。

## 单一大模型 baseline

单一大模型 baseline 应优先使用本地模型，否则资源开销不可比。

推荐设置：

| baseline | 用途 | 注意 |
| --- | --- | --- |
| 本地 7B / 14B dense LLM | 主要资源对照 | 可采集 GPU 显存、耗时和功耗 |
| 外部 API 模型 | 质量上界 | 不作为本地资源开销对照 |
| 单一中模型 | 消融对照 | 判断 workflow 收益是否来自多阶段结构 |

如果只有外部 API 大模型可用，则只能报告：

```text
小模型 workflow 质量接近外部大模型
小模型 workflow 本地资源开销低于本地单中模型或朴素小模型调度
```

不能声称本地小模型 workflow 的 GPU 开销优于外部 API 大模型，因为外部 API 的真实硬件开销不可见。

## 质量门槛

质量门槛应先于调度优化，否则资源优化没有意义。

推荐规则：

```text
small_workflow_quality >= big_model_quality - delta
```

建议阈值：

| 任务 | 指标 | 首版 delta |
| --- | --- | ---: |
| GSM8K | exact match | 3% - 5% 绝对值 |
| MATH easy subset | exact match | 5% 绝对值 |
| HumanEval | pass@1 | 3% - 5% 绝对值 |
| MBPP sanitized | pass@1 | 3% - 5% 绝对值 |

结果应分成两层报告：

| 配置 | 是否进入调度实验 |
| --- | --- |
| 质量达标 workflow | 是 |
| 质量不达标 workflow | 否，只做诊断 |

这样能避免把“更便宜但明显更笨”的方案混入最终结论。

## GNN 调度问题

GNN-aware 调度只优化本地 tool 节点。

核心输入：

| 输入 | 来源 |
| --- | --- |
| ONNX 图特征 | 当前 GNN 数据抽取流程 |
| runtime | batch、sequence length、decode output length、phase |
| GPU 类型 | V100、A100 等 |
| 当前缓存状态 | 调度器状态 |
| 当前可用显存 | 调度器或监控 |

核心预测目标：

| 目标 | 调度作用 |
| --- | --- |
| deployment duration | 冷启动和预部署 |
| run duration | tool JCT 和 critical path |
| GPU memory | OOM 避免和并行/串行决策 |
| GPU power | energy proxy |

辅助目标：

| 目标 | 用途 |
| --- | --- |
| GPU util | 解释利用率，不作为首要目标 |
| SM active / occupancy | 分析 kernel 活跃度和异常样本 |
| CPU / memory delta | 只有出现主机瓶颈时纳入 |

## 调度策略对照

建议沿用现有 workflow 调度文档中的 baseline。

| 策略 | 含义 |
| --- | --- |
| `round_robin` | V100/A100 轮转，不看预测 |
| `a100_first` | 强卡优先，可用性 baseline |
| `v100_only` | 旧卡优先，成本保守 baseline |
| `static_size` | 只用 ONNX 静态规模代理 |
| `gnn_aware` | 用 GNN 预测 deploy / run / mem / power 选卡 |
| `gnn_aware_cache` | 进一步考虑缓存复用 |
| `gnn_aware_energy` | 在质量和延迟约束下优化能耗代理 |

首版只需要到 `gnn_aware`，不要一开始就实现完整多目标优化器。

## 调度评价指标

| 指标 | 含义 | 方向 |
| --- | --- | --- |
| avg session makespan | workflow 端到端平均耗时 | 越低越好 |
| p95 session makespan | 尾部耗时 | 越低越好 |
| avg tool JCT | 单个 tool 完成时间 | 越低越好 |
| OOM events | 显存失败次数 | 越低越好 |
| retry events | 失败重试次数 | 越低越好 |
| cache hit rate | 模型复用比例 | 通常越高越好 |
| cold start sec | 总部署耗时 | 越低越好 |
| energy proxy | `power * duration` 估算 | 越低越好 |
| GPU memory utilization | 缓存/运行占用水平 | 需要结合 OOM 判断 |

最终表格应同时报告质量和资源，不能只报告资源：

```text
dataset / task
workflow config
quality metric
quality gap vs big model
scheduler
makespan
OOM / retry
cold start
energy proxy
```

## Azure Trace 用法

Azure LLM Inference Dataset 2024 不包含原始 prompt 内容，只包含 token 规模和时间信息。

可用字段：

| 字段 | 用法 |
| --- | --- |
| timestamp | 构造请求到达序列 |
| context tokens | 映射 prompt length |
| generated tokens | 映射 decode output length |
| service category | 映射 math / code workflow 比例 |

推荐映射：

```text
coding requests -> HumanEval / MBPP workflow
chat requests -> GSM8K / MATH workflow
context tokens -> sequence_length bucket
generated tokens -> decode_max_output_length bucket
```

注意：

- Azure trace 不提供答案，因此不能用于质量评估。
- replay 时应保留真实时间分布，或压缩为固定倍速。
- token bucket 应落在本项目已有 profile 覆盖范围内，避免把调度实验变成纯 OOD 压测。

### 数据层

新增或扩展任务数据转换能力：

```text
public benchmark sample
  -> normalized task sample
  -> workflow instance
```

建议产物：

```text
data/workflows/llm_20260618/
  tasks/
  workflows/
  manifest.json
  quality_results.json
  replay_traces.json
```

### Workflow schema

当前 workflow schema 已有 DAG、节点、model 和 runtime 概念，但需要补充两类字段。

建议补充：

| 字段 | 位置 | 用途 |
| --- | --- | --- |
| `source_dataset` | workflow metadata | 追踪样本来源 |
| `sample_id` | workflow metadata | 关联 benchmark 样本 |
| `quality_metric` | workflow metadata | 记录评估口径 |
| `candidate_models` | tool node | 表达可替代模型 |
| `slo` | workflow metadata | 表达质量或延迟约束 |

不建议补充：

- benchmark ground truth。
- 真实运行结果。
- GNN 预测值。
- 调度决策结果。

这些应放在 evaluation artifact 中。

### 模型执行层

需要统一本地小模型和单一大模型的调用接口。

接口应能表达：

| 能力 | 说明 |
| --- | --- |
| prefill | prompt forward-only |
| decode | generate with max_new_tokens |
| sequence classification | router / classifier |
| text-to-text | T5 finalizer 或 summarizer |

代码任务额外需要安全沙箱执行生成代码。沙箱是 evaluator，不是 GNN tool 节点。

### Resource profile

当前 GNN 对 LLM 的 `prefill` 有数据，但首版 workflow 需要更多 `decode` profile。

重点补充：

| 维度 | 建议范围 |
| --- | --- |
| model | Qwen3、T5、Gemma、GPT-2/BERT |
| phase | inference、prefill、decode |
| sequence length | 128、256、512、1024 |
| decode output length | 32、64、128、256 |
| batch size | 1、2、4 |
| GPU | V100、A100 |

如果 decode profile 不足，GNN 调度对 LLM workflow 的关键成本会偏弱。

### 质量评估

数学评估：

| 数据集 | 处理 |
| --- | --- |
| GSM8K | 提取 `####` 后答案，做数值归一化 |
| MATH | 解析 boxed/final answer，做 LaTeX 和符号归一化 |

代码评估：

| 数据集 | 处理 |
| --- | --- |
| HumanEval | 执行官方测试，统计 pass@1 |
| MBPP | 执行内置 test cases，统计 pass@1 |

代码执行必须隔离：

- 禁止网络。
- 限制 CPU 时间。
- 限制内存。
- 使用临时目录并清理。
- 捕获 timeout、syntax error、runtime error。

## 首版最小实验

推荐首版不要追求全量复杂度。

数据：

| 数据集 | 数量 |
| --- | ---: |
| GSM8K test subset | 200 - 500 |
| HumanEval | 164 |
| MBPP sanitized subset | 200 - 500 |

模型：

| 角色 | 候选 |
| --- | --- |
| small workflow | Qwen3 0.6B / 1.7B、T5、GPT-2/BERT |
| single big model | 本地 7B 或 14B dense LLM |
| quality upper bound | 可选外部 API |

调度：

| 策略 | 是否首版 |
| --- | --- |
| `round_robin` | 是 |
| `a100_first` | 是 |
| `static_size` | 是 |
| `gnn_aware` | 是 |
| `gnn_aware_cache` | 可选 |

阶段：

```text
任务样本转写
  -> 生成 workflow DAG
  -> 跑小模型 workflow 和单一大模型质量
  -> 过滤质量达标配置
  -> 采集或复用 resource profile
  -> trace replay 调度
  -> 汇总质量和资源结果
```

## 阶段计划

### Phase 0: 准备

目标：

- 固定数据集清单。
- 固定首版模型清单。
- 明确质量门槛。

产物：

```text
docs/workflow/roadmap_20260618.md
data/workflows/llm_*/manifest draft
```

### Phase 1: 质量实验

目标：

- 跑通小模型 workflow。
- 跑通单一大模型 baseline。
- 得到 GSM8K、HumanEval、MBPP 的质量指标。

判断：

```text
如果 small workflow 达不到质量门槛，先改 workflow 或模型组合，不进入调度实验。
```

### Phase 2: Profile 补齐

目标：

- 补齐小模型 workflow 节点的 V100/A100 资源 profile。
- 特别补齐 decode 阶段。

判断：

```text
如果 decode profile 覆盖不足，先补采样，不直接用 extrapolation 做主结论。
```

### Phase 3: 调度 replay

目标：

- 对质量达标 workflow 做离线 replay。
- 比较 GNN-aware 与朴素调度。

使用：

- 固定 workflow 请求集。
- Azure trace token bucket 或合成 session trace。
- 相同质量配置下比较资源指标。

### Phase 4: 端到端论证

目标：

- 汇总小模型 workflow vs 单一大模型质量和资源。
- 汇总 GNN-aware vs baseline 的调度收益。

最终结论形态：

```text
在 GSM8K / HumanEval / MBPP 上，小模型 workflow 与单一大模型质量差距在阈值内。
在这些达标 workflow 上，GNN-aware 调度相对 round_robin / a100_first / static_size 降低 OOM、cold start、makespan 或 energy proxy。
因此，本项目的 GNN 资源预测器可以作为 LLM workflow 小模型群体调度的系统优化组件。
```

## 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 小模型 workflow 质量不达标 | 无法进入资源优化主结论 | 降低任务难度、加入 verifier、选择更强小模型 |
| 多节点 decode 成本高于单大模型 | 资源结论失败 | 引入 early exit、减少 verifier 调用、缓存常用模型 |
| HumanEval 样本太少 | 统计不稳 | 加 MBPP sanitized |
| MATH 太难 | 小模型质量地板效应 | 先跑 GSM8K 和 MATH easy subset |
| 外部 API 大模型不可比 | 资源结论不公平 | 外部 API 只做质量上界 |
| decode profile 不足 | GNN 调度信号弱 | 优先补采 decode profile |
| 代码执行有安全风险 | 可能污染环境 | sandbox、timeout、临时目录清理 |
| LLaMA 现有预测误差偏高 | 影响调度结论 | 首版不把 LLaMA 作为主模型 |

## 不做的事

首版不做：

- 不训练 GNN 预测答案正确率。
- 不把 benchmark 样本直接作为 GNN 训练标签。
- 不把外部 API 延迟和费用混入本地 GPU profile。
- 不做 VideoMME 全量视频处理。
- 不做 SWE-bench 类真实仓库修复任务。
- 不做全局多租户 MILP。
- 不把所有预测目标都作为同等重要优化目标。

## 推荐表述

建议后续论文或报告中这样描述：

```text
我们从公开 LLM benchmark 构建可执行的 workflow evaluation dataset。
每个 workflow 由多个本地小模型 tool 节点组成，并与单一大模型 baseline 做任务质量对照。
只有当小模型 workflow 的质量接近单一大模型时，才进入资源调度评估。
在调度阶段，GNN 预测器根据模型 ONNX 图、runtime 和硬件特征估计部署耗时、运行耗时、显存和功耗。
调度器使用这些预测值做设备选择、OOM 避免、冷启动优化和缓存复用。
实验同时报告质量指标和资源指标，证明 GNN-aware 调度在保持近似智能的条件下降低 LLM workflow 的系统开销。
```
