# 工作流系统实验结果（system_20260713_v2）

## 技术摘要

正式矩阵已于 2026-07-14 20:15 UTC 完成，共 75/75 次完整运行（trials）、15/15 个各重复 5 次（`n=5`）的实验组，正式运行失败和事后排除均为 0。实验支持以下结论：

- **QMSum 突发到达（burst）：WF-Cache 是资源效率取舍，不是端到端加速。** 相对 LG-Batch，其整批完成加速比（makespan speedup）为 `0.994x [0.978, 1.010]`，没有可辨识加速，第 95 百分位任务延迟（p95）反而高 `2.436% [0.026, 4.845]`；同时模型驻留开销（resident GPU-s）和空载扣除后的单次完成能耗分别降低 `36.416%` 和 `20.557%`。相对 WF-FIFO，WF-Cache 慢 `2.1%`，p95 高 `2.622%`，但模型驻留开销降低 `25.316%`。
- **QMSum 的低空泡来自等待位置转移。** WF-Cache 将流水线驻留空泡率（pipeline bubble）从 LG-Batch 的 `36.508%` 降至 `5.475%`，vLLM 内部平均排队时间从 `89.412 秒` 降至 `0.037 秒`，但应用层因队列满而阻塞的背压时间（backpressure）增至 `334.702 秒`。因此低空泡不能单独解释为端到端性能提升。
- **QMSum 开放到达（open-loop）暴露出尾延迟代价。** 在 75% 负载下，WF-Cache 吞吐与 LG-Batch 无可辨识差异，但 p95 高 `102.502%`；在 125% 负载下，吞吐低 `2.9%`，p95 高 `116.853%`。两点都节省模型驻留开销，但当前策略不适合作为尾延迟改善方案。
- **MBPP 2-GPU 下 WF-Cache 获得稳定的性能和驻留收益，但没有能耗收益。** 相对 WF-FIFO，WF-Cache 的整批完成速度为 `1.052x`、p95 降低 `5.191%`、模型驻留开销降低 `11.048%`；能耗点估计反而高 `23.454%`，且区间跨 0。相对 WF-History，前三项收益相近，能耗则显著高 `20.311%`。
- **MBPP 的实用资源拐点是 2 GPU。** WF-Cache 从 2 GPU 增至 3 GPU 后，均值吞吐由 `5.868` 降至 `5.817 个完整任务/分钟`，模型驻留开销由 `183.708` 增至 `282.674 GPU-s`。3-GPU LG-Batch 的首次重复存在显著冷加载/顺序异常，正式 `n=5` 区间很宽，不能据此判断其与 WF-Cache 的胜负。

## 阅读指南：术语、指标和数值方向

本节是报告的阅读前提。项目专用名称保留英文原名以便对应代码和图表，但首次阅读只需按中文定义理解。除非表格另有说明，`均值 [95% CI]` 表示 5 次独立运行的均值和 95% 置信区间，例如 `425.002 [413.042, 436.962]` 表示均值为 425.002，区间为 413.042 至 436.962。

### 实验对象与负载

| 术语 | 本报告中的准确含义 |
|---|---|
| QMSum | 会议记录问答式摘要任务。一个完整任务会先把长文本拆成多个分块并行总结，再等待所有分块完成后合并，因此会产生分叉、汇合和排队。 |
| MBPP | Python 代码生成与修复任务。一个完整任务包含初始代码生成、测试/批评、修复和最终测试，用于观察多模型顺序切换。 |
| 工作流（workflow） | 一个样本从输入到最终输出所经过的整条多节点执行图，不等同于单次大模型调用。 |
| 完整任务（session） | 一个样本执行一次完整工作流。QMSum 和 MBPP 每个正式 trial 都固定执行 24 个 session。 |
| 一次完整运行（trial） | 在一个固定场景、策略、GPU 数和参数配置下，把 24 个 session 全部执行完一次。表中的计数指标先在 trial 内统计，再对 5 次 trial 求均值和区间。 |
| 重复编号（repetition） | 同一配置的第 1 至第 5 次独立运行。配对比较使用相同 repetition 的冻结输入和到达序列，以减少输入差异。 |
| `n=5` 实验组 | 同一配置有 5 次 trial，不是 5 个样本；每组实际覆盖 `5 × 24 = 120` 个 session。 |
| 突发到达（burst） | 24 个 session 在运行开始时一起进入系统，用于观察批处理、排队和资源竞争。 |
| 开放到达（open-loop） | session 按预先生成的泊松到达时间进入系统，到达节奏不等待前一个任务完成，更接近持续外部流量。 |
| 工作负载（workload） | 一次实验实际投入系统的输入样本、到达时间和请求组合。本报告正式 workload 是冻结的 24 个样本子集。 |
| `parent-60` | 用于选择正式 24 个样本及做先前容量标定的 60 样本母集，不代表本轮正式 trial 使用了 60 个样本。 |
| GPU | 图形处理器；本实验把它作为加载模型和执行大模型推理的加速设备。GPU 数表示一个配置最多能使用几张卡。 |
| 词元（token） | 大模型处理文本时使用的基本单位，可能是一个词、词的一部分或标点，不等同于汉字数或单词数。 |
| 提示长度预检查（prompt preflight） | 正式运行前检查提示文本和最大输出长度是否能放进模型上下文窗口。它只确认输入可执行，不产生性能比较结果。 |
| 容量标定（calibration） | 先用饱和负载估计系统每秒可完成多少 session，再据此设置 open-loop 到达率。它只提供负载输入，不计入本轮 75 个正式 trial，也不是待比较的新策略。 |
| 容量（capacity） | 标定得到的参考完成率；本报告为 `0.077483 session/秒`。它是 parent-60 工作负载上的参考值。 |
| 负载系数（load factor） | 设定到达率除以参考容量。75% 表示按参考容量的 0.75 倍送入，125% 表示按 1.25 倍送入。 |
| 设定到达率（offered rate） | 外部计划每秒送入多少 session，单位为 session/秒；它是输入速率，不是系统实际完成吞吐。 |

### 调度策略

| 名称 | 本报告中实际做法 |
|---|---|
| LG-Batch | `LG` 指本项目使用的 LangGraph 工作流框架。该并发基线预先静态加载场景所需模型并使其持续驻留，再并发执行多个完整工作流；不使用预测缓存做模型预取或驱逐。 |
| WF-FIFO | `WF` 指自定义工作流执行器，`FIFO` 指“先进先出”。任务按到达顺序处理，模型按需加载，并使用简单驱逐规则；不使用预测缓存。 |
| WF-History | `History` 指“本轮历史”。自定义工作流执行器只使用当前完整运行中已观察到的加载和执行历史做生命周期决策；每次运行开始时清空历史，不读取冻结预测缓存。 |
| WF-Cache | `Cache` 指“预测缓存”。自定义工作流执行器读取冻结的合成预测缓存，用预测耗时辅助任务准入、模型预取和结合工作流进度的驱逐。该缓存不是本轮图神经网络的输出，也不代表预测精度实验。 |
| `g1`、`g2`、`g3` | 分别表示该配置可使用 1、2、3 张 GPU。 |
| `(seq3,q16)` | `max_num_seqs=3`、`queue_capacity=16` 的缩写，即每个 vLLM 引擎最多同时调度 3 条序列，节点间有界队列最多容纳 16 项。 |

### 统计比较怎么读

| 术语 | 定义与判断规则 |
|---|---|
| 均值（mean） | 5 次 trial 的算术平均值。它描述平均表现，不代表每次运行都等于该值。 |
| 95% 置信区间（95% CI） | CI 是“置信区间”的英文缩写。本报告用适合小样本均值估计的 Student-t 方法，根据 5 次 trial 计算不确定范围；样本只有 5 次，区间会受首轮冷加载等异常影响。 |
| p95 | 第 95 百分位 session 延迟：约 95% 的 session 延迟不超过该值，越低越好。本报告先在每个 trial 的 24 个 session 内算 p95，再跨 5 次 trial 汇总。 |
| 候选/基线（candidate/reference） | 斜线左侧是要评价的候选策略，右侧是比较基线。例如 `WF-Cache/WF-FIFO` 表示评价 WF-Cache 相对 WF-FIFO 的变化。 |
| 加速比（speedup） | 整批完成时间使用“基线时间 ÷ 候选时间”，吞吐使用“候选吞吐 ÷ 基线吞吐”。都以 1 为无差异点；大于 1 表示候选更快，小于 1 表示候选更慢。 |
| 降幅（reduction） | 使用 `(基线值 - 候选值) ÷ 基线值`。正数表示候选降低了该开销，负数表示候选反而更高。例如 `resident GPU-s reduction = 36.416%` 表示候选的模型驻留开销比基线少 36.416%。 |
| 区间跨无差异点 | speedup 的置信区间跨 1，或 reduction 的置信区间跨 0，表示本轮重复不足以辨识稳定差异，不能只按均值宣布胜负。 |
| 同 repetition 配对 | 候选和基线先按相同重复编号一一计算比值或降幅，再汇总 5 个配对效应；不是拿两个组均值直接相除。 |

### 性能与资源指标

| 指标 | 测量对象、单位与数值方向 |
|---|---|
| 整批完成时间（makespan） | 从 trial 开始到 24 个 session 全部产生业务结果的实际经过时间，单位为秒，不含其后的清理时间。越低越好。 |
| 全程吞吐（sessions/min） | `24 ÷ makespan × 60`，表示整次运行平均每分钟完成多少 session。越高越好，包含冷启动和尾部排空影响。 |
| 稳态吞吐（steady-state throughput） | 只使用完成顺序中间 20% 至 80% 的时间戳拟合完成斜率，弱化启动和尾部影响，单位为 session/分钟。它不是独立跑出的长稳态实验。 |
| session 延迟 | 单个 session 从其到达到产生最终结果的时间，单位为秒。越低越好；open-loop 中包含到达后的所有排队时间。 |
| 单位 GPU 吞吐（sessions/min/GPU） | 全程吞吐除以可用 GPU 数，用于比较单位 GPU 的产出。越高通常越好，但仍需同时看延迟和总资源。 |
| 模型驻留开销（resident GPU-s） | 各模型副本完成加载后留在 GPU 上的时间之和。1 个副本驻留 10 秒是 10 GPU-s；2 个副本各驻留 10 秒是 20 GPU-s。相同 workload 下越低表示占用 GPU 的累计时间越少，但不等于计算量或显存大小。 |
| 活跃计算时间（active GPU-s） | 各模型副本实际执行推理任务的时间区间并集，再跨副本求和；同一副本上的重叠请求不会重复累计。 |
| 每次完成的活跃 GPU 时间（GPU-s/completion） | `active GPU-s ÷ 完成 session 数`，表示平均完成一个 session 消耗多少活跃 GPU 时间。越低通常越好。 |
| 模型加载开销（loading GPU-s） | 各 GPU 上模型从开始加载到加载完成的时间区间之和，单位为 GPU-s。它反映累计加载占用；加载若与其他工作重叠，不一定等量增加 makespan。 |
| 空闲驻留时间（idle-resident GPU-s） | 模型已驻留但没有执行推理的累计 GPU 时间。越低表示已占用的模型副本更少闲置，但可能只是等待被移到 GPU 之外。 |
| 扣空载后的单次能耗（idle-subtracted energy/completion） | GPU 功率遥测按时间积分，减去每张 GPU 首个空载功率基线，再除以完成 session 数，单位为焦耳/次完成。越低越好；它不是整机能耗。 |
| 驻留开销降幅（resident GPU-s reduction） | 候选相对基线少用了多少模型驻留 GPU 时间。正数是节省，负数是增加；只在完成相同冻结 workload 的配对运行间比较。 |

### 流水线与模型生命周期指标

| 指标 | 本报告中的准确含义 |
|---|---|
| 分叉/汇合（fan-out/fan-in） | fan-out 把一个 QMSum session 拆成多个并行分块；fan-in 必须等这些分块全部返回后才能执行合并节点。 |
| 汇合平均等待（mean fan-in wait） | 每个汇合节点从首次发现上游结果未齐，到所有必需结果到齐的等待时间，再取平均，单位为秒。越低表示分支更同步。 |
| 流水线空泡率（pipeline bubble） | 在业务尚未结束且模型已驻留的窗口内，“模型驻留但没有执行推理”的 GPU 时间占比。越低只表示驻留窗口利用更充分；若等待移到应用队列，端到端延迟仍可能变差。 |
| vLLM 平均排队时间（mean vLLM queue） | 一次推理请求进入 vLLM 后、真正开始被引擎处理前的平均等待，单位为秒。它不包含进入 vLLM 之前的应用层等待。 |
| 背压持续时间（backpressure） | 下游有界队列已满，导致上游不能把结果放入队列的时间区间并集，单位为秒。越高表示应用层阻塞越久；它不是把每个被阻塞项目的时长简单相加。 |
| 队列容量（queue capacity） | 节点间队列最多可暂存的项目数。容量小会更早触发背压，容量大则可能增加排队和内存占用。 |
| vLLM | 本实验实际执行大模型推理的服务引擎。报告中的 vLLM 排队只统计请求进入该引擎之后的等待。 |
| 连续批处理（continuous batching） | vLLM 在已有序列运行时动态加入新序列，序列完成后立即补位，而不是等待固定批次整体结束。 |
| `max_num_seqs` | 单个 vLLM 引擎同一时刻最多调度的序列数；本报告的 `seq1` 和 `seq3` 分别表示 1 和 3。 |
| 模型副本（replica） | 一个加载在某张 GPU 上、可接收推理请求的模型实例。`resident replica` 表示该实例已加载且尚未被驱逐。 |
| 完成加载次数（loads） | trial 内收到 `model_load_finished` 的次数，即模型副本完成从存储/主存到可用状态的次数。越少不必然越好，还要看驻留和延迟。 |
| 驻留复用次数（reuses） | 请求到达时直接使用已经驻留的模型副本、因而避免再次加载的事件数。`reuses=69` 表示每次完整运行有 69 个请求复用了现有副本，不是复用了 69 个模型。越高通常说明加载复用更多，但不能单独证明性能更好。 |
| 预取启动次数（prefetches） | 在工作流尚未显式请求下一模型前，调度器根据预测提前启动模型加载的次数。本报告表中的 `1.000 [1.000, 1.000]` 表示该组每次完整运行都恰好主动提前加载 1 次，不是每个完整任务 1 次。 |
| 驱逐完成次数（evictions） | 为释放 GPU 资源而将驻留模型移除并完成驱逐的次数。驱逐过多可能增加后续重载，过少可能长期占用 GPU。 |
| 无效预取次数（wasted prefetches） | 预取完成后，在模型被任何任务实际取得使用之前就被驱逐，或直到运行结束仍未使用的次数。0 表示本轮预取都被使用过，不代表预取一定缩短了端到端时间。 |

### 质量、完整性与复现术语

| 术语或指标 | 本报告中的准确含义 |
|---|---|
| F1 | 精确率与召回率的调和平均数，用一个 0 至 1 的数同时反映“匹配内容是否准确”和“参考内容覆盖多少”；越高表示文本重合越强。 |
| ROUGE-1 / ROUGE-2 / ROUGE-L | QMSum 生成摘要与参考摘要之间的词元重合 F1：分别看单词、连续双词和最长公共子序列。取值 0 至 1，越高表示文本重合更多；它不等同于事实正确性或人工质量。 |
| 首次通过率（initial pass@1） | MBPP 每个样本只取一份初始代码，能通过固定测试的样本比例。`23/24 = 95.833%`。 |
| 修复后通过率（final pass@1） | 经过批评/修复节点后，最终代码能通过固定测试的样本比例。`22/24 = 91.667%`。 |
| 修复成功数（repaired） | 初始代码未通过、但最终代码通过的样本数。 |
| 修复后退化数（regressed） | 初始代码通过、但修复后的最终代码不再通过的样本数。本报告每个 MBPP trial 都为 1。 |
| 空输出数（empty outputs） | 最终摘要为空的 session 数，不是空的中间分块数。0 表示没有最终空输出。 |
| 触及生成上限（token-limit hit） | 某次大模型调用生成到了配置的最大输出 token 数，存在被截断的可能；不等于该输出必然错误。最终合并节点命中比中间分块命中更直接影响最终结果。 |
| 运行事件轨迹（trace） | 按时间记录的运行事件流，例如任务开始/结束、入队/出队、加载/驱逐。它用于重建延迟和资源区间。 |
| 运行事件未配对（trace unmatched） | 应成对出现的开始/结束事件没有匹配上。0 表示本轮用于计算指标的事件对完整，不表示系统绝无其他类型问题。 |
| 质量护栏（quality guardrail） | 用来确认不同调度策略没有明显改变输出语义或执行完整性的最低检查，不用于宣称算法质量提升。 |
| GPU 遥测（telemetry） | 运行期间定期采样的 GPU 功率、显存和利用率数据，用于派生能耗等指标。 |
| 合成预测缓存（synthetic prediction cache） | 预先冻结的模型耗时预测表，仅作为 WF-Cache 的调度输入；本实验没有验证其预测准确率，也不能把结果解释为 GNN 算法收益。 |
| 清单（manifest） | 冻结输入、样本、配置或产物及其来源的机器可读目录。 |
| SHA-256 / hash | 文件内容指纹，用于确认输入和结果没有被替换；它不是实验指标。 |
| dirty worktree / diff | 运行时仓库存在未提交改动；复现时除 git commit 外还必须保留当时改动内容的 diff 及其 hash。 |

## 统计与实验口径

- 正式矩阵为 15 个实验单元，每个单元 5 次独立运行，共 75 次 trial；每次 trial 固定执行 24 个 session。
- 均值的 95% 置信区间使用 Student-t 区间（自由度 `df=4`）。session p95 先在每次 trial 的 24 个 session 内计算，再跨 5 次 trial 汇总。
- 配对效应使用相同重复编号（repetition）的冻结输入和到达序列。加速比大于 1 表示候选策略更快；降幅大于 0 表示候选策略的对应开销更低。
- 本实验验证调度系统的性能、资源和机制行为，不将固定子集解释为算法级或数据集级基准测试（benchmark）。质量指标的区间只反映固定工作负载的重复运行波动。
- QMSum 开放到达实验使用冻结的 parent-60 QMSum 2-GPU 容量标定值生成到达率；该容量只是负载输入，不是本轮 24-session 工作负载的新容量结论。

## 结论性解释与论文复用

### QMSum

- **可以写：** 细粒度工作流运行时能显著降低 GPU 模型驻留开销和流水线空泡。WF-Cache 相对 LG-Batch 将模型驻留开销降低 `36.416%`，并将空泡率从 `36.508%` 降至 `5.475%`。
- **必须同时写：** 该收益没有转化为突发到达场景的整批完成时间或 p95 改善。WF-Cache/LG-Batch 的整批完成加速比区间跨 1，p95 反而高 `2.436%`；相对 WF-FIFO 则明确慢 `2.1%`。
- **机制解释：** vLLM 内部排队基本被消除，但 WF-Cache 的应用层背压持续 `334.702 秒`。结果支持“系统将等待移出 GPU 驻留窗口”的解释，不支持“等待被完全消除”或“低空泡导致加速”的因果表述。
- **压力边界：** 开放到达的两个负载点都出现显著尾延迟代价，125% 负载还出现吞吐损失。当前 WF-Cache 不能写成高负载稳健性或尾延迟优化。
- **消融：** `max_num_seqs=1` 的稳定退化验证连续批处理的必要性；`queue_capacity=1` 显著增加流水线空泡和驻留开销，但其端到端区间不足以形成加速结论。

### MBPP

- **可以写：** 2-GPU 同资源下，WF-Cache 相对先进先出策略（WF-FIFO）和仅使用本轮历史的策略（WF-History）均有约 `1.05x` 的整批完成加速、约 `5%` 的 p95 降幅和约 `11%` 的模型驻留开销降幅。
- **必须同时写：** 该策略没有节能证据。相对 WF-History 的能耗显著高 `20.311%`；相对 WF-FIFO 的点估计高 `23.454%`，但区间跨 0。
- **资源曲线：** WF-Cache 2 GPU 是测试范围内的实用拐点。3 GPU 没有提高均值吞吐，反而增加 `53.871%` 的模型驻留开销；1 GPU 虽驻留更低，但吞吐只有 `2.994 个完整任务/分钟`。
- **不可写：** 3-GPU LG-Batch 与 WF-Cache 的正式比较区间过宽，不能宣称任一方更快或更节省资源。

### 质量与语义

- QMSum 三种突发到达策略没有最终空输出，ROUGE 均值接近；MBPP 六组得到完全相同的代码测试通过/失败结果。这些数据支持“调度策略没有造成可观察的系统性语义偏移”。
- QMSum 存在 137 次触及生成上限，其中 1 次发生在最终合并节点，因此不能声称零截断。固定 24 个样本上的质量结果只作为运行时质量护栏，不能写成数据集级质量提升或无损保证。

## 写作边界

- 只有重复 5 次（`n=5`）且输入内容指纹（hash）一致的实验组，才可用于正式数值和配对效应。
- 部分实验矩阵的结果不能外推到未运行配置；机制伴随指标不能单独作为因果证据。
- 固定 24 个样本用于系统验证；质量指标只是运行时质量护栏，不能代表整个数据集的算法质量。
- 合成预测缓存是冻结的调度输入，不支持图神经网络（GNN）预测精度或算法收益结论。

## 局限、异常与稳健性

- 每组只有 5 次独立完整运行。Student-t 区间能够表达本机重复波动，但对极端冷加载异常较敏感。
- MBPP 3-GPU LG-Batch 第 1 次重复的整批完成时间为 `494.228 秒`、模型加载开销为 `524.822 GPU-s`；其余四次分别为 `167.169–175.872 秒` 和 `202.716–204.627 GPU-s`。该次运行正好是矩阵中的首个 MBPP 完整运行，现象与冷文件/模型加载或运行顺序效应一致，但没有独立证据确认原因。预注册的五次结果全部保留，不做事后排除。
- MBPP 1-GPU WF-Cache 第 1 次重复也出现较高模型加载开销（`487.820 GPU-s`，其余四次为 `310.966–313.377 GPU-s`），进一步提示首轮加载效应。它不影响 2-GPU 同资源策略比较，但使 1-GPU 资源点的端到端 95% 置信区间变宽。
- QMSum 容量来自复用的 parent-60 标定。开放到达到达率的相对负载含义依赖该标定，不能外推为本轮 24 个完整任务子集的独立容量曲线。
- 能耗由 GPU 功率遥测按时间积分并扣除首个空载样本后得到，适合组内诊断，不等同于整机能耗。
- 运行环境所在代码仓库有未提交改动，并冻结了改动内容指纹。复现需要同时保留 Git 提交和当时的改动内容，不能只检出 Git 提交。
