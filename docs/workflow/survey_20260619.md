# LLM Workflow 调度方向论文调研 20260619

## 结论

本项目当前不把研究重点放在“如何设计更聪明的 workflow”上。

更准确的研究链路是：

```text
先用实验验证小模型 workflow 作为执行形态是否有存在必要性
  -> 只要质量接近单一大模型，就把它视为可调度对象
  -> 再研究 GNN-aware / workflow-aware 调度是否能降低执行开销
```

因此，论文引用应服务于两个论证，而不是泛泛证明 agent 很有用：

| 论证 | 需要什么证据 | 适合引用的论文类型 |
| --- | --- | --- |
| workflow 有存在必要性 | 多模型组合、级联、路由可以接近强模型质量，并降低成本或资源开销 | LLM cascade、model routing、mixture / ensemble |
| workflow 值得被调度 | workflow 内部结构暴露后，系统可以优化延迟、显存、缓存、能耗和成本 | compound AI serving、agent workflow scheduling |

原始阅读清单里的三篇论文不是同等重要：

| 论文 | 是否值得引用 | 引用位置 |
| --- | --- | --- |
| JARVIS / HuggingGPT | 可引用，但只能作背景 | 说明 LLM controller + 专家模型 workflow 是已有范式 |
| LLaVA-Plus | 不建议作为核心引用 | 只能作 tool-augmented / multimodal agent 背景 |
| SAGA | 值得核心引用 | 支撑 workflow / session 应作为调度对象 |

后续检索发现，更适合支撑本项目论证的是：

| 论文 | 核心价值 |
| --- | --- |
| FrugalGPT | LLM cascade 可匹配强模型质量并显著降成本 |
| Large Language Model Cascades with Mixture of Thought | 在 GSM8K 等推理任务上接近 GPT-4 质量，约 40% 成本 |
| AutoMix | 小模型先答并自检，不可靠时路由到大模型，提高单位成本收益 |
| RouteLLM | 学习 router，在弱模型和强模型间选择，降低成本且保持目标质量 |
| CascadeServe | 把 cascade 放进在线 serving 系统，联合考虑准确率、延迟和成本 |
| Cascadia | LLM cascade serving 需要联合优化部署、并行和路由 |
| Murakkab | agentic workflow 暴露结构后可用 profile-guided optimizer 做资源优化 |
| Parrot | LLM 应用不应只暴露独立请求，应用级数据流能打开端到端优化空间 |
| Kairos | multi-agent serving 需要 workflow-aware priority scheduling 和 memory-aware dispatch |
| Rethinking the Value of Multi-Agent Workflow | 反例/边界：不要默认多 agent workflow 必然优于单 agent |

## 项目当前问题

0619 时间点，项目已经完成了本地小样本 pilot：

```text
本地单一 Qwen3-32B
  vs
弱小模型 workflow: Qwen3-0.6B + Qwen3-1.7B + Qwen3-4B
  vs
强小模型 workflow: Qwen3-4B + Qwen3-8B + Qwen3-14B
```

当前实验结果见 [res_20260619.md](./res_20260619.md)：

| 方案 | GSM8K | MBPP | 总计 | 峰值显存合计 | 热态总延迟 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单一 `Qwen3-32B` | 10/10 | 9/10 | 19/20 | 61.359GB | 322.826s |
| 弱小模型 workflow | 7/10 | 6/10 | 13/20 | 12.110GB | 163.071s |
| 强小模型 workflow | 10/10 | 7/10 | 17/20 | 50.730GB | 439.081s |

这说明强小模型 workflow 已经比弱 workflow 更接近 32B，但仍不能直接宣称整体智能水平相当。

当前项目真正需要回答的是：

```text
是否存在一个质量接近单一大模型的小模型 workflow？
如果存在，这个 workflow 的执行结构是否给调度器留下优化空间？
GNN-aware 调度能否比朴素调度更好地利用这些优化空间？
```

这和“研究如何编排 workflow 才能更聪明”不同。workflow 编排只是前置实验条件，不是最终贡献点。

## 原始阅读清单

### JARVIS / HuggingGPT

链接：

- [GitHub: AI-Chef/HuggingGPT](https://github.com/AI-Chef/HuggingGPT)
- [HuggingGPT: Solving AI Tasks with ChatGPT and its Friends in Hugging Face](https://arxiv.org/abs/2303.17580)

论文做了什么：

HuggingGPT 把 ChatGPT 作为 controller，用自然语言作为统一接口，连接 Hugging Face 上的专家模型。系统流程大致是：

```text
用户请求
  -> LLM 做任务规划
  -> 按模型描述选择专家模型
  -> 执行每个子任务
  -> 汇总执行结果并返回
```

论文重点在 task planning、model selection、task execution 和 response generation。它证明了 LLM 可以作为控制器，把多个模型和工具组织成一个能完成复杂任务的 workflow。

与当前项目的联系：

它和当前项目的联系是“执行形态”层面的。

当前项目也在讨论：

```text
输入任务
  -> 多个小模型节点
  -> evaluator / verifier / repair
  -> 最终输出
```

因此 HuggingGPT 可以作为背景引用，说明“LLM controller + 多模型协作”不是本项目凭空构造的概念，而是已有 agent workflow 范式。

局限：

HuggingGPT 不直接证明以下内容：

- 小模型 workflow 能达到单一大模型智能水平。
- 多模型 workflow 的本地 GPU 资源开销更低。
- workflow-aware scheduler 能提升端到端性能。
- GNN 资源预测应该如何进入调度。

是否值得引用：

可引用，但不应作为核心证据。

建议引用位置：

```text
背景段：已有 agent 系统通常通过 LLM controller 组织多个专家模型和工具完成复杂任务。
```

不建议把它作为下面这种结论的证据：

```text
HuggingGPT 证明小模型 workflow 比单一大模型更优。
```

这个结论它没有证明。

论文做了什么：

LLaVA-Plus 是一个多模态 tool-use agent。它维护一个 skill repository，里面包含视觉和视觉语言工具，例如检测、分割、OCR、检索、生成等。模型通过多模态 instruction tuning 学会：

- 它的主要贡献是工具使用能力训练，不是 workflow 执行优化。

是否值得引用：

不建议作为核心引用。最多作为背景引用。

建议引用位置：

```text
背景段：多模态 agent 中也存在通过工具扩展模型能力的路线。
```

如果论文篇幅有限，可以不引用它。

### SAGA

链接：

- [SAGA: Workflow-Atomic Scheduling for AI Agent Inference on GPU Clusters](https://arxiv.org/abs/2605.00528)

论文做了什么：

SAGA 关注 agent inference serving。它指出传统 LLM serving scheduler 往往把每次 LLM call 当成独立请求处理，但 agent 任务通常包含多轮：

```text
Thought
  -> Action / tool call
  -> Observation
  -> 下一次 Thought
```

如果系统只按 request-level 调度，会丢掉 workflow/session 级信息，导致 KV cache 被错误回收、上下文重复计算、端到端 task completion time 变差。

SAGA 的核心机制包括：

| 机制 | 含义 |
| --- | --- |
| Agent Execution Graph | 把 agent workflow 表示成带依赖和转移概率的图 |
| workflow-aware KV cache management | 根据 workflow 后续复用概率决定缓存保留 |
| session-affinity batching | 让同一 session 的相关请求尽量落在能复用缓存的 worker |
| work stealing | 在保留 locality 的同时缓解负载不均 |
| Agent Fair Share | 用 task completion time 视角定义 fairness |

与当前项目的联系：

SAGA 与当前项目最终目标强相关。

当前项目已有：

- workflow schema / DAG。
- scheduler 初步选卡逻辑。
- GNN predictor，可预测本地模型节点的运行时间、显存、功耗等资源指标。
- GSM8K / MBPP evaluator，用于判断 workflow 质量是否达标。

SAGA 支撑的不是“小模型 workflow 更聪明”，而是：

```text
workflow 不应被调度器看成一组互相独立的模型调用。
调度器应看到 workflow/session 结构，并围绕端到端任务指标优化。
```

这正是后续 GNN-aware 调度要做的方向。

差异：

SAGA 主要优化 LLM serving 的 KV cache、session locality 和 multi-tenant fairness。当前项目更关注本地模型节点的：

```text
deployment duration
run duration
GPU memory
GPU power
OOM / retry
cold start
```

因此不能照搬 SAGA 的 KV cache 算法，但可以借鉴它的调度抽象。

是否值得引用：

值得核心引用。

建议引用位置：

```text
系统动机段：agent workflow 应作为一等调度对象，request-level scheduling 会丢失关键结构信息。
```

## 补充检索论文

### FrugalGPT

链接：

- [FrugalGPT: How to Use Large Language Models While Reducing Cost and Improving Performance](https://arxiv.org/abs/2305.05176)

论文做了什么：

FrugalGPT 研究 LLM cascade。它不是每个请求都直接调用最贵最强模型，而是学习一个级联策略：

```text
先调用便宜模型
  -> 判断答案是否可靠
  -> 可靠则停止
  -> 不可靠则继续调用更强模型
```

论文在多个 API 模型和多个数据集上评估成本-质量权衡。它报告 FrugalGPT 可以在匹配最佳单模型性能的同时显著降低成本。例如论文表格中，为达到相同准确率：

| 数据集 | 最佳单模型 | FrugalGPT 成本节省 |
| --- | --- | ---: |
| HEADLINES | GPT-4 | 98.3% |
| OVERRULING | GPT-4 | 73.3% |
| COQA | GPT-3 | 59.2% |

与当前项目的联系：

这是最适合支撑“workflow / cascade 有存在必要性”的论文之一。

当前项目的小模型 workflow 不是完全相同的 cascade，但论证结构类似：

```text
不是每个任务都必须由最大模型独立完成。
可以用多个较便宜模型或条件路径，在接近强模型质量时降低成本。
```

差异：

FrugalGPT 使用商业 API 价格作为 cost，当前项目使用本地 GPU 资源指标：

```text
显存
冷启动
运行时间
吞吐
功耗代理
OOM / retry
```

因此它不能直接证明当前本地 Qwen workflow 更省资源，但能证明“级联/组合模型在质量-成本曲线上可能优于单模型”。

是否值得引用：

值得核心引用。

建议引用位置：

```text
相关工作：LLM cascade 已被证明可以在接近强模型质量时显著降低推理成本。
```

### Large Language Model Cascades with Mixture of Thought Representations

链接：

- [Large Language Model Cascades with Mixture of Thought Representations for Cost-Efficient Reasoning](https://arxiv.org/abs/2310.03094)

论文做了什么：

这篇论文专门研究 reasoning 任务上的 LLM cascade。它让弱模型先生成多个答案，并用答案一致性判断题目是否简单；如果弱模型答案足够一致，就接受弱模型答案，否则升级到强模型。

它还引入不同 thought representation：

| 表示 | 含义 |
| --- | --- |
| CoT | Chain-of-Thought |
| PoT | Program-of-Thought |
| MoT | Mixture of Thought，混合 CoT 和 PoT |

实验覆盖六个 reasoning benchmark，包括 GSM8K、ASDIV、TabMWP、DATE、Navigate、CREPE。论文使用 GPT-3.5-turbo 作为弱模型，GPT-4 作为强模型。

关键结果：

```text
MoT cascade 平均准确率约 0.929
GPT-4-CoT-SC 平均准确率约 0.931
MoT cascade 只需要约 40% 的 GPT-4-CoT-SC 成本
```

与当前项目的联系：

这篇比 FrugalGPT 更贴近当前项目的 GSM8K 方向，因为它明确覆盖数学推理任务，并直接比较弱模型 cascade 与 GPT-4 强模型。

它支持当前项目的前置假设：

```text
在可分解或可判别难度的任务上，小/弱模型组合可能接近强模型质量，并降低成本。
```

差异：

这篇仍然是 API 成本口径，不是本地 GPU profile 口径。它也不是 GNN 调度论文。

是否值得引用：

值得核心引用，尤其适合写在 GSM8K / reasoning workflow 实验动机附近。

### AutoMix

链接：

- [AutoMix: Automatically Mixing Language Models](https://arxiv.org/abs/2310.12963)

论文做了什么：

AutoMix 研究在小模型和大模型之间自动切换。它先让小模型回答，再让小模型做 self-verification；如果自检不可靠，就用 router 决定是否调用更大的模型。

简化流程是：

```text
小模型生成答案
  -> 小模型/验证器估计答案可靠性
  -> router 判断是否升级到大模型
```

论文强调两个点：

- 不需要访问模型 logits 或权重，适合黑盒模型。
- 用 POMDP-based router 处理 noisy self-verification。

论文报告在 LLaMA2-13B/70B 等设置上，AutoMix 相比强 baseline 提高单位成本收益，达到相近性能时可降低超过 50% 计算成本。

与当前项目的联系：

AutoMix 支撑的是“动态使用模型能力”的合理性：

```text
简单样本不必总走最大模型。
复杂样本才值得升级到更强模型。
```

当前项目后续如果定义 workflow profile，可以记录：

```text
first-pass 是否通过
repair 是否触发
verifier 置信度
升级到更大模型的比例
```

这些都和 AutoMix 的思想相通。

差异：

AutoMix 更像 model switching / routing，不是完整 DAG workflow，也不是 GPU 调度系统。

是否值得引用：

值得引用，但作为 FrugalGPT / MoT cascade 的补充。

### RouteLLM

链接：

- [RouteLLM: Learning to Route LLMs with Preference Data](https://arxiv.org/abs/2406.18665)

论文做了什么：

RouteLLM 学习一个 router，在弱模型和强模型之间做二选一。目标是：

```text
在达到目标质量的前提下，尽量少调用强模型。
```

论文关注 routing，而不是 cascade。每个 query 通常只调用一个模型，因此比 cascade 更少增加延迟。

它提出的评价口径包括：

| 指标 | 含义 |
| --- | --- |
| strong model call rate | 强模型调用比例，越低越省成本 |
| response quality | 输出质量 |
| PGR / APGR | router 恢复了多少弱强模型性能差距 |

论文报告 router 可以在多个 benchmark 上实现超过 2x 成本节省，并保持目标质量。

与当前项目的联系：

RouteLLM 可以支撑“模型选择本身就是可优化对象”。

当前项目后续的 GNN-aware scheduler 不负责判断答案质量，但它可以在质量达标 workflow 集合中选择更低资源配置。这个思想和 RouteLLM 的目标类似：

```text
质量约束固定后，优化成本。
```

差异：

RouteLLM 优化的是请求到模型的语义路由；当前项目优化的是本地模型节点到 GPU 的资源调度。两者都做 cost-quality tradeoff，但作用层不同。

是否值得引用：

值得引用，适合支撑“quality-constrained cost optimization”。

### CascadeServe

链接：

- [CascadeServe: Unlocking Model Cascades for Inference Serving](https://arxiv.org/abs/2406.14424)

论文做了什么：

CascadeServe 把 model cascade 放进在线 serving 系统。它指出 cascade 有两个系统价值：

- 在保持 accuracy 的同时减少工作量。
- 暴露更细粒度的 work-accuracy tradeoff，可以适应请求到达率变化。

但 cascade 真正用于 serving 时，会遇到系统问题：

```text
workload adaptation
model replication
hardware allocation
inference scheduling
request batching
```

CascadeServe 通过 offline gear plan 和 online adaptation 处理这些问题。论文报告相对 state-of-the-art baseline 有 2-3x 成本节省。

与当前项目的联系：

它非常适合衔接本项目的第二阶段：

```text
一旦 workflow / cascade 质量达标，系统问题会变成如何部署、调度和适应负载。
```

当前项目的 GNN predictor 可以提供 CascadeServe 类系统需要的 model profile 信号：

```text
deploy duration
run duration
GPU memory
GPU power
```

差异：

CascadeServe 面向通用 ML cascade serving，不专门是 LLM workflow，也不使用 GNN 图结构预测模型资源。

是否值得引用：

值得核心引用，用于支撑“cascade 不只是算法问题，还是 serving / scheduling 问题”。

### Cascadia

链接：

- [Cascadia: An Efficient Cascade Serving System for Large Language Models](https://arxiv.org/abs/2506.04203)

论文做了什么：

Cascadia 是面向 LLM cascade 的 serving 系统。它联合优化：

| 决策 | 含义 |
| --- | --- |
| deployment plan | 不同模型如何部署、分配资源和并行 |
| routing strategy | 请求如何在小、中、大模型之间流动 |
| quality constraint | 在质量约束下优化 latency / throughput |

论文强调 LLM cascade 的不同模型有不同显存和算力需求，不能只做静态 routing，也不能只做静态部署。它报告 Cascadia 在多种 workload trace 和模型 cascade 下，相比单模型和已有 cascade baseline 有更好的延迟、吞吐和 SLO 表现。

与当前项目的联系：

Cascadia 与本项目后续方向非常近：

```text
本项目：质量达标 workflow -> profile -> GNN-aware 调度 replay
Cascadia：质量约束 cascade -> deployment + routing co-optimization
```

差异：

Cascadia 关注 LLM cascade serving 的系统 co-design。当前项目的特色是用 GNN 预测本地模型节点资源，并把预测信号放入 workflow 调度。

是否值得引用：

值得核心引用。

### Murakkab

链接：

- [Murakkab: Resource-Efficient Agentic Workflow Orchestration in Cloud Platforms](https://arxiv.org/abs/2508.18298)

论文做了什么：

Murakkab 面向 agentic workflow serving。它指出今天的 agent workflow 往往把 agent logic、模型选择和硬件选择紧耦合在一起，导致系统无法跨层优化 accuracy、latency、energy 和 cost。

它提出：

```text
declarative workflow specification
  + profile-guided optimizer
  + adaptive runtime
```

核心思想是把 workflow specification 与 execution configuration 解耦，让系统可以在满足 SLO 的前提下动态选择模型、工具和硬件配置。

论文报告在多种 workflow 上：

```text
GPU usage 最多降低 2.8x
energy consumption 最多降低 3.7x
cost 最多降低 4.3x
同时保持 SLO
```

与当前项目的联系：

这是和当前项目整体路线最贴近的论文之一。

当前项目已有对应基础：

| Murakkab 概念 | 当前项目对应 |
| --- | --- |
| declarative workflow specification | `src/workflow/schema.py` 和 YAML loader |
| model / workflow profile | 当前正在补质量结果和本地 model profile |
| optimizer / runtime | `src/workflow/scheduler.py` 和 GNN predictor 雏形 |
| quality SLO | GSM8K exact match、MBPP pass@1 |
| resource target | deploy/run/mem/power、OOM/retry |

是否值得引用：

值得核心引用。它支撑的是“workflow 调度优化本身有系统价值”，不是“如何让 workflow 更聪明”。

### Parrot

链接：

- [Parrot: Efficient Serving of LLM-based Applications with Semantic Variable](https://arxiv.org/abs/2405.19888)

论文做了什么：

Parrot 指出 LLM 应用通常由多个 LLM request 组成，但公共 LLM service 只看到一个个独立请求，因此无法优化端到端应用性能。它提出 Semantic Variable，把 prompt 中的输入/输出变量标记出来，让 serving system 能看到跨请求的数据流关系。

论文报告 Parrot 在一些 LLM application use case 上可实现数量级的端到端性能提升。

与当前项目的联系：

Parrot 支撑的是一个系统原则：

```text
如果 serving layer 看不到应用级结构，只能做局部优化。
把 workflow / dataflow 暴露给 serving layer，才有端到端优化空间。
```

这和当前项目的 workflow schema、profile 和 scheduler 方向一致。

差异：

Parrot 主要处理 LLM prompt / semantic variable / request correlation，不是本地小模型 GPU 资源预测。

是否值得引用：

值得作为系统背景引用，优先级低于 Murakkab、SAGA、Cascadia。

### Kairos

链接：

- [Kairos: Low-latency Multi-Agent Serving with Shared LLMs and Excessive Loads in the Public Cloud](https://arxiv.org/abs/2508.06948)

论文做了什么：

Kairos 研究 multi-agent 应用在共享 LLM serving 下的低延迟调度。它发现不同 agent role 会导致明显不同的输出长度、推理延迟和显存需求；如果 serving 系统忽略这些差异，就会产生排队、head-of-line blocking 和 GPU memory overload。

Kairos 包含：

| 模块 | 作用 |
| --- | --- |
| workflow orchestrator | 收集 agent-specific 信息并分析 workflow |
| workflow-aware priority scheduler | 根据剩余执行延迟做优先级 |
| memory-aware dispatcher | 根据 GPU memory demand 分发请求 |

论文在 A40 GPU 上评估，报告端到端延迟降低 17.8% 到 28.4%。

与当前项目的联系：

Kairos 很适合支撑“agent / workflow 节点角色会影响系统资源行为，因此调度器需要看到 workflow 结构和节点 profile”。

当前项目的强 workflow 中也能看到类似现象：

- GSM8K solver 和 MBPP coder / repair 的 token 行为不同。
- MBPP repair 触发导致端到端延迟显著增加。
- 不同模型节点显存差异明显，`Qwen3-14B` 单卡峰值接近 V100 32GB 上限。

是否值得引用：

值得引用，尤其适合讨论 workflow-aware priority 和 memory-aware dispatch。

### Small Language Models are the Future of Agentic AI

链接：

- [Small Language Models are the Future of Agentic AI](https://arxiv.org/abs/2506.02153)

论文做了什么：

这是一篇 position paper。它的主张是：agentic AI 系统中的大量语言模型调用是重复、范围明确、非开放对话式的，因此 small language models 在很多 agentic invocation 中已经足够强，并且更适合生产部署。

它强调：

```text
SLM 对许多 agent 子任务已经足够强
SLM 更低延迟、更低显存、更低成本
复杂开放任务仍可保留 LLM
异构 agentic system 是自然选择
```

与当前项目的联系：

它适合作为高层动机引用，说明“不是所有 agent 节点都必须使用最大模型”。这与当前项目探索 `4B + 8B + 14B` workflow 对照 `32B` 的方向一致。

局限：

它是 position paper，不是一个严格系统实验来证明某个小模型 workflow 接近某个单一大模型。

是否值得引用：

可引用，但不要作为关键实验证据。

### Mixture-of-Agents

链接：

- [Mixture-of-Agents Enhances Large Language Model Capabilities](https://arxiv.org/abs/2406.04692)

论文做了什么：

Mixture-of-Agents 让多个 LLM agent 分层生成和聚合回答。后续层可以读取前一层多个 agent 的输出，再进一步生成更好的回答。论文报告 open-source LLM 组成的 MoA 在 AlpacaEval 2.0、MT-Bench、FLASK 等 benchmark 上可超过 GPT-4 Omni。

与当前项目的联系：

它支持“多个模型/agent 的组合可能达到或超过单一强模型质量”。

局限：

它不直接讨论本地 GPU 资源调度，也不一定降低成本。多层多 agent 可能显著增加延迟和调用成本。因此它只适合支持“组合可能提升能力”，不适合直接支持“更有性能开销优势”。

是否值得引用：

可选引用，不建议作为主证据。

### Rethinking the Value of Multi-Agent Workflow

链接：

- [Rethinking the Value of Multi-Agent Workflow: A Strong Single Agent Baseline](https://arxiv.org/abs/2601.12307)

论文做了什么：

这篇论文质疑同质 multi-agent workflow 的价值。它认为许多 multi-agent workflow 中的 agent 使用同一个 base model，只是角色 prompt、位置或工具不同。这样的 workflow 可能被一个 single agent 通过多轮上下文模拟出来，并且 single agent 可以复用 KV cache，因此成本更低。

论文提出 OneFlow，用 meta-LLM 和 MCTS 搜索 workflow，再转成 single-agent execution。实验覆盖代码、数学、问答、规划等任务。

与当前项目的联系：

这篇是重要的反例和边界。

它提醒当前项目不能预设：

```text
多模型 / 多节点 workflow 一定比单一模型有价值。
```

本项目当前路线正好可以避免这个问题：

```text
先做 Qwen3-8B / 14B / 32B direct baseline
再做小模型 workflow 对照
只有 workflow 质量接近且相对单模型有优势，才进入调度实验
```

是否值得引用：

值得引用。它能让论证更严谨，说明项目不是盲目追随 multi-agent/workflow，而是通过实验验证 workflow 是否有存在必要性。

### C3PO

链接：

- [C3PO: Optimized Large Language Model Cascades with Probabilistic Cost Constraints for Reasoning](https://arxiv.org/abs/2511.07396)

论文做了什么：

C3PO 研究 reasoning 任务上的 cost-controlled LLM cascade。它不用人工标签，而是用未标注模型输出构建 cascade，并通过 conformal prediction 给 test-time cost 超预算概率提供约束。

论文覆盖 GSM8K、MATH-500、BigBench-Hard、AIME 等 reasoning benchmark，目标是在成本约束下减少相对最强模型的 regret。

与当前项目的联系：

它说明 cascade 不只是经验策略，也可以有概率成本约束和泛化保证。对当前项目的启发是，后续 SLO 可以不仅写成平均成本，还可以写成：

```text
p95 latency 不超过阈值
显存超限概率不超过阈值
cost / retry 超预算概率不超过阈值
```

是否值得引用：

可作为补充引用。优先级低于 FrugalGPT、MoT cascade、Cascadia、Murakkab。

### 其他同类 routing / cascade 论文

本轮检索还出现了一批同类论文。它们与项目诉求有联系，但大多属于 query-level routing 或 cascade 策略，和本项目最终的 workflow-level GPU 调度还有一层距离。因此建议把它们作为扩展引用，而不是主线核心引用。

| 论文 | 做了什么 | 与当前项目的关系 | 引用优先级 |
| --- | --- | --- | --- |
| [MixLLM: Dynamic Routing in Mixed Large Language Models](https://arxiv.org/abs/2502.18482) | 用 contextual bandit 在候选 LLM 中为每个 query 选择模型，同时考虑质量、成本和延迟；论文报告在时间约束下达到 GPT-4 质量的 97.25%，成本为 24.18%。 | 支撑“质量、成本、延迟可以被统一放进 routing 目标”，但它优化的是 query 到模型的选择，不是 workflow DAG 到 GPU 的调度。 | 中 |
| [PickLLM: Context-Aware RL-Assisted Large Language Model Routing](https://arxiv.org/abs/2412.12170) | 用轻量 RL 在模型池中在线选择 LLM，reward 同时包含准确率、成本和延迟。 | 支撑“模型选择可以被表述成在线优化问题”，但实验和目标都偏 routing，不直接证明小模型 workflow 接近单一大模型。 | 低到中 |
| [Agreement-Based Cascading for Efficient Inference](https://arxiv.org/abs/2407.02348) | 用同层模型 ensemble 的 agreement 决定是否升级到更大模型；目标是让 cascade 作为现有模型的 drop-in replacement，并提升效率和准确率。 | 与 verifier / self-consistency 思想相关，能补充解释为什么多小模型一致性可作为是否升级的信号。 | 中 |
| [UCCI: Calibrated Uncertainty for Cost-Optimal LLM Cascade Routing](https://arxiv.org/abs/2605.18796) | 用 calibrated uncertainty 决定小模型是否升级到大模型，并在约束下优化成本；生产 NER workload 中报告 4B/12B cascade 的成本降低。 | 提醒当前项目后续如果做质量门控，应关注置信度校准，而不是只用经验阈值。它不直接解决 workflow 调度。 | 低到中 |

这些论文进一步强化了一个判断：前人的工作已经反复验证“不是每个 query 都必须由最大模型处理”。但它们大多停留在 query-level model selection，本项目如果继续推进，需要把这个思想上升到：

```text
质量达标 workflow 集合
  -> 节点级资源 profile
  -> workflow-aware / GNN-aware GPU 调度
```

这也是为什么主线引用仍应优先选择 FrugalGPT、MoT cascade、AutoMix、RouteLLM、CascadeServe、Cascadia、Murakkab 和 SAGA。

## 对当前项目写法的建议

建议后续技术报告或论文中明确避免以下过强表述：

```text
小模型 workflow 比单一大模型更聪明。
小模型 workflow 必然更省资源。
多 agent / 多模型架构天然优于单模型。
```

更稳妥的表述是：

```text
已有 LLM cascade、routing 和 agentic workflow serving 研究表明，
多模型组合可以在部分任务中接近强模型质量，并带来成本或资源优化空间。
本项目不假设 workflow 必然优于单模型，而是先用本地 Qwen direct baseline
和小模型 workflow 做质量验证。只有质量接近单一大模型的 workflow，
才进入后续 profile 和 GNN-aware 调度实验。
```

建议当前项目的实验设计保留以下对照：

| 对照 | 目的 |
| --- | --- |
| `Qwen3-32B direct` | 本地单一大模型主 baseline |
| `Qwen3-14B direct` | 判断强 workflow 收益是否只是来自 14B |
| `Qwen3-8B direct` | 判断中模型 direct 是否足够 |
| 强小模型 workflow | 目标 workflow |
| no-repair workflow | 判断 repair 是否真的贡献质量 |
| no-verifier workflow | 判断 verifier 是否值得其延迟成本 |

后续 profile 至少应记录：

```text
workflow_name
sample_id
dataset
quality_metric
quality_score / passed
node_outputs
node_latency_sec
end_to_end_latency_sec
repair_triggered
first_pass_passed
after_repair_passed
model_name
device
peak_memory_gb
cold_start_sec
tokens_per_sec
```

这些字段能把文献中的三个层次连起来：

```text
FrugalGPT / MoT / AutoMix / RouteLLM:
  质量约束下选择更便宜模型或路径

CascadeServe / Cascadia:
  cascade 达标后需要 serving-level 部署和调度

Murakkab / SAGA / Parrot / Kairos:
  workflow 结构暴露后，调度器才能优化端到端成本
```

## 最终判断

`survey_20260619.md` 原来的三篇论文里，只有 SAGA 与最终调度目标强相关；HuggingGPT 可作为 workflow 背景；LLaVA-Plus 不应占据主要篇幅。

如果目的是论证“前人已经验证了小模型或弱模型组合可以接近单一强模型，并可能更省成本”，应重点引用 FrugalGPT、MoT cascade、AutoMix 和 RouteLLM。

如果目的是论证“这种 workflow / cascade 一旦存在，就值得系统调度优化”，应重点引用 CascadeServe、Cascadia、Murakkab、SAGA，并用 Parrot / Kairos 作为补充。

如果目的是让论证更可信，还应引用 Rethinking the Value of Multi-Agent Workflow，说明本项目不会默认 workflow 一定有效，而是先通过 direct baseline 和消融实验验证它是否值得被调度。
