# 训练时长中 Checkpoint 保存开销影响分析

> 更新时间：2026-04-15  
> 目的：评估历史实验结果里训练阶段 `duration_sec` 因 checkpoint 保存带来的偏高幅度，并确认当前这批结果是否可以继续用于训练时长分析。

## 1. 结论

- 当前这批已完成实验里，checkpoint 保存对训练阶段 `duration_sec` 的影响整体不大。
- 按配置级别估算，checkpoint 保存开销占训练时长的比例约为 `0.14%` 到 `2.19%`。
- 加权中位数约为 `1.03%`，说明旧结果中的训练时长通常只会被轻微抬高。
- 当前 `config/arch/*.yaml` 这批实验配置全部为 `export_onnx: false`，因此现有结果里没有可直接用于“训练时间 vs 导出时间占比”分析的导出时长数据。

## 2. 数据范围

- 分析对象：`config/arch/*.yaml` 当前 15 份模型配置对应的最新 `res/*/results/*_results.json`
- 有可用结果的配置：`13/15`
- 缺失结果的配置：
  - `inception_v3_variants.yaml`
  - `resnet50_variants.yaml`
- 有可用导出时长的配置：`0`

## 3. 方法

- 对每份 `config/arch/*.yaml`，匹配对应模型目录下时间戳最新的结果 JSON。
- 从结果 JSON 中读取每个变体的 `training.timings.started_at_ts` 与 `ended_at_ts`，计算原始训练时长。
- 对每个配置，选取一个“中位大小”的历史 checkpoint 文件，使用单次 `torch.save(...)` 重放写盘，估算 checkpoint 保存耗时。
- 用该估算值与该配置的训练时长中位数做比值，得到“训练时长中 checkpoint 保存占比”的近似量级。

说明：

- 这不是逐变体精确重算，而是配置级近似估算。
- 由于写盘环境、缓存状态和文件大小不同，单次 benchmark 只适合判断“影响是否显著”，不适合当成毫秒级精确修正值。
- 本次分析使用的是历史已生成的 checkpoint 文件，不涉及重新跑训练，也不修改正式实验结果。

## 7. 对已有结果的解释

- 如果目标是分析训练阶段时长趋势、模型间排序或量级差异，当前历史结果通常仍可直接使用。
- 如果目标是做非常细粒度的训练时长比较，优先关注 `VGG16`、`VGG19` 这两类高占比配置，因为它们的 checkpoint 保存占比接近 `2%`。
- 对 `BERT Large`、`ViT`、`MobileNet` 这类训练时长较长或 checkpoint 较小的配置，checkpoint 保存开销几乎不会影响结论。

## 8. 关于导出时长

- 当前 `config/arch/*.yaml` 下这批实验配置全部为 `export_onnx: false`。
- 对应结果 JSON 里的 `onnx_export` 字段均为 `null`，没有可直接分析的导出阶段时间窗口。
- 因此本次文档只能回答“训练时长中 checkpoint 保存占比是否显著”，不能直接回答“训练时间和模型导出时间占比”。

## 9. 建议

- 继续使用现有历史训练 `duration_sec` 做总体分析是可接受的。
- 如果后续需要严谨比较训练时长，建议在新结果中直接使用移除 checkpoint 保存后的训练计时逻辑。
- 如果后续需要分析训练/导出占比，需要单独补跑一批 `export_onnx: true` 的实验，或为导出阶段补齐独立监控数据。
